# Feature Specification: KP-09 — ورودی سرویس واسط Jira

**Feature Branch**: `master` (platform planning; no feature branch created)

**Created**: 2026-10-22

**Status**: Draft — مشخصات و طراحی اولیه؛ پیاده‌سازی و پذیرش اجرا نشده است.

**Input**: User description: «نیازمندی دریافت‌شده از سرویس واسط Jira به همان درخواست داخلی نسخه‌دار تبدیل شود، منشأ حفظ و دریافت تکراری کنترل شود و PO همچنان ورود را تصمیم بگیرد.» مطابق مدل کارکرد و بستهٔ KP-09.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - تثبیت قرارداد واقعی سرویس (Priority: P1)

توسعه‌دهنده نمونهٔ واقعی را پاک‌سازی و نگاشت و خطاهای آن را با تیم ثبت می‌کند.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: نمونهٔ تأییدشده بدون secret به shape fixture تبدیل و هر فیلد ورودی قابل ردیابی باشد.

**Acceptance Scenarios**:

1. **Given** نمونهٔ واقعی و توضیح احراز هویت/خطا از مالک سرویس، **When** قرارداد بررسی می‌شود، **Then** نگاشت و فیلد غایب/اختیاری ثبت شوند. (AS-11)
2. **Given** نمونهٔ واقعی موجود نیست، **When** mapper production خواسته می‌شود، **Then** کار نگاشت مسدود و schema ساختگی ساخته نشود. (AS-12)

### User Story 2 - دریافت درخواست نسخه‌دار (Priority: P1)

فرد مجاز نیازمندی Jira را در پروژهٔ خودش import می‌کند و متن اصلی را می‌بیند.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: ورودی معتبر یک request با provenance بسازد؛ اصلاح منبع یک revision جدید بسازد.

**Acceptance Scenarios**:

1. **Given** پاسخ واقعی معتبر و اتصال پروژه، **When** import انجام می‌شود، **Then** متن اصلی، شناسهٔ منبع و نسخهٔ قابل شناسایی در درخواست ذخیره شوند. (AS-21)
2. **Given** پاسخ ناقص یا غیرقابل اعتبارسنجی، **When** import انجام می‌شود، **Then** بدون ساخت درخواست ناقص خطای قابل اقدام ثبت شود. (AS-22)

### User Story 3 - ورود با تصمیم PO و دریافت مجدد (Priority: P1)

PO پس از import نسخهٔ فلو را انتخاب می‌کند و دریافت بعدی به تصمیم قبلی دست نمی‌زند.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: دوباره‌خوانی همان issue instance تکراری نسازد و نسخهٔ تازه نیازمند تصمیم مناسب باشد.

**Acceptance Scenarios**:

1. **Given** درخواست واردشده و بدون PO approval، **When** اجرا خواسته می‌شود، **Then** شروع متوقف باشد. (AS-31)
2. **Given** دریافت تکراری هم‌زمان یا منبع تغییرکرده، **When** import دوباره انجام می‌شود، **Then** همان محتوا no-op؛ تغییر یک revision تازه با تصمیم قبلی غیرقابل انتقال بسازد. (AS-32)

### Edge Cases

- بعد از sample: create/update/no-op، outoforder، concurrentimport، 401/403/429/5xx/timeout/oversize/badformat، missingrequired، crossconnector/project، credentialredaction، PO gate و manualregression؛ فعلاً هیچ livecall انجام نشود.
- تغییر مجوز در نشست باز؛ شناسهٔ معتبر پروژهٔ دیگر؛ تکرار کلیک و رقابت با revision قدیمی؛ پاسخ خطا نباید secret یا محتوای غیرمجاز افشا کند.

## Requirements *(mandatory)*

### Functional Requirements

تمام الزام‌های زیر اجباری‌اند (MUST)؛ جزئیات پیاده‌سازی در plan و contracts قرار دارد.

- **FR-001** (US1): قبل از نگاشت، نمونهٔ واقعی موفق و خطا، semantics شناسه/نسخه/زمان/صفحه‌بندی و روش auth سرویس واسط دریافت و تأیید شوند.
- **FR-002** (US1): نمونهٔ واقعی و credentials خصوصی بمانند؛ fixture مشترک sanitized و هم‌شکل منبع واقعی و فاقد PII باشد.
- **FR-003** (US1): قرارداد از سرویس واسط استخراج شود؛ فیلد بومی Jira یا لینک جهت‌دار فرضی جای حقیقت سرویس ننشیند.
- **FR-004** (US1): نبود sample یا دسترسی معتبر وضعیت blocked بسازد؛ بخش داخلی و مسیر دستی مستقل باقی بمانند.
- **FR-005** (US2): پاسخ اعتبارسنجی‌شده به قرارداد داخلی KP-04 تبدیل و متن اصلی و provenance حفظ شوند؛ فقدان داده صریح باشد.
- **FR-006** (US2): اختیار import و credential به همان پروژه محدود باشد؛ account/service actor واقعی دریافت ثبت شود و secret در پاسخ یا log نباشد.
- **FR-007** (US2): کلید dedupe ترکیب scope، connector و external identity باشد؛ محتوای یکسان no-op و تغییر واقعی revision تازه بسازد.
- **FR-008** (US2): خطای شبکه، auth، format و rate-limit از هم قابل تشخیص و retry محدود فقط برای خواندن ایمن باشد.
- **FR-009** (US3): import به‌خودی‌خود flow انتخاب، PO approval ثبت یا مرحله اجرا نکند؛ مسیر تصمیم KP-04 حفظ شود.
- **FR-010** (US3): یک پاسخ قدیمی یا خارج‌ترتیب متن جدید را بازنویسی نکند؛ اگر نسخهٔ منبع قابل مقایسه نیست، conflict نیازمند بررسی ثبت شود.
- **FR-011** (US3): خطای import به درخواست‌های دستی و سابقهٔ قبلی آسیب نزند؛ حذف issue منبع تاریخچهٔ داخلی را حذف نکند.
- **FR-012** (US3): رابط فارسی/RTL منشأ، آخرین دریافت، no-op/conflict/error و شرط PO را نشان دهد؛ پذیرش live تا نمونه و اتصال واقعی قابل اجرا اعلام نشود.

### Key Entities *(include if feature involves data)*

- **ConnectorBinding**: اتصال مجاز همان پروژه با مرجع امن تنظیمات و محدودهٔ منبع.
- **ImportEnvelope**: ورودی داخلی Kara پس از دریافت منبع؛ شکل پاسخ سرویس بیرونی را فرض نمی‌کند.
- **ImportReceipt**: رسید دریافت با منشأ، محتوا و درخواست متناظر برای تشخیص دریافت تکراری.
- **MappingRecord**: نگاشت تأییدشده از فیلدهای واقعی سرویس به درخواست داخلی، پس از دریافت نمونه.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: هر شش سناریوی AS-11 تا AS-32 با نتیجهٔ مورد انتظار و شاهد قابل ردیابی پاس شوند؛ مورد بحرانی اجرا نشده یا شکست‌خورده باقی نماند.
- **SC-002**: در ماتریس دو پروژه، حساب نامجاز و حساب دارای مجوز لغوشده، تعداد خواندن یا اثر غیرمجاز صفر باشد؛ تمام مسیرهای مربوط پوشش داشته باشند.
- **SC-003**: در تغییر نسخه، تکرار اقدام و شکست‌های این بسته، صددرصد سوابق لازم و ارتباط عامل/نسخه باقی و اثر منطقی مضاعف صفر باشد.
- **SC-004**: هر سه مسیر انسانی این بسته با دادهٔ ساختگی، متن فارسی، چیدمان RTL و صفحه‌کلید قابل تکمیل باشند؛ وضعیت خالی، انتظار و خطا اقدام بعدی را مشخص کنند.

## Assumptions

- وابستگی: KP-04 پذیرفته‌شده و نمونهٔ واقعی پاک‌سازی‌شدهٔ سرویس واسط؛ نمونه اکنون موجود نیست. پذیرش پیش‌نیازها باید با گزارش واقعی احراز شود؛ نوشتن این spec به معنی تحقق آن‌ها نیست.
- خارج از محدوده: حدس schema بومی Jira، اتصال مستقیم جای سرویس واسط، ساخت credential، فعال‌سازی webhook بدون قرارداد واقعی و تأیید خودکار PO.
- مجوزهای بومی، حساب واقعی، نقش‌های KP-01 و قواعد انسانی قرارداد 1.0.0 باقی‌اند؛ نقش مدیریتی به‌خودی‌خود PO نیست.
- سنجش اولیه با حداقل دو پروژه و چند حساب مستقل آزمایش است؛ SLA تولید و ظرفیت Kubernetes در این گام تعیین نمی‌شوند.
- داده و نمونه‌های آزمون ساختگی‌اند؛ credential، سند مشتری و پاسخ خام اتصال در Git قرار نمی‌گیرند.

## Clarifications

- تصمیم‌های قبلی کاربر بازاستفاده شدند: Kara نام همین محصول است؛ مدیریت دسترسی با ادمین کل و مدیر پروژه، شروع مراحل توسط انسان و نهایی‌سازی با عامل واقعی است.
- سؤال تازه‌ای پرسیده نشد؛ پاسخ یا تأیید جدیدی به کاربر نسبت داده نمی‌شود. ساخت ایجنت کلاسور پس از پذیرش KP-08 است.
- وضعیت ورودی/مرز اجرایی: BLOCKED-INPUT: نمونهٔ موفق/خطا، نسخه‌بندی و ترتیب، صفحه‌بندی، auth، attachment و rate-limit سرویس موجود نیست. plan نگاشت فیلد و پذیرش زنده عمداً نهایی نیست؛ این مانع تکمیل port داخلی/مشخصات رفتار یا مسیر دستی نیست. عرضهٔ متعهد به Jira بدون رفع این gate ممنوع.
