# Feature Specification: KP-02 — تعریف ایجنت قابل اجرا و مجوزهای صریح

**Feature Branch**: `master` (platform planning; no feature branch created)

**Created**: 2026-10-22

**Status**: Draft — مشخصات و طراحی اولیه؛ پیاده‌سازی و پذیرش اجرا نشده است.

**Input**: User description: «ادمین کل یا مدیر پروژه یک برنامهٔ منتشرشده را به ایجنت مدیریت‌شده متصل کند و اقدام‌های مجاز هر عضو را جدا تعیین کند تا عضو عادی بتواند کار مجازش را بدون دسترسی ویرایش انجام دهد.» مطابق مدل کارکرد و بستهٔ KP-02.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ثبت تعریف و مجوز (Priority: P1)

مدیر پروژه از برنامه‌های همان پروژه نسخهٔ منتشرشده را انتخاب و مجوزهای اعضای فعال را ذخیره می‌کند.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: مدیر دو عضو را با اختیار متفاوت ثبت کند و پس از بازخوانی همان نسخه و اختیارها را ببیند.

**Acceptance Scenarios**:

1. **Given** برنامهٔ منتشرشده و دو عضو فعال، **When** مدیر run را به عضو عادی و feedback را به عضو دیگری می‌دهد، **Then** فقط همین اقدام‌ها ثبت و قابل مشاهده‌اند. (AS-11)
2. **Given** یک editor فاقد اختیار مدیریت، **When** برای خودش grant می‌سازد، **Then** تغییر رد و سیاست قبلی حفظ می‌شود. (AS-12)

### User Story 2 - اجرای مجاز با حساب عادی (Priority: P1)

عضو عادی دارای run، نسخهٔ مجاز ایجنت را در مسیر کنترل‌شده اجرا می‌کند و حق انتشار نمی‌گیرد.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: یک normal مجاز اجرا کند؛ همان فرد نتواند draft یا مجوز دیگری را ویرایش کند.

**Acceptance Scenarios**:

1. **Given** عضو عادی با run و نسخهٔ منتشرشده، **When** اجرای کنترل‌شده را درخواست می‌کند، **Then** همان نسخه با هویت واقعی او اجرا و نتیجهٔ مجاز برگردانده می‌شود. (AS-21)
2. **Given** فقط مجوز run، **When** انتشار یا بازخورد بدون grant را درخواست می‌کند، **Then** بدون ایجاد اثر رد می‌شود. (AS-22)

### User Story 3 - لغو و حفظ نسخه (Priority: P1)

مدیر مجوز را لغو می‌کند و عضو در درخواست بعدی دیگر حق اجرا یا خواندن دادهٔ تازهٔ خصوصی ندارد.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: با نشست باز، grant را لغو کنید؛ درخواست بعدی رد شود و سابقهٔ اجرا باقی بماند.

**Acceptance Scenarios**:

1. **Given** نشست باز و grant لغوشده، **When** عضو اجرا یا دریافت نتیجهٔ تازه می‌خواهد، **Then** سیاست تازه اعمال می‌شود. (AS-31)
2. **Given** نسخهٔ منتشرشدهٔ مصرف‌شده و انتشار جدید، **When** کاربر حذف نسخهٔ قدیمی را می‌خواهد، **Then** تا وجود ارجاع مصرفی حذف متوقف و نسخهٔ ثابت حفظ می‌شود. (AS-32)

### Edge Cases

- root/owner/admin/editor/normal، دو پروژه، run-only، لغو در نشست باز، grant حذف و عضویت مجدد، REST مستقیم و public/service/debug/node/loop/socket/trigger/queue/tool، stop با task بیگانه، republish و delete/bind هم‌زمان؛ برنامهٔ legacy همان رفتار قبلی داشته باشد.
- تغییر مجوز در نشست باز؛ شناسهٔ معتبر پروژهٔ دیگر؛ تکرار کلیک و رقابت با revision قدیمی؛ پاسخ خطا نباید secret یا محتوای غیرمجاز افشا کند.

## Requirements *(mandatory)*

### Functional Requirements

تمام الزام‌های زیر اجباری‌اند (MUST)؛ جزئیات پیاده‌سازی در plan و contracts قرار دارد.

- **FR-001** (US1): فقط ادمین کل فعال یا مدیر همان پروژه بتواند دسترسی را تغییر دهد؛ manage_access با grant واگذار نشود.
- **FR-002** (US1): view، run، feedback، finalize، edit_definition و publish_definition جدا ثبت شوند؛ نقش کاری یا عنوان مدیر جای grant عملیاتی نباشد.
- **FR-003** (US1): تعریف به برنامه و نسخهٔ منتشرشدهٔ دقیق همان پروژه، نسخهٔ قرارداد و هش آن متصل شود؛ draft و ارجاع خارج پروژه رد شوند.
- **FR-004** (US1): عضویت مجدد، مجوز حذف‌شدهٔ عضویت قبلی را زنده نکند؛ تغییر مجوز دارای عامل، زمان، revision و سابقهٔ قابل پیگیری باشد.
- **FR-005** (US2): run برای عضو عادی مجاز باشد و هیچ حق editor، انتشار، PO یا نهایی‌سازی ضمنی نسازد.
- **FR-006** (US2): تمام مسیرهای اجرای برنامهٔ مدیریت‌شده، توقف، مشاهدهٔ نتیجه، debug، ابزار، trigger و ادامهٔ صف سیاست واحد را اعمال یا صریحاً مسدود کنند.
- **FR-007** (US2): ورودی actor، وضعیت مجوز یا شناسهٔ نسخهٔ انتخاب‌نشده از کاربر معتبر تلقی نشود؛ اجرای مجاز همیشه به نسخهٔ ثابت متصل باشد.
- **FR-008** (US2): برای برنامهٔ قدیمی ثبت‌نشده، رفتار بومی باقی بماند؛ تبدیل به managed اقدامی صریح با preflight مسیرهای عمومی و زمان‌بندی باشد.
- **FR-009** (US3): لغو grant، حذف عضویت یا غیرفعال‌شدن حساب در اقدام بعدی و تحویل نتیجه دوباره کنترل شود؛ سابقه حذف نشود.
- **FR-010** (US3): ثبت تکراری یک اقدام یکسان فقط یک اثر داشته باشد؛ دادهٔ متفاوت با همان کلید و revision قدیمی تعارض آشکار بدهند.
- **FR-011** (US3): نسخهٔ اجرایی ارجاع‌شده با انتشار تازه جابه‌جا و با حذف بومی ناپدید نشود؛ حذف و اتصال هم‌زمان کنترل شوند.
- **FR-012** (US3): رابط فارسی و RTL، loading/empty/error/conflict و استفاده با صفحه‌کلید را پوشش دهد؛ خواندن تعریف اطلاعات اتصال، prompt خصوصی و لاگ دیگران را باز نکند.

### Key Entities *(include if feature involves data)*

- **ManagedAgent**: تعریف یک نقش قابل اجرا در پروژه، متصل به نسخهٔ مشخص برنامه و قرارداد.
- **AgentGrant**: اختیار یک عضو مشخص برای اقدام مشخص روی همان ایجنت.
- **PolicyAction**: تغییر مجوز قابل پیگیری با عامل و نتیجه، مقاوم در برابر تکرار همان اقدام.
- **ExecutionBinding**: رابطهٔ اجرای فرد مجاز با نسخهٔ ثابت ایجنت و ورودی انتخاب‌شده.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: هر شش سناریوی AS-11 تا AS-32 با نتیجهٔ مورد انتظار و شاهد قابل ردیابی پاس شوند؛ مورد بحرانی اجرا نشده یا شکست‌خورده باقی نماند.
- **SC-002**: در ماتریس دو پروژه، حساب نامجاز و حساب دارای مجوز لغوشده، تعداد خواندن یا اثر غیرمجاز صفر باشد؛ تمام مسیرهای مربوط پوشش داشته باشند.
- **SC-003**: در تغییر نسخه، تکرار اقدام و شکست‌های این بسته، صددرصد سوابق لازم و ارتباط عامل/نسخه باقی و اثر منطقی مضاعف صفر باشد.
- **SC-004**: هر سه مسیر انسانی این بسته با دادهٔ ساختگی، متن فارسی، چیدمان RTL و صفحه‌کلید قابل تکمیل باشند؛ وضعیت خالی، انتظار و خطا اقدام بعدی را مشخص کنند.

## Assumptions

- وابستگی: KP-01 پذیرفته‌شده. پذیرش پیش‌نیازها باید با گزارش واقعی احراز شود؛ نوشتن این spec به معنی تحقق آن‌ها نیست.
- خارج از محدوده: طراحی فلو، پروندهٔ تولید، اجرای خودکار و ساخت ایجنت تخصصی کلاسور؛ انتخاب خروجی مرحله در KP-05 است.
- مجوزهای بومی، حساب واقعی، نقش‌های KP-01 و قواعد انسانی قرارداد 1.0.0 باقی‌اند؛ نقش مدیریتی به‌خودی‌خود PO نیست.
- سنجش اولیه با حداقل دو پروژه و چند حساب مستقل آزمایش است؛ SLA تولید و ظرفیت Kubernetes در این گام تعیین نمی‌شوند.
- داده و نمونه‌های آزمون ساختگی‌اند؛ credential، سند مشتری و پاسخ خام اتصال در Git قرار نمی‌گیرند.
