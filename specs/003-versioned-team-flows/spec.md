# Feature Specification: KP-03 — فلوهای تیمی نسخه‌دار

**Feature Branch**: `master` (platform planning; no feature branch created)

**Created**: 2026-10-22

**Status**: Draft — مشخصات و طراحی اولیه؛ پیاده‌سازی و پذیرش اجرا نشده است.

**Input**: User description: «هر تیم بتواند چند فلو ساده با مراحل مشخص تعریف کند، نسخهٔ کامل آن را منتشر کند و پرونده‌های قبلی را روی نسخهٔ منتخب نگه دارد.» مطابق مدل کارکرد و بستهٔ KP-03.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - تعریف چند فلو (Priority: P1)

عضو دارای مجوز بومی ویرایش دو فلو با ترتیب و ایجنت متفاوت می‌سازد.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: دو draft مستقل ذخیره و بازخوانی شوند؛ عضو عادی نتواند آن‌ها را تغییر دهد.

**Acceptance Scenarios**:

1. **Given** عضو editor و دو ایجنت همان پروژه، **When** دو فلو متفاوت می‌سازد، **Then** draft مستقل و قابل اصلاح ذخیره می‌شوند. (AS-11)
2. **Given** شناسهٔ ایجنت پروژهٔ دیگر، **When** ذخیرهٔ binding انجام می‌شود، **Then** ارجاع نامعتبر رد می‌شود. (AS-12)

### User Story 2 - انتشار معتبر (Priority: P1)

عضو مجاز نسخهٔ کامل فلو را منتشر می‌کند و خطای مرحلهٔ ناقص را می‌بیند.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: فلو معتبر منتشر شود؛ cycle و مرحلهٔ بدون finalizer منتشر نشوند.

**Acceptance Scenarios**:

1. **Given** draft کامل با وابستگی رو به جلو، **When** انتشار درخواست می‌شود، **Then** نسخهٔ ثابت با مشخصات همهٔ مراحل ساخته می‌شود. (AS-21)
2. **Given** چرخه یا خروجی تأمین‌نشده یا finalizer بدون اختیار، **When** انتشار درخواست می‌شود، **Then** فهرست خطاهای قابل اصلاح برگردد و publication نسازد. (AS-22)

### User Story 3 - آرشیو و حفظ اجراهای قبلی (Priority: P1)

تیم نسخهٔ دوم را منتشر و نسخهٔ قبلی را برای پروندهٔ فعال حفظ می‌کند.

**Why this priority**: این مسیر بخش لازم هدف بسته است؛ نبود آن مانع پذیرش همین قابلیت است.

**Independent Test**: پروندهٔ نمونه روی v1 بماند؛ ورودی تازه بتواند v2 را انتخاب کند.

**Acceptance Scenarios**:

1. **Given** پروندهٔ متصل به v1 و انتشار v2، **When** نمای پرونده باز می‌شود، **Then** bindingهای v1 همچنان مرجع‌اند. (AS-31)
2. **Given** فلو archived، **When** PO برای درخواست تازه آن را انتخاب می‌کند، **Then** انتخاب تازه رد و تاریخچهٔ قبلی خواندنی می‌ماند. (AS-32)

### Edge Cases

- دو فلو، چند نسخه، cycle و duplicate step، ref بیگانه، finalizer حذف‌شده، publication هم‌زمان، archive و ادامهٔ pin قبلی، ویرایش با run-only، UI validation و legacy studio.
- تغییر مجوز در نشست باز؛ شناسهٔ معتبر پروژهٔ دیگر؛ تکرار کلیک و رقابت با revision قدیمی؛ پاسخ خطا نباید secret یا محتوای غیرمجاز افشا کند.

## Requirements *(mandatory)*

### Functional Requirements

تمام الزام‌های زیر اجباری‌اند (MUST)؛ جزئیات پیاده‌سازی در plan و contracts قرار دارد.

- **FR-001** (US1): ساخت و ویرایش فلو فقط با مجوز بومی معتبر همان پروژه انجام شود؛ run ایجنت حق طراحی فلو ندهد.
- **FR-002** (US1): هر پروژه چند فلو با نام یکتا و مراحل دارای کلید پایدار داشته باشد؛ وابستگی‌های ساده و ورودی هر مرحله مشخص باشند.
- **FR-003** (US1): هر مرحله به نسخهٔ دقیق ایجنت و نسخهٔ منتشرشدهٔ اجرای آن، قرارداد و نهایی‌کنندهٔ فعال متصل باشد.
- **FR-004** (US1): هر تغییر draft با نسخهٔ مورد انتظار کنترل و سابقهٔ عامل نگه داشته شود؛ ذخیرهٔ هم‌زمان تغییر دیگری را بازنویسی نکند.
- **FR-005** (US2): انتشار نیازمند مجوز بومی انتشار و بررسی تازهٔ همهٔ bindingها و مجوزهای لازم باشد.
- **FR-006** (US2): مرحلهٔ تکراری، چرخه، وابستگی گم‌شده، نسخهٔ draft و نهایی‌کنندهٔ نامعتبر مانع انتشار شوند.
- **FR-007** (US2): نسخهٔ منتشرشده شامل همهٔ bindingها و هش محتوا تغییرناپذیر باشد؛ ویرایش نسخهٔ تازه بسازد.
- **FR-008** (US2): خطای اعتبارسنجی به مرحله و فیلد مشخص وصل باشد؛ ذخیرهٔ draft ناقص با اخطار مجاز ولی publication ناقص ممنوع باشد.
- **FR-009** (US3): نسخهٔ تازه هیچ instance یا تصمیم قبلی را خودکار تغییر ندهد.
- **FR-010** (US3): آرشیو انتخاب جدید را ببندد ولی خواندن مجاز تاریخچه و ادامهٔ نسخهٔ pin‌شده را حذف نکند.
- **FR-011** (US3): حذف یا تغییر app/workflow/agent مصرف‌شده با guard و قفل جلوگیری شود؛ references از scope خارج نشوند.
- **FR-012** (US3): رابط فارسی/RTL مراحل، مسئول‌ها، نسخه و خطاهای empty/loading/conflict را قابل استفاده با صفحه‌کلید نشان دهد.

### Key Entities *(include if feature involves data)*

- **TeamFlow**: تعریف همکاری یک تیم با نام و مراحل قابل اصلاح پیش از انتشار.
- **FlowVersion**: نسخهٔ ثابت منتشرشده از فلو که پرونده‌ها به همان متصل می‌شوند.
- **StageBinding**: تعیین ایجنت، ورودی، پیش‌نیاز و نهایی‌کنندهٔ هر مرحله در یک نسخهٔ فلو.
- **FlowReference**: رابطهٔ پرونده و تصمیم با نسخهٔ فلو و برنامه‌های لازم برای حفظ سابقه.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: هر شش سناریوی AS-11 تا AS-32 با نتیجهٔ مورد انتظار و شاهد قابل ردیابی پاس شوند؛ مورد بحرانی اجرا نشده یا شکست‌خورده باقی نماند.
- **SC-002**: در ماتریس دو پروژه، حساب نامجاز و حساب دارای مجوز لغوشده، تعداد خواندن یا اثر غیرمجاز صفر باشد؛ تمام مسیرهای مربوط پوشش داشته باشند.
- **SC-003**: در تغییر نسخه، تکرار اقدام و شکست‌های این بسته، صددرصد سوابق لازم و ارتباط عامل/نسخه باقی و اثر منطقی مضاعف صفر باشد.
- **SC-004**: هر سه مسیر انسانی این بسته با دادهٔ ساختگی، متن فارسی، چیدمان RTL و صفحه‌کلید قابل تکمیل باشند؛ وضعیت خالی، انتظار و خطا اقدام بعدی را مشخص کنند.

## Assumptions

- وابستگی: KP-02 پس از پذیرش. پذیرش پیش‌نیازها باید با گزارش واقعی احراز شود؛ نوشتن این spec به معنی تحقق آن‌ها نیست.
- خارج از محدوده: ویرایشگر عمومی گراف دوم، اجرای موازی پیچیده، حلقهٔ خودکار و مهاجرت خودکار پرونده‌های فعال.
- مجوزهای بومی، حساب واقعی، نقش‌های KP-01 و قواعد انسانی قرارداد 1.0.0 باقی‌اند؛ نقش مدیریتی به‌خودی‌خود PO نیست.
- سنجش اولیه با حداقل دو پروژه و چند حساب مستقل آزمایش است؛ SLA تولید و ظرفیت Kubernetes در این گام تعیین نمی‌شوند.
- داده و نمونه‌های آزمون ساختگی‌اند؛ credential، سند مشتری و پاسخ خام اتصال در Git قرار نمی‌گیرند.
