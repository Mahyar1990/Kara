# اعتبارسنجی تخصصی خروجی پیش از تصمیم انسانی

Kara می‌تواند Code validator صریح همان Workflow ثابت را پس از ویرایش انسانی، هنگام درخواست تصمیم و دوباره پیش از نهایی‌سازی اجرا کند. این قابلیت عمومی هیچ schema یا قاعدهٔ تخصصی محصولی را وارد بستر نمی‌کند. موفقیت اعتبارسنج جای تصمیم انسانی نیست و مرحلهٔ بعد همچنان فقط پس از finalize مسئول تعیین‌شده آماده می‌شود.

سازنده در `data` یک Code node پایتون، قرارداد زیر را قرار می‌دهد. همهٔ خروجی‌های تنها End باید مستقیماً به خروجی‌های همین node وصل باشند:

```json
{"kara_output_validator":{"version":1,"candidate_arguments":{"text":"answer"}}}
```

در این مثال مقدار پیشنهادی Artifact با کلید `answer` جای آرگومان `text` می‌نشیند. تمام آرگومان‌های دیگر، از جمله زمینه و metadata پایان مدل، فقط از ورودی ثبت‌شدهٔ همان Code node در اجرای موفق اصلی می‌آیند. کلاینت نمی‌تواند code، زمینه، `finish_reason` یا نتیجهٔ اعتبارسنج را ارسال کند. علت پایان گم‌شده هرگز stop فرض نمی‌شود. قواعد اختصاصی داخل کد نسخه‌دار خود ایجنت می‌مانند.

Workflow/agent/digest ثابت، اجرای بومی موفق با هویت درست، پیوند تلاش با همان مرحله و دور و input_digest و اجرای یکتای موفق validator بررسی می‌شوند. زمینهٔ گم‌شده، اجرای مبهم/تکراری، نسخهٔ نامعتبر یا خرابی sandbox جلوی تصمیم و تحویل را می‌گیرد. قرارداد فعلی مخصوص یک validator پایتون و یک End است؛ حلقه و اجرای تکراری همان validator پشتیبانی نمی‌شوند.

فقط همان Code در sandbox بومی با محدودیت‌ها و پیکربندی موجود اجرا می‌شود؛ LLM یا کل Workflow دوباره اجرا نمی‌شود. کد باید اعتبارسنج خالص و قابل تکرار باشد و به مدل، شبکه یا اثر بیرونی وابسته نباشد؛ این hook اجرای بی‌شبکه را در سطح sandbox تضمین نمی‌کند. نتیجهٔ آن هنگام edit_output به‌صورت Artifact انسانی تازه و نرمال‌شده ثبت می‌شود. request_decision و finalize نتیجهٔ نرمال‌شده را با Artifact منتخب مقایسه می‌کنند. تغییر محتوا یا خطا، تصمیم جدید یا تحویل نمی‌سازد. خطای عمومی HTTP هیچ source/context خصوصی sandbox را افشا نمی‌کند.

پاسخ موفق اقدام، `output_validation` شامل شناسهٔ validator، Workflow و digest آن، digest کد، تلاش، Artifact، input_digest و digest محتوای پیشنهادی/معتبر دارد. این مدرک در journal immutable همان اقدام ذخیره می‌شود؛ GET مرحله تضمین گزارش آخرین مدرک نیست. تکرار همان کلید اقدام پاسخ ذخیره‌شده را برمی‌گرداند؛ نهایی‌سازی تازه اعتبارسنج را دوباره اجرا می‌کند.

Workflowهای بدون اعلان صریح، قرارداد عمومی قبلی را دارند و پذیرش تخصصی برای آن‌ها ادعا نمی‌شود. فعال‌سازی برای PA-04/TL نیازمند نسخهٔ جدید دارایی‌ها روی `clasor-agents` و انتشار مستقل است؛ نسخه‌ها و FlowVersionهای موجود بازنویسی نمی‌شوند. ادغام شاخهٔ کلاسور برای استفاده از این قابلیت لازم نیست.

بررسی ۲۳ اکتبر ۲۰۲۶: پنج سناریوی تخصصی و یک چرخهٔ عمومی مرحله روی PostgreSQL آزمایشی بررسی شدند. رکوردهای اجرای اصلی fixture ساختگی‌اند؛ Code validator در sandbox واقعی اجرا شد. پذیرش/رد و نرمال‌سازی ویرایش، حفظ زمینه، زمینهٔ ناقص/تکراری، قرارداد نامعتبر، توقف هنگام خرابی sandbox و تحویل منتخب موفق بودند. در آزمون اول، دو سناریو به علت رد اجرای پایتون با گزینهٔ شبکهٔ خاموش شکست خوردند؛ اتصال با پیکربندی بومی موجود سازگار شد و فقط سناریوهای متأثر دوباره اجرا و موفق شدند. هیچ قاعدهٔ پذیرش ضعیف نشد.

۵۶ آزمون `make check` موفق‌اند. تصویر API ساخته و در چهار سرویس backend محلی فعال شد؛ Compose و `make doctor` موفق بودند. شمار و hash محتوای ۲۳ جدول تیمی/Workflow/WorkflowRun پیش و پس از راه‌اندازی برابر بود. هیچ مدل یا پذیرش واقعی PO → TL اجرا نشد و دارایی‌ها/نسخه‌های فعلی کلاسور تغییر نکردند. رابط کلاینت تغییر نکرد؛ smoke رابط لازم نبود.
