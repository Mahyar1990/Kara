# اجرای محلی کارا با Runner نسخهٔ ۲

در این معماری، اجرای برنامه، مراحل ایجنت و فلو، درخواست مدل و اجرای گرهٔ کد روی دستگاه کاربر انجام می‌شود. کارا تعریف‌ها، مجوزها، تصمیم‌های انسانی، صف، وضعیت، تاریخچهٔ گره‌ها و نتیجه را نگه می‌دارد. **نبود Runner، قطع شبکه یا پشتیبانی‌نشدن یک قابلیت، اجرای سروری را فعال نمی‌کند.**

تعریف منتشرشدهٔ برنامه و ارتباط ایجنت/فلو بازنویسی نمی‌شود. هر اجرا snapshot، اثرانگشت نسخه، کاربر، عضویت، دستگاه مقصد و اتصال مدل شخصی مشخص دارد. خروجی دستگاه یک شاهد اجرای ثبت‌شده است؛ جای تصمیم یا تأیید واقعی PO/TL/QC را نمی‌گیرد.

## راه‌اندازی دستگاه

بستهٔ تازه را از «تنظیمات و اتصال‌ها ← Runnerهای شخصی» دریافت و در پوشهٔ خصوصی باز کنید. Python 3.10+ و Git لازم است؛ Windows از WSL استفاده می‌کند. در پوشهٔ بسته:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m kara_source_runner pair --server https://YOUR-KARA-HOST
```

در محیط محلی این پروژه آدرس کارا `http://localhost:8080` است. کد یک‌بارمصرف را در پرسش مخفی ترمینال وارد کنید. دستگاهی که قبلاً متصل شده، پس از جایگزینی بسته از همان فایل خصوصی تنظیمات استفاده می‌کند و به اتصال دوباره نیاز ندارد.

برای سیستم دارای Docker:

```sh
docker build -f Dockerfile.code -t kara/code-python:2.0 .
docker pull node:22-alpine
python -m kara_source_runner service install
```

فرمان service مخصوص Linux با systemd کاربری است؛ پس از نصب، ترمینال می‌تواند بسته شود. در macOS یا محیط فاقد systemd، به‌جای آن `python -m kara_source_runner run` را اجرا و ترمینال را باز نگه دارید. Windows به WSL دارای systemd نیاز دارد؛ در WSL بدون آن، اجرای دستی ممکن است. برای کاربرد مدل/سورس بدون گره کد، آماده‌سازی تصویرهای کد الزامی نیست؛ نبود Docker به‌تنهایی اجرای process را مجاز نمی‌کند.

Runner هیچ تصویری را حین کار خودکار pull نمی‌کند. کد در کانتینر بدون شبکه، بدون capability، با فایل‌سیستم پایهٔ خواندنی، کاربر غیرریشه و محدودیت حافظه، زمان و تعداد فرایند اجرا می‌شود. تصویر پایتون همراه بسته Jinja2 نیز دارد؛ کدهای فعلی محصول فقط به کتابخانهٔ استاندارد پایتون نیاز دارند.

### سرویس پس‌زمینهٔ Linux برای هر همکار

بستهٔ Runner نسخهٔ ۲٫۱٫۲ شامل فرمان `service` و فایل `BACKGROUND.md` است. ابتدا با حساب شخصی خود pair کنید و اجرای دستی قبلی را متوقف کنید؛ بسته و venv باید در پوشه‌ای دائمی و خصوصی بمانند. unit کاربری در `~/.config/systemd/user/kara-source-runner.service` یا مسیر XDG_CONFIG_HOME ساخته، enabled و شروع می‌شود. نصب و مدیریت آن بدون sudo است؛ نصب‌کننده Docker نصب نمی‌کند، گروه یا lingering را تغییر نمی‌دهد و به pairing، توکن یا سورس‌ها دست نمی‌زند.

برای CA سازمانی و عضویت موجود در گروه Docker، به‌جای فرمان پایهٔ نصب از این نمونه با مسیر واقعی همان دستگاه استفاده کنید:

```sh
python -m kara_source_runner service install --ca-bundle /PATH/TO/trusted-ca.pem --docker-group docker
```

گواهی به SSL_CERT_FILE، REQUESTS_CA_BUNDLE و GIT_SSL_CAINFO معرفی و اعتبار ساختاری آن بررسی می‌شود؛ TLS روشن می‌ماند. گروه انتخابی باید از قبل متعلق به حساب باشد؛ sg آن را برای سرویس فعال می‌کند و UID همان کاربر می‌ماند. عضویت گروه Docker دسترسی مدیریتی daemon می‌دهد و باید با مسئول سیستم هماهنگ شود. در نبود گزینهٔ CA، همین متغیرهای موجود محیط نصب بررسی و ذخیره می‌شوند. PATH و انتخاب صریح Docker نیز حفظ می‌شوند؛ سایر متغیرهای shell کپی نمی‌شوند و فایل‌های startup shell اجرا نمی‌شوند.

برای ساخت تصویر Python در شبکهٔ محدود، base image و index معتبر خودتان را تعیین کنید؛ مسیر CA فقط build secret است و محتوایش در تصویر کپی نمی‌شود:

```sh
docker build -f Dockerfile.code -t kara/code-python:2.0 --build-arg PYTHON_BASE_IMAGE=python:3.12-bookworm --build-arg PIP_INDEX_URL=https://YOUR-MIRROR/simple/ --secret id=kara_ca,src=/PATH/TO/trusted-ca.pem .
```

اطلاعات ورود را در URL index قرار ندهید. نصب سرویس تصویر کد را pull نمی‌کند و active بودن سرویس به معنی آماده‌بودن همهٔ تصویرها یا اتصال موفق به کارا نیست. وضعیت online را در کارا و یک آزمون کوچک مناسب را پس از نصب بررسی کنید.

فرمان‌های مدیریت مستقل‌اند؛ توقف/راه‌اندازی مجدد کار جاری را قطع می‌کند:

```sh
python -m kara_source_runner service status
python -m kara_source_runner service logs
python -m kara_source_runner service stop
python -m kara_source_runner service start
python -m kara_source_runner service restart
python -m kara_source_runner service uninstall
```

uninstall فقط unit مدیریت‌شده را حذف می‌کند؛ فایل اتصال، worktree، بسته و backupها می‌مانند. نصب دوبارهٔ عین تنظیمات، unit را بازنویسی نمی‌کند. سرویس متفاوت یا دستی با خطا حفظ می‌شود؛ برای جایگزینی آگاهانه، همهٔ گزینه‌های اختصاصی را دوباره همراه `service install --replace` مشخص کنید. نسخهٔ قبلی unit با مجوز خصوصی backup و سرویس restart می‌شود. گزینه‌های run مانند `--root`، backend، تصویرها، اجازهٔ نوشتن و هارنس برای service install نیز وجود دارند؛ اجازهٔ process یا هارنس خودکار فعال نمی‌شود. برای config اختصاصی، `--config /PATH/device.json` را پیش از service بیاورید؛ هر حساب سیستم فقط یک نام سرویس مدیریت‌شده دارد.

برای ارتقا، ابتدا سرویس را متوقف، فایل‌های بسته را در همان محل جایگزین و سپس سرویس را شروع کنید؛ تنظیمات خصوصی و ریشهٔ سورس حفظ شوند. نسخه‌های جدید از اجرای هم‌زمان دو Runner برای یک config جلوگیری می‌کنند؛ نسخه‌های قدیمی این قفل را ندارند و باید دستی متوقف شوند.

بستن ترمینال سرویس را متوقف نمی‌کند. ادامه پس از logout/boot به user manager، دسترسی به home/venv، Docker و شبکه وابسته است؛ `loginctl show-user "$(id -u)" --property=Linger` را بررسی و در صورت نیاز از مسئول سیستم دربارهٔ lingering کمک بگیرید. نصب‌کننده خروج از حساب یا reboot انجام نمی‌دهد. restart سرویس باعث تکرار خودکار کار قطع‌شده نمی‌شود. هر همکار دستگاه و اتصال شخصی خودش را دارد؛ برای سرور کارا روی دستگاه دیگر، HTTPS معتبر لازم است و loopback سرور نباید روی VDI همکار کپی شود.

برای سیستم شرکت یا VDI بدون Docker:

```sh
python -m kara_source_runner run --code-backend process --allow-local-code
```

این گزینه فقط برای برنامه‌های مورد اعتماد است: **حالت process، sandbox سیستم‌عامل نیست و کد دسترسی فایل و شبکهٔ حساب کاربر را دارد.** فرایند جدا، محیط تمیز و محدودیت زمان/منابع، جای جداسازی Docker را نمی‌گیرند. این حالت بدون گزینهٔ صریح فعال نمی‌شود. JavaScript به Node نصب‌شده نیز نیاز دارد. دستگاهی که محیط مجاز کد ندارد، کار نیازمند کد را دریافت نمی‌کند.

در صفحهٔ Runner، برای هر پروژه دستگاه مقصد را ذخیره کنید. همان حساب می‌تواند چند دستگاه داشته باشد و هر پروژه انتخاب مستقل دارد. تغییر دستگاه برای کارهای تازه است؛ کار قبلی به‌صورت پنهانی جابه‌جا یا تکرار نمی‌شود.

## اتصال worktree

اگر برنامه به فایل‌های پروژه نیاز دارد، ابتدا با Runner نسخهٔ ۲ سورس را روی همان دستگاه آماده کنید و نتیجهٔ موفق آن را در «دستگاه اجرای این پروژه» انتخاب کنید. آماده‌سازی قدیمیِ فاقد نشان مالک باید دوباره انجام شود. اتصال سورس، دستورالعمل یا prompt برنامه را تغییر نمی‌دهد و فایل‌های مخزن و Markdown را خودکار اجرا نمی‌کند.

ریشهٔ پیش‌فرض `~/KaraSourceWorkspaces` است و با `--root` تغییر می‌کند. هر آماده‌سازی پوشهٔ مستقل دارد. در Docker، worktree انتخاب‌شده پیش‌فرض خواندنی است؛ نوشتن به گزینهٔ `--allow-worktree-write` روی دستگاه نیاز دارد. در حالت process این گزینه فقط پوشهٔ کاری را تعیین می‌کند و محدودیت فایل در سطح سیستم‌عامل ایجاد نمی‌کند.

حساب‌ها و سرورهای متفاوت، outbox و کش جدا بر اساس هویت دستگاه/سرور دارند. manifest سورس نیز به همین هویت متصل است تا نتایج یا فایل‌های حساب دیگری تصادفی استفاده نشوند.

## مرز اجرا و پشتیبانی

- اجرای دستی workflow، اجرای ایجنت و مراحل فلو، پیش‌نمایش گرهٔ ذخیره‌شده و اتوماسیون زمان‌بندی‌شده به صف دستگاه واگذار می‌شوند.
- ارتباط مدل‌های شخصی شامل LLM، embedding، rerank، آزمون اتصال و شمارش توکن از Runner انجام می‌شود. پاسخ‌های موجود با قالب مصرف‌کنندهٔ کارا سازگار می‌شوند؛ هیچ توکن مشترک پروژه جای اتصال شخصی را نمی‌گیرد.
- خواندن جیرا و آزمون GitLab نیز از دستگاه مقصد انجام می‌شوند. دستگاه باید به شبکه و گواهی سرویس‌های سازمان دسترسی داشته باشد.
- موتور محلی، گره‌های فعلی `start`، `end`، `code`، `llm`، `if-else`، `variable-aggregator` و `knowledge-retrieval` را اجرا می‌کند؛ پروتکل همچنین answer، template-transform، HTTP request و شروع زمان‌بندی/webhook را تعریف می‌کند.
- آداپتور مدل فعلی برای سرویس‌های سازگار با OpenAI Chat Completions است؛ همهٔ اتصال‌های موجود هنگام بررسی از همین نوع بودند. افزودن ارائه‌دهندهٔ متفاوت به آداپتور محلی نیاز دارد.
- این پروتکل جایگزین عمومی تمام قابلیت‌های upstream نیست. حالت‌های chat/Agent v2، گره‌های خارج از قرارداد، loop/iteration، ورودی فایل و vision، دانش خارجی و فیلتر خودکار metadata در این نسخه **مسدودند**؛ هیچ fallback سروری ندارند. استفاده از آن‌ها نیازمند توسعهٔ قرارداد و آداپتور محلی است. همهٔ ۵۱ گراف ذخیره‌شدهٔ فعلی از بررسی ساختاری قرارداد عبور کردند؛ این بررسی، آزمون اجرای واقعی آن‌ها نیست.

## وضعیت، نتیجه و بازیابی

Runner قابلیت‌های خود را اعلام می‌کند و فقط کار همان حساب و دستگاه را می‌گیرد. قبل از تحویل اعتبارنامه و در heartbeat، عضویت، دسترسی برنامه/ایجنت، نسخهٔ workflow و اتصال شخصی دوباره بررسی می‌شوند. حذف و ایجاد دوبارهٔ عضویت، ادامهٔ اجرای قبلی را مجاز نمی‌کند.

وضعیت گره و خروجی آن، نتیجهٔ نهایی، تعداد مراحل و توکن‌های گزارش‌شده در کارا ثبت می‌شوند. تاریخچهٔ workflow و ایجنت با نتیجهٔ محلی تکمیل می‌شود. پیام خام خطای provider یا توکن در رویدادها و لاگ نتیجه نوشته نمی‌شود.

هنگام اجرای کار، heartbeat هر ۱۰ ثانیه و lease برابر ۹۰ ثانیه است. لغو کار/دستگاه یا قطع ارتباط، worker محلی را متوقف می‌کند؛ timeout مدل و کد نیز محدود است. کار قطع‌شده خودکار دوباره اجرا نمی‌شود. retry ارسال یک رویداد یا نتیجه با همان شناسه، مدل یا کد را تکرار نمی‌کند. outbox خصوصی نتیجهٔ ارسال‌نشده را نگه می‌دارد؛ نتیجهٔ دیررس پس از لغو یا اتمام lease رد می‌شود. نتیجهٔ ردشده برای بررسی محلی حفظ می‌شود.

دانشِ مجازِ برنامه با شناسه و hash قطعه‌ها ثابت می‌شود؛ تغییر یا لغو دسترسی هنگام انتقال باعث رد نسخهٔ ناسازگار می‌شود. بازیابی و رتبه‌بندی روی دستگاه است. embedding در پوشهٔ خصوصی دستگاه با کلید مدل/نسخه/متن کش می‌شود تا indexing و جست‌وجوی بعدی درخواست تکراری نسازند. آزمون اعتبارنامه از کش عبور می‌کند تا واقعاً اتصال را بررسی کند.

## منابع و بررسی

قرارداد HTTP: [Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)، [Embeddings](https://developers.openai.com/api/reference/resources/embeddings/methods/create).

طبق درخواست کاربر، تست کلاینت، مرورگر، اجرای واقعی مدل و اجرای گرهٔ کد در این تحویل انجام نمی‌شود. بررسی syntax، سازگاری ساختاری گراف‌ها، آزمون‌های محدود سرور، ساخت و سلامت runtime و مقایسهٔ hash دارایی‌های قبلی انجام می‌شوند. مصرف رم و رفتار اجرای واقعی دستگاه تا آزمون کاربر تأییدشده نیست.

## شناخت دستگاه‌ها در صفحهٔ Runnerهای شخصی

صفحهٔ Runnerها نمای کل حساب را نشان می‌دهد: نام و شناسهٔ کوتاه دستگاه، آخرین تماس، قابلیت‌های اعلام‌شده، پروژه‌هایی که آن را برای اجرای برنامه و مدل انتخاب کرده‌اند، سورس متصل به هر اجرا و کارهای جاری. آماده‌سازی مخزن و اجرای برنامه دو انتخاب جدا هستند؛ انتخاب Runner برای آماده‌سازی سورس، مقصد اجرای برنامهٔ پروژه را تغییر نمی‌دهد.

«ارتباط تازه» یعنی دستگاه در ۹۰ ثانیهٔ اخیر با کارا تماس داشته است و تضمین موفقیت اجرا نیست. محیط کد یا دسترسی شبکه می‌تواند همچنان به تنظیم نیاز داشته باشد. قابلیت‌ها به‌صورت گزارش‌شده نمایش داده می‌شوند؛ نوع Docker/process از دادهٔ فعلی دستگاه قابل تشخیص نیست و صفحه آن را حدس نمی‌زند.

برای تغییر مقصد، پروژه، دستگاه و آماده‌سازی موفق سورس را بررسی و «ذخیرهٔ مقصد اجرا» را بزنید. پیش از ذخیره، انتخاب‌ها فقط پیش‌نویس هستند. ورود به پروژه‌ای دیگر برای تنظیم مقصد یا پیگیری، با اقدام صریح کاربر انجام می‌شود. نمای وضعیت فقط اطلاعات حساب خود کاربر در پروژه‌های در دسترس را می‌خواند؛ متن برنامه، درخواست مدل، کد، توکن و خروجی خام در API این نما قرار نمی‌گیرد.

فهرست کارها، آماده‌سازی سورس، اجرای برنامه و فراخوانی مدل/اتصال را جدا نام‌گذاری می‌کند و قابل فیلتر بر اساس پروژه و دستگاه است. راهنمای نصب، اتصال یک‌بارمصرف و محیط کد در بخش جداگانه قرار دارند؛ هر دستگاه تازه یک کد مستقل می‌خواهد. لغو دسترسی، پروژه‌های متأثر را قبل از اقدام نشان می‌دهد و فایل‌های محلی را حذف نمی‌کند.

## انتخاب دستگاه به تفکیک گام

اجرای دستی جدید، مدل هر LLM و Runner هر گام اجرایی را جدا دریافت می‌کند؛ مقصد پروژه جای این انتخاب صریح را نمی‌گیرد. Runner اولین گام اجرایی هماهنگی گراف را انجام می‌دهد. برای گام راه‌دور یک درخواست فرزند ثابت در صف RPC ساخته می‌شود؛ شناسه از اجرای اصلی و گام مشتق می‌شود و تکرار ارسال، اجرای دوباره ایجاد نمی‌کند. دستگاه مقصد فقط اعتبار مدل‌های همان گام و دانش وابسته‌اش را دریافت می‌کند. تغییر دسترسی، لغو یا پایان lease اجرای اصلی، دسترسی درخواست فرزند را هم می‌بندد. انتظار برای گام راه‌دور حداکثر ده دقیقه است و پس از خطا جایگزینی خودکار انجام نمی‌شود.

قابلیت `node-routing-v1` از بستهٔ تازهٔ Runner اعلام می‌شود. دستگاه‌های قدیمی برای snapshotهای قدیمی قابل استفاده‌اند؛ گام‌های اجرای جدید به Runner به‌روز نیاز دارند. سورس آمادهٔ هر دستگاه در انتخاب‌های همان اجرا مشخص است و گام‌های یک دستگاه از سورس مشترک استفاده می‌کنند. جزئیات در [مدل و Runner هر گام](program-runtime-model.md) آمده است.

اجرای هماهنگ‌کننده‌ها برای هر حساب به‌صورت اتمیک پذیرش می‌شود. تا وقتی یک برنامه فعال است، برنامهٔ دیگری که به یکی از دستگاه‌های همان برنامه نیاز دارد در صف می‌ماند؛ درخواست فرزند همان برنامه روی دستگاه مقصد قابل دریافت است. این رزرو از انتظار دوری دو برنامه برای Runnerهای یکدیگر جلوگیری می‌کند.
