# قرارداد اجرایی PA-04 — نسخهٔ 1.0.0

۲۳ اکتبر ۲۰۲۶ — گام ۱ [برنامهٔ کلاسور](clasor-agents-implementation-plan.md)، پس از [خط مبنای پایلوت](clasor-pilot-baseline.md). دارایی‌ها فقط روی `clasor-agents` هستند؛ این بسته Workflow، prompt تحلیلگر یا مجوز اجرای آن نیست.

**به‌روزرسانی گام ۲:** [بستهٔ مستقل Workflow و شواهد واقعی](clasor-pa04-workflow.md) اضافه شد. توضیح‌های «آینده» و «اجرا نشده» در این سند، وضعیت پایان گام ۱ و خود بستهٔ قرارداد را توصیف می‌کنند؛ وضعیت جاری مدل و تنظیمات فعال در سند Workflow است. schema سیمی 1.0.0 تغییر نکرد؛ اعتبارسنج محتوایی برای استفادهٔ همان قواعد داخل sandbox جدا شد.

## دارایی و اجرای کوتاه

- [schema ورودی](../clasor_agents/pa04/schemas/input.schema.json) و [schema خروجی](../clasor_agents/pa04/schemas/output.schema.json)، با JSON Schema draft 2020-12.
- [اعتبارسنج و سازگارکنندهٔ ورودی](../clasor_agents/pa04/contract.py)، فقط کتابخانهٔ استاندارد Python؛ بدون شبکه، مدل یا تغییر runtime.
- [چهار نمونهٔ ساختگی](../clasor_agents/pa04/fixtures/cases.json) شامل ورودی، binding مورد انتظار، پاسخ مرجعِ نوشته‌شده برای آزمون و rubric معنایی. پاسخ‌های مرجع خروجی مدل نیستند.
- [manifest](../clasor_agents/pa04/manifest.json): نسخه، hash فایل‌ها، حدود و وضعیت `offline-contract-only`؛ prompt/workflow revision فعلاً null و live_model_test=false هستند.

```sh
.venv/bin/python scripts/check_clasor_contract.py --bundle .runtime/pa04-contract-v1.json
.venv/bin/python -m unittest scripts.test_clasor_pa04_contract
```

bundle یک بستهٔ JSON قابل خواندن در Python/ابزار ساخت بعدی است؛ **DSL قابل import در استودیوی Kara نیست**. بازسازی manifest پس از تغییر آگاهانهٔ قرارداد:

```sh
.venv/bin/python -m clasor_agents.pa04.package > clasor_agents/pa04/manifest.json
```

بسته از فایل‌های نسخه‌دار بازسازی می‌شود و drift فایل‌ها را رد می‌کند. بازسازی hash به‌تنهایی تأیید تغییر قرارداد نیست؛ diff و بررسی مرتبط همچنان لازم‌اند. برای تغییر ناسازگار نسخهٔ تازه بسازید.

## ورودی و مرز اعتماد

Envelope شامل contract_version/role_id، binding، mode، request، sources، feedback_context و previous_analysis است. تمام فیلدها صریح‌اند و فیلد اضافی پذیرفته نیست.

`binding` از caller معتبر می‌آید: project_id، request_id، request_revision_id، stage_id، base_revision، request_sha256، source_bundle_sha256، previous_artifact_id و previous_analysis_sha256. شناسه‌ها UUID استاندارد lowercase و بازبینی عدد صحیح مثبت‌اند. `validate_input(envelope, expected_binding)` همهٔ این داده‌ها را با binding مورد انتظار تطبیق می‌دهد. hash متن درخواست، محتوا و مشخصات منابع نیز کنترل می‌شوند؛ تغییر متن و محاسبهٔ دوبارهٔ hash نمی‌تواند زیر binding قبلی پنهان بماند. شناسهٔ خروجی قبلی باید از Artifact واقعی انتخاب شود؛ previous_analysis_sha256 فقط hash متن تحلیل است و با digest داخلی Artifact یکی نیست. نبود متن و شناسهٔ خروجی قبلی باید هم‌زمان باشد. بستهٔ منابع بر اساس id مرتب و hash متادیتای id/kind/reference/revision/sha256 محاسبه می‌شود.

این کنترل، authentication یا ACL سرور نیست. caller باید نسخه/عضویت/اختیار واقعی را از Kara بگیرد؛ گرفتن expected_binding از خود پاسخ مدل یا همان دادهٔ نامعتبر، مرز اعتماد را از بین می‌برد. در این گام caller و نسخه‌ها fixture‌اند؛ اتصال معتبر به API واقعی در ساخت Workflow/adapter بعدی لازم است.

هر منبع یا `repository_rule` است یا `evidence`؛ متن منبع اجازهٔ تغییر نقش، اجرای ابزار یا نهایی‌سازی نمی‌سازد. نمونه‌ها فقط منبع ساختگی دارند؛ بستهٔ خصوصی sandbox به Git یا fixture منتقل نشده است. نقل‌قول خروجی باید عیناً در منبع ارجاع‌شده موجود باشد؛ شناسهٔ منبع ناموجود رد می‌شود.

سه حالت: `analyze`، `clarify` و `review_change`. دو حالت آخر بازخورد غیرخالی لازم دارند؛ review_change علاوه بر آن، تحلیل پیشین با hash انتخاب‌شده در binding می‌خواهد. تغییر درخواست باید با revision/hash معتبر جدید بیاید؛ تغییر درخواست از مسیر بازخورد، جای تصمیم ورود تازهٔ PO نیست.

## اتصال به Start و بازخورد Kara

`build_inputs` چهار مقدار متنی/انتخابی request، mode، source_context و feedback_context می‌سازد. متن request بدون خلاصه، بازنویسی یا normalization جابه‌جا می‌شود. source_context فقط JSON منابع منتخب و تحلیل پیشین است؛ metadata اعتماد بستر به مدل سپرده نمی‌شود.

در فلو آینده، request از متن نسخهٔ درخواست، context از بستهٔ منتخب و feedback_context ابتدا از ثابت خالی نگاشت شود. متغیر دریافت‌کنندهٔ بازخورد بومی **feedback_context** انتخاب شود. بستر فعلی سابقه و خروجی مبنا را همراه یک پیشوند متنی به متغیر منتخب اضافه می‌کند؛ این رشته JSON خالص نیست و در این بسته به‌عنوان داده حفظ می‌شود. متن اصلی request برای ورود بازخورد استفاده نشود. بررسی این نگاشت در API/رابط واقعی به گام Workflow تعلق دارد؛ در این گام رفتار رشتهٔ الحاق‌شده آفلاین بررسی شد.

## خروجی و پذیرش تلاش

خروجی End آینده یک کلید `analysis` با مقدار **متن JSON** دارد؛ فیلد object بومی Start لازم نیست. JSON تحلیل شامل نسخه/نقش، hash درخواست، status، summary، scope، conditions، requirements، acceptance_criteria، questions و assumptions است.

هر شرط دارای نقل‌قول/منبع است؛ نیازمندی به شرط و AC به نیازمندی وصل می‌شود. نیازمندی بدون AC، شرط بدون نگاشت، شناسهٔ تکراری، ارجاع گم‌شده و hash نسخهٔ دیگر رد می‌شوند. شرط حل‌نشده در پاسخ غیرآماده می‌تواند به سؤال مسدودکننده وصل باشد. `ready_for_review` سؤال مسدودکننده ندارد و نیازمندی/AC لازم دارد؛ needs_clarification و blocked سؤال مسدودکننده لازم دارند. فرض‌ها همواره `needs_confirmation=true` دارند.

فیلد approved، finalizer_id یا grants در قرارداد خروجی وجود ندارد؛ مدل نمی‌تواند تأیید PO، پذیرش یا مرج TL تولید کند. متن داخل summary/نیازمندی هم اختیار اجرا ندارد؛ کنترل schema به‌تنهایی معنای تمام جملات را بررسی نمی‌کند.

`validate_attempt` وضعیت فنی، finish_reason و outputs را از adapter معتبر می‌گیرد. فقط succeeded + stop + یک خروجی analysis پذیرفته می‌شود؛ timeout/failed/cancelled، علت length/content_filter یا نبود علت پایان رد می‌شوند. adapter نباید در نبود metadata واقعی، stop را حدس بزند. JSON بریده/ناقص، کلید تکراری، NaN/Infinity و عدد overflow رد می‌شوند. ویرایش انسانی JSON نیز پیش از مصرف در نقش بعدی باید دوباره اعتبارسنجی شود. موفقیت این تابع فقط پذیرش فنی قرارداد است، نه نهایی‌سازی مرحله.

## حدود و ارزیابی

حدود قطعی محلی: هر payload حداکثر ۳۲۷۶۸ بایت UTF-8، درخواست حداکثر ۴۰۰۰ نویسه، حداکثر چهار منبع با سقف ۲۰۰۰ نویسه برای هر منبع و ۶۰۰۰ نویسه در مجموع، بازخورد ۸۰۰۰ و تحلیل قبلی ۱۶۰۰۰ نویسه. سرریز رد می‌شود؛ برش خاموش یا retry خودکار وجود ندارد. رشد سابقهٔ بومی نیز در adapter آینده باید به همین حدود کنترل شود.

manifest برای مرحلهٔ مدل **پیشنهاد** زمینهٔ ۱۶۳۸۴ و خروجی ۲۰۴۸ توکن با صفر retry خودکار ثبت می‌کند. این تنظیمات در Kara اعمال یا اندازه‌گیری نشده‌اند؛ تنظیم فعلی smoke همان ۴۰۹۶/۵۱۲ است. سقف بایت/نویسه تخمین توکن نیست و پیش از پذیرش تحلیلگر باید بودجهٔ واقعی، سربار و خروجی نمونه اندازه‌گیری شوند. متن کامل مخازن در هر فراخوانی ارسال نشود.

چهار rubric معنایی: حفظ رفتار روشن، سؤال به‌جای حدس در ابهام، حفظ شرط منفی/صفر/انتظار/پیام خطا، و نپذیرفتن دستور جعلی منبع. اعتبارسنج نمی‌تواند ثابت کند مدل تمام شروط را استخراج کرده، «نمایش» را به «به‌روزرسانی» تبدیل نکرده یا سیاستی اختراع نکرده است؛ این‌ها معیار آزمون معنایی و بازبینی انسانی گام بعد هستند. قبول پاسخ مرجع fixture، موفقیت مدل محسوب نمی‌شود.

## نتیجه و گام بعد

چهار نمونهٔ قرارداد و ۱۱ آزمون متمرکز مرز نسخه/منبع/خطا موفق شدند؛ مجموع make check با آزمون‌های بستر ۶۵ مورد بود. چهار ref محلی sandbox نیز با خط مبنای خصوصی یکسان ماندند. runtime و رابط تغییر نکردند و فراخوانی مدل یا تست سراسری تکرار نشد. یک شکست در آزمون اولیه ناشی از alias شدن پاسخ مرجع داخل خود fixture تست بود؛ کپی مستقل اصلاح و مورد ناموفق مجدداً بررسی شد.

بستهٔ prompt/Workflow و adapter اکنون ساخته شده‌اند؛ [گزارش گام ۲](clasor-pa04-workflow.md) دو اجرای واقعیِ ردشده به علت نبود finish_reason معتبر را ثبت می‌کند. قدم بعد رفع ناسازگاری metadata و سپس تکمیل آزمون معنایی و یک دور بازخورد است. پس از قبولی تحلیلگر، اتصال PO → TL و تصمیم‌های واقعی هر نقش بررسی شود.
