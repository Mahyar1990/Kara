# گزارش پذیرش KP-02

۲۲ اکتبر ۲۰۲۶ — تعریف ایجنت تیمی، مجوزهای صریح و اجرای مستقل نسخهٔ منتشرشده. قرارداد و محدودیت‌ها در [ایجنت‌های تیم](kara-team-agents.md) ثبت شده‌اند. ساخت ایجنت‌های اختصاصی کلاسور هنوز شروع نشده است.

## شواهد API و موتور

- ۶۹ آزمون PostgreSQL/API: تعریف و مجوزها، اتصال guard به سازندهٔ واقعی وب، migration، نقش‌های KP-01 و رگرسیون پروژه‌ها، کاربران، کارتابل، قالب‌ها و اتوماسیون‌ها؛ موفق.
- ۵۴ آزمون بستر در `make check`؛ موفق. پس از توقف و ادامهٔ کار، این مجموعه‌های موفق بدون تغییر مرتبط دوباره اجرا نشدند.
- HTTP با JWT و CSRF بومی روی بانک جدا `kara_kp01_restore` و دو پروژهٔ ساختگی بررسی شد؛ حساب و دادهٔ آزمایشی وارد بانک اصلی نشدند.
- عضو `normal` بدون editor نسخهٔ اول Workflow را اجرا کرد، درحالی‌که برنامه نسخهٔ دوم منتشرشده داشت؛ شناسهٔ نسخه و Account واقعی در WorkflowRun تطبیق داده شدند.
- دو POST هم‌زمان با یک کلید، یک attempt و یک WorkflowRun ساختند. دو ویرایش هم‌زمان ACL با revision یکسان، ۲۰۰ و ۴۰۹ گرفتند.
- CSRF ناقص، actor جعلی در body، پروژهٔ خارجی، استفادهٔ دوباره از کلید با payload متفاوت و revision قدیمی رد شدند.
- وب عمومی با passport معتبر، Service API با کلید معتبر، draft، تک‌گره، iteration/loop، trigger، stop و حذف منبع نتوانستند مسیر تیمی را دور بزنند.
- پس از لغو `run`، دریافت نتیجه و replay درخواست نیز ۴۰۳ شدند؛ اجرا در کارتابل قدیمی نشت نکرد.

گزارش‌های طولانی و fixture دارای رمز، فقط در `.runtime/kp02/` باقی می‌مانند. `http-result.json` خلاصهٔ نتیجه و `web-build-final.log` گزارش ساخت کامل است. این فایل‌ها خصوصی و خارج Git هستند.

## کلاینت و محیط

ساخت کامل Dockerfile مشترک تا مرحلهٔ ۴۷ موفق شد؛ TypeScript و ۱۴ آزمون رابط نیز موفق بودند. دریافت رسمی لایهٔ کوچک Alpine انجام و وابستگی‌های JavaScript با کش معتبر و lockfile ثابت نصب شدند. کامپایل Next.js حدود ۵٫۸ دقیقه طول کشید.

آزمون کوتاه مرورگر روی کلاینت نهایی موفق بود: مدیر، ایجنت را با نسخهٔ اول ثبت و فقط `run` را به عضو داد؛ عضو عادی همان ورودی را اجرا و خروجی `answer` صحیح دریافت کرد. عنوان Kara و RTL، نبود فرم مدیریت برای عضو و فقط‌خواندنی‌بودن چهار فرم نقش‌های KP-01 نیز بررسی شدند. تصویر خصوصی `ui-member-run.png` شاهد رابط است.

کنترل نهایی متمرکز، اختیار ادمین کل در جایگزینی ACL و Account، نسخه، خروجی و نقش `normal` همان اجرای مرورگر را در بانک تطبیق داد؛ مجموعهٔ کامل API تکرار نشد. محیط با `make up` به بانک اصلی بازگشت و `make doctor` موفق شد. شمارنده و هش محتوای ۱۳ جدول قبلی شامل پروژه، عضویت/نقش، برنامه، Workflow، فرم انسانی و اتوماسیون پیش و پس از migration یکسان بود. سه پروژهٔ اصلی حفظ شدند؛ بانک اصلی صفر ایجنت تیمی ساختگی و دو migration ثبت‌شده دارد. پیش از ارتقا backup خصوصی گرفته شد. worker اصلی پاسخ `pong` داد و کلاینت اصلی همان سه پروژه را بدون خطای رابط نمایش داد.

## حدود نتیجه

پذیرش این گام مربوط به Community محلی و Workflow قطعی بدون فراخوانی مدل است. تست مدل یا Enterprise ادعا نمی‌شود. چرخهٔ بازخورد/نهایی‌سازی، فلوهای تیمی، تحویل و بازیابی پیشرفته هنوز گام‌های بعدند. در صورت مرگ worker پس از claim، تلاش خودکار دوباره اجرا نمی‌شود؛ رکورد running نامعلوم نیازمند بررسی است و تکمیل بازیابی در KP-07 قرار دارد.

## ادامهٔ کار

گام بعد KP-03: ساخت، اعتبارسنجی و انتشار فلوهای تیمی نسخه‌دار با ارجاع به ایجنت‌های مجاز همین پروژه؛ اجرای جاری باید روی نسخهٔ انتخاب‌شده باقی بماند.
