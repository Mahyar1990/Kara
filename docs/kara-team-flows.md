# فلوهای تیمی نسخه‌دار — KP-03

فلو، ترتیب همکاری انسان‌ها با ایجنت‌های ثبت‌شدهٔ همان پروژه است. انتشار فلو هیچ ایجنتی را اجرا نمی‌کند و جای تصمیم PO را نمی‌گیرد. پروندهٔ درخواست و تصمیم ورود در KP-04 و اجرای مراحل در KP-05 اضافه می‌شوند.

## رفتار

- عضو فعال دارای نقش فنی owner/admin/editor و مجوز بومی ساخت برنامه، پیش‌نویس می‌سازد و ویرایش می‌کند. نقش کاری به‌تنهایی این اختیار را نمی‌دهد. در Enterprise، مجوز بومی انتشار برنامه‌های مراحل نیز هنگام انتشار بررسی می‌شود؛ پذیرش فعلی روی Community است.
- هر فلو نام یکتای جاری در همان پروژه، توضیح و حداکثر ۳۰ مرحلهٔ مرتب دارد. پیش‌نویس ناقص قابل ذخیره است؛ انتشار آن رد می‌شود.
- هر مرحله شناسهٔ پایدار `key`، عنوان، ایجنت، اجراکننده، نهایی‌کننده، incarnation عضویت هر دو فرد، نقش تصمیم اختیاری PO/TL و اتصال ورودی دارد.
- اجراکننده باید grant فعلی `run` و نهایی‌کننده grant فعلی `finalize` همان ایجنت را داشته باشند. در صورت انتخاب نقش تصمیم، نهایی‌کننده باید همان نقش کاری را نیز داشته باشد. انتشار grant تازه‌ای ایجاد نمی‌کند.
- منبع ورودی: متن درخواست، مقدار ثابت با نوع معتبر، یا خروجی نام‌گذاری‌شدهٔ یکی از مراحل قبلی. ارجاع به خود/مرحلهٔ آینده، منبع یا خروجی گم‌شده، ورودی ناشناخته و ورودی الزامیِ بدون منبع رد می‌شوند. ترتیب خطی و ارجاع فقط به عقب، چرخه را منع می‌کند؛ موتور گراف دوم ساخته نشده است.
- محتوای ورودی ثابت و پیکربندی نسخهٔ منتشرشده برای اعضای پروژه قابل خواندن است؛ رمز یا اعتبارنامه اینجا ذخیره نشود. گراف و prompt و اتصال خصوصی Workflow در snapshot قرار نمی‌گیرند.
- انتشار، شناسهٔ مستقل، شمارهٔ نسخه، digest و snapshot مراحل می‌سازد. شناسه و digest Workflow منتشرشده و قرارداد ایجنت و افراد انتخاب‌شده از دادهٔ معتبر سرور گرفته می‌شوند.
- ویرایش بعدی فقط پیش‌نویس را تغییر می‌دهد. نسخهٔ قبلی با همان شناسه و محتوای ثابت قابل خواندن می‌ماند؛ مصرف‌کنندگان آینده باید همین شناسه را pin کنند، نه `current_version_id` را در هر اقدام دوباره بخوانند.
- بایگانی، ویرایش و انتشار تازه را می‌بندد؛ نسخه‌های تاریخی حذف نمی‌شوند. لغو grant/نقش یا حذف عضویت نیز تاریخچه را بازنویسی نمی‌کند؛ هنگام اقدام اجرایی آینده باید اختیار و عضویت دوباره بررسی شوند.

## ذخیره و تراکنش

مهاجرت افزایشی `003_team_flows`، جدول‌های `company_team_flows` و `company_team_flow_versions` را می‌سازد. header پیش‌نویس، revision و اشاره‌گر انتشار دارد؛ نسخهٔ منتشرشده قرارداد v1، snapshot، ناشر، زمان UTC و digest دارد. FK مرکب، اشاره‌گر نسخهٔ جاریِ متعلق به فلو یا پروژهٔ دیگر را منع می‌کند. trigger پایگاه داده UPDATE/DELETE نسخهٔ منتشرشده را خطا می‌کند؛ API حذف خام ندارد.

checksum مهاجرت‌های ۰۰۱ و ۰۰۲ دست‌نخورده است. مهاجرت ۰۰۳ برای بدنهٔ trigger از مرز صریح `-- kara-statement` استفاده می‌کند؛ تقسیم سادهٔ semicolon داخل بدنهٔ تابع انجام نمی‌شود. DDL و marker همان تراکنش و قفل migration را حفظ می‌کنند.

نوشتن فلو ابتدا ردیف Tenant و سپس فلو را قفل می‌کند؛ این ترتیب با تغییر نقش و ACL هماهنگ است. انتشار زیر همان قفل، scope، عضویت، مجوز، وضعیت برنامه و digest نسخهٔ منتشرشده را بازبینی می‌کند. ثبت نسخه، تغییر pointer/revision و رویداد idempotency یک تراکنش‌اند. رویدادهای `flow.save/publish/archive` از journal موجود ایجنت‌ها استفاده می‌کنند و به actor/پروژه/عملیات/هدف/payload مقیدند.

## API

پیشوند: `/console/api/company/projects/<project_id>/team/flows` با نشست و CSRF بومی.

| مسیر | روش | رفتار |
| --- | --- | --- |
| `/` | GET / POST | فهرست / ساخت پیش‌نویس |
| `/options` | GET | اعضای فعال و ایجنت‌های قابل انتخاب و مجریان/نهایی‌کنندگان دارای grant؛ فقط سازندهٔ مجاز |
| `/<flow_id>` | GET / PUT | خواندن / ذخیرهٔ پیش‌نویس |
| `/<flow_id>/publish` | POST | اعتبارسنجی و ساخت نسخهٔ ثابت |
| `/<flow_id>/archive` | POST | بایگانی بدون حذف تاریخچه |
| `/<flow_id>/versions` | GET | نسخه‌های منتشرشده |
| `/<flow_id>/versions/<version_id>` | GET | خواندن همان نسخهٔ دقیق |

عضو عادی فقط فلوهای منتشرشده و تاریخچهٔ آن‌ها را می‌بیند؛ `draft_stages` در پاسخ او نیست. تمام mutationها header `Idempotency-Key` با UUID استاندارد و `expected_revision` صحیح مثبت دارند. ثبت جدید revision یک دارد؛ هر ذخیره/انتشار/بایگانی revision را افزایش می‌دهد. کلید یکسان با درخواست یکسان نتیجهٔ قبلی می‌دهد؛ payload متفاوت یا revision قدیمی ۴۰۹ می‌گیرد. actor، workflow snapshot و شناسهٔ نسخه را کلاینت تعیین نمی‌کند.

شکل مرحلهٔ پیش‌نویس:

```json
{
  "key": "analysis", "title": "تحلیل درخواست", "agent_id": "<uuid>",
  "executor_id": "<account-uuid>", "executor_membership_id": "<join-uuid>",
  "finalizer_id": "<account-uuid>", "finalizer_membership_id": "<join-uuid>",
  "decision_role": "po", "inputs": {"request": {"source": "request"}}
}
```

اتصال خروجی مرحلهٔ قبلی: `{"source":"stage","stage_key":"analysis","output":"answer"}`. مقدار ثابت: `{"source":"constant","value":"متن ساختگی"}`. اعتبارسنجی نوع مقدار خروجی پویا هنگام اجرای مرحله نیز لازم است؛ وجود نام خروجی، تضمین نوع مقدار در زمان اجرا نیست.

در خطا: قالب نامعتبر ۴۰۰، نبود اختیار ۴۰۳، مرجع خارج scope یا گم‌شده ۴۰۴، revision/عضویت قدیمی یا نام تکراری ۴۰۹، پیش‌نیاز ناقص یا نسخه/اتصال نامعتبر ۴۲۲. قبل از migration نسخهٔ پشتیبان بگیرید؛ بازگشت مخرب خودکار و حذف تاریخچه وجود ندارد.

## حذف با تأیید نام

سازندهٔ مجاز فلو می‌تواند از کارت آن، «حذف فلو» را انتخاب کند. واردکردن دقیق نام کامل در دیالوگ لازم است و این شرط همراه revision و اختیار در سرور نیز کنترل می‌شود. حذف از فهرست و انتخاب برای درخواست‌های تازه انجام می‌شود؛ رکورد تاریخچه و نسخه‌های منتشرشده، تصمیم‌ها و اجراهای قبلی حفظ می‌شوند و اجرای تیمیِ از قبل ایجادشده قابل ادامه است. نام فلو برای ساخت مورد تازه آزاد می‌شود. فلوهای بایگانی‌شده نیز قابل حذف‌اند.

مسیر `POST /company/projects/<project>/team/flows/<id>/delete` بدنهٔ `expected_revision, confirmation_name` و header معمول `Idempotency-Key` دارد. خطاهای نام، اختیار، scope و نسخه همان قرارداد حذف ایجنت را دارند. هیچ حذف واقعی روی داده‌های کاربر در بررسی‌های توسعه انجام نمی‌شود؛ تست‌ها از تراکنش‌ها و موارد ساختگی استفاده می‌کنند.
