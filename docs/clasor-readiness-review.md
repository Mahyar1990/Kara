# بازبینی آمادگی Kara برای برنامه‌ریزی ایجنت‌های کلاسور

۲۳ اکتبر ۲۰۲۶ — مبنای بازبینی `master` در `e008e1d`، پس از [پذیرش KP-08](kara-kp08-validation.md). مرجع نیاز، تصمیم‌های U-01 تا U-14 در [مدل کارکرد](kara-operating-model.md) است؛ U-14 پس از پاسخ تکمیلی کاربر ثبت شد.

## تصمیم

**برنامه‌ریزی و شروع پایلوت ایجنت تحلیل نیازمندی با ورودی دستی قابل انجام است؛ تمام چشم‌انداز محصول هنوز تکمیل نشده است.** هستهٔ همکاری انسانی مسیر دستی پذیرفته شده، اما این پذیرش به معنای آماده‌بودن Jira، ابزار توسعه/QC، مدل بومی هر پروژه یا استقرار سازمانی نیست. هیچ ایجنتی در این بازبینی ساخته یا فعال نشد.

## قیود فنی مؤثر بر طراحی ایجنت

- ایجنت تیمی فعلی یک **Workflow با شروع دستی** است. Start متنی/انتخاب/عدد/checkbox پشتیبانی می‌شود؛ ورودی file/object، Agent v2، گره agent داخلی، trigger و فرم تصمیم داخلی در ثبت این نوع ایجنت پذیرفته نیستند (`agents.contracts`). نام «ایجنت» در محصول الزاماً به گره فنی agent اشاره ندارد.
- در نگاشت `source=request` فقط متن نسخهٔ درخواست به Workflow می‌رسد (`stages.resolve`). وجود پیوست در پرونده به معنای خواندن خودکار آن توسط مدل نیست. قرارداد پایلوت باید متن و منابع منتخب را صریح منتقل کند؛ استخراج پیوست، جست‌وجوی مخزن و DMS کار جدا هستند.
- JSON تو‌در‌تو ورودی Start فعلی نیست؛ برای پایلوت می‌توان بستهٔ ساختاریافته را با schema مشخص به متن JSON تبدیل کرد. اعتبارسنجی معنایی/schema تخصصی باید در Workflow و بستهٔ ارزیابی طراحی شود؛ کنترل فعلی نام خروجی و حجم، صحت تحلیل را تضمین نمی‌کند. رشد تاریخچهٔ بازخورد و سقف ورودی/خروجی باید در قرارداد هزینه لحاظ شوند.
- تعریف ایجنت به workflow_id و digest ثابت متصل است. API عمومی برای جایگزینی نسخهٔ تعریف همان ایجنت وجود ندارد؛ ثبت دوبارهٔ همان App رد می‌شود (`agents.register`). برای نسخهٔ جدید پایلوت، برنامه/تعریف مستقل ثبت و نسخهٔ تازهٔ فلو منتشر شود تا پرونده‌های قبلی ثابت بمانند. ویرایش درجا، روش ارتقای نسخه نیست.
- مجوز اجرا/بازخورد/نهایی‌سازی، نقش کاری و نقش فنی ساخت برنامه مستقل‌اند. اگر PO باید فلو بسازد، اختیار فنی مناسب هم لازم دارد؛ اگر فقط تحلیل را اجرا کند، grant مرحله کافی است.

## شواهد این بازبینی

- کد مدیریت پروژه، نقش/ACL، فلو، درخواست، مرحله، صف و بازیابی با مستندات و معیارهای KP-08 تطبیق داده شد. تغییر تولیدی پس از پذیرش بررسی‌شده وجود نداشت؛ HEAD بعدی فقط اصلاح برنامهٔ کلاسور بود.
- بررسی اسناد و لینک‌ها و ۵۴ آزمون سبک `make check` در همین بازبینی موفق شدند؛ کد محصول و runtime تغییر نکردند.
- `make doctor` فعلی موفق: تصویر API/web/worker منطبق، کلاینت HTTP 200 و فارسی/RTL، API pong. صفحهٔ باز پروژه بدون alert و دارای مسیرهای ایجنت تیم، فلو، درخواست، اجرای تیمی و کارتابل بود. تست سراسری یا فراخوانی مدل در این بازبینی تکرار نشد.
- شواهد خصوصی موجود KP-08 بازخوانی شدند: چهار phase موفق، هشت اجرای قطعی موتور، smoke مستقل اتصال مدل HTTP 200، و تطبیق پیش/پس ۳۱ جدول اصلی. این‌ها اجرای ثبت‌شدهٔ پذیرش قبلی‌اند؛ اجرای جدید مدل یا کل سناریو در این نوبت نیستند.
- خواندن فقط شمار تنظیمات، در تراکنش read-only بانک اصلی: سه provider-model معتبر و سه مدل پیش‌فرض LLM ثبت‌اند، ولی تعداد رکوردهای معتبر در جدول `providers` صفر است؛ مسیر credential سطح مدل جداست، بنابراین این شمارها به‌تنهایی اثبات اتصال یا خرابی نیستند. آزمون موفق **LLM در Workflow بومی همان پروژه** هنوز شاهد ندارد و پیش‌نیاز پذیرش ایجنت واقعی است. هیچ credential خوانده یا چاپ نشد.
- در بانک اصلی تعداد تعریف ایجنت تیمی و نسخهٔ منتشرشدهٔ فلوی تیمی هر دو صفر بود. پذیرش KP-08 در بانک آزمایشی جدا انجام شده؛ پروژهٔ عملیاتی کلاسور هنوز باید راه‌اندازی شود. وجود برنامه‌های قدیمی استودیو با ثبت ایجنت تیمی یکسان نیست.
- هر چهار مخزن محلی Server/Client/Newman/PlayWright و ref محلی `origin/sandbox` در دسترس‌اند؛ در Server/Client شاخهٔ sandbox محلی هم با آن برابر بود. commitهای دقیق در `.runtime/clasor-readiness-review/repository-baselines.json` خصوصی ثبت شدند. fetch، تغییر شاخه و بررسی عمیق سورس انجام نشد؛ تازگی نسبت به سرور یا صحت زمینهٔ تخصصی هنوز ادعا نمی‌شود.
