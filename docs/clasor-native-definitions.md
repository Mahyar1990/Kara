# تعریف‌های بومی PA-04 و TL در پایلوت

**وضعیت جاری:** تعریف‌های مستقل PA-04 0.1.3 و TL 0.1.1 با hook نهایی‌سازی نصب و به نسخهٔ ۲ همان فلو متصل شدند؛ [گزارش اتصال و انتشار](clasor-finalization-hook.md) مرجع جاری است. این سند سابقهٔ نصب 0.1.2/0.1.0 را حفظ می‌کند.

۲۳ اکتبر ۲۰۲۶ — تعریف PA-04 نسخهٔ 0.1.2 و TL نسخهٔ 0.1.0 در دو برنامهٔ مستقل پایلوت وارد و منتشر، به‌عنوان ایجنت تیمی ثبت و به پیش‌نویس دومرحله‌ای متصل شدند. **در پایان گام تعریف‌ها، فلو منتشر نشده بود؛ اکنون [نسخهٔ ۱ فلو](clasor-flow-publication.md) نیز منتشر شده است. مدل اجرا نشده و تصمیم PO/TL ثبت نشده است.** انتشار تعریف، پذیرش تحلیلگر یا آمادگی اجرای مدل نیست.

[DefinitionCaller](../clasor_agents/product_flow/definitions.py) ابزار تنظیم تعریف است؛ از [Caller مراحل](clasor-product-caller.md) جداست. Caller معمولی همچنان endpoint انتشار ندارد. تنظیم تعریف فقط import برنامهٔ تازه، خواندن/انتشار Workflow پین‌شده، ثبت ایجنت و تنظیم grant مسئول منتخب را انجام می‌دهد؛ endpointهای اجرای Workflow/مدل، تنظیم مدل/اعتبارنامه، انتشار فلو و تصمیم انسانی را ندارد.

## روش و مرزها

1. با حساب سازندهٔ مجاز، project/workspace/عضویت از API نشست تطبیق داده شود. این عنوان فنی، جای PO/TL در تصمیم‌های مرحله را نمی‌گیرد.
2. import_definition فقط یکی از بسته‌های محلی analysis یا planning را وارد می‌کند و app_id قبلی برای جایگزینی نمی‌فرستد. پاسخ import را فوراً در journal خصوصی ذخیره کنید. import بومی کلید idempotency ندارد؛ در timeout با نتیجهٔ نامشخص، ابتدا import را reconcile کنید و خودکار دوباره import نکنید.
3. verify_import، شناسه و نسخهٔ رسید را کنترل و graph را با سازندهٔ محلی دقیقاً مقایسه می‌کند. فقط viewport چیدمان حذف می‌شود؛ node، edge، prompt، مدل و Code نمی‌توانند متفاوت باشند. environment/conversation/rag variables نیز باید همان آرایه‌های خالی export باشند.
4. publish_definition فقط برای app تأییدشده مجاز است. نام نسخه مطابق سقف ۲۰ نویسهٔ API بومی، PA04-0.1.2 یا TL-0.1.0 است. پس از انتشار GET مستقل، graph و شناسهٔ Workflow منتشرشده را کنترل می‌کند. برای بازیابی، اگر همان نسخهٔ پین‌شده از قبل منتشر شده باشد، نسخهٔ تکراری نمی‌سازد؛ انتشار موجود با marker متفاوت رد می‌شود.
5. register_definition فقط Workflow منتشرشدهٔ مطابق رسید را ثبت می‌کند؛ قرارداد Start/End نیز با بسته تطبیق دارد. در تکرار، ثبت موجود همان app خوانده و کنترل می‌شود. receipt و کلیدهای registration/grants خصوصی و پایدار بمانند.
6. assign_responsible فقط روی ایجنتِ ثبت و تأییدشده کار می‌کند. grantهای view/run/feedback/finalize به شخص منتخب داده می‌شوند؛ edit/publish/manage_access اضافه نمی‌شوند. ACL غیرخالیِ متفاوت بازنویسی نمی‌شود؛ تغییر مجوز فرد دیگر به تصمیم مدیریتی جدا نیاز دارد.
7. bind با options تازه، نقش po/tl، incarnation عضویت، grantها و Workflowهای جدید را کنترل می‌کند. همان پیش‌نویس اتصالِ ساخته‌شده در گام قبل با CAS و GET مستقل تکمیل می‌شود؛ فلو منتشر نمی‌شود و نسخهٔ تعریف/اجرای قدیمی دست‌نخورده می‌ماند.

پس از قطع ارتباط، از رسیدهای خصوصی همان مرحله ادامه دهید؛ گردش‌کار قدیمی را reset یا overwrite نکنید. برای ثبت و grant از همان Idempotency-Key و بدنه استفاده شود. تطابق schema/graph یا انتشار بومی، موفقیت اتصال مدل، اجرای واقعی برنامه‌ریز یا تصمیم انسانی را اثبات نمی‌کند. alias و بودجهٔ مدل در این گام تغییر/آزمون نشدند.

## نتیجهٔ واقعی

- دو app مستقل برای PA-04 0.1.2 و TL 0.1.0 ساخته شدند؛ graph پیش‌نویس و graph منتشرشدهٔ هر دو با export متناظر تطبیق داشت.
- هر دو به‌عنوان ایجنت تیمی همان پروژه ثبت شدند. PA-04 به حساب ساختگی PO و TL به حساب ساختگی TL متصل است؛ هر مرحله یک executor/finalizer مشخص دارد.
- با نشست واقعی PO، TL و حساب بدون مجوز، دسترسی بررسی شد: هر مسئول چهار grant ایجنت خودش را دید؛ PO مجوز run/feedback/finalize برنامه‌ریز نگرفت و TL این اختیارها را روی تحلیلگر نگرفت. نقش بومی TL برای این کار editor نشد.
- پیش‌نویس دومرحله‌ای قبلی اکنون تمام شناسه‌های ایجنت، Workflow و مسئول/عضویت را دارد؛ current_version_id همچنان null است. هیچ FlowVersion یا FlowInstance جدید، درخواست یا تصمیم ورود ساخته نشد.
- state/revision/round، attempts، artifacts، feedback و decisions مرحلهٔ شکست‌خوردهٔ قبلی پیش و پس از این کار برابر ماندند. آن سابقه به موفقیت تبدیل نشد.
- شمار WorkflowRun دو app تازه در DB **صفر** بود. در sandbox واقعی بومی، فقط Code آماده‌سازی و validator TL با پاسخ مرجع ساختگی اجرا و نتیجه تطبیق داده شد؛ finish_reason=null نیز با incomplete_output رد شد. این بررسی یک اجرای LLM/Workflow تحلیلگر نیست.

اولین درخواست انتشار PA-04 به دلیل طول بیش از ۲۰ نویسهٔ نام نسخه، ۴۲۲ گرفت؛ نام مطابق قرارداد API اصلاح شد و ادامه از همان import موجود انجام شد. import تکراری ساخته نشد. make check نهایی با ۱۲۳ آزمون موفق شد. شش آزمون متمرکز کنترل graph/متغیر، import مستقل، طول marker و readback، ثبت و قرارداد، حفظ ACL و محدودیت endpointها را پوشش می‌دهند.

رسیدهای import/Workflow/agent/grants و draft، بررسی دسترسی و شواهد sandbox در `.runtime/clasor-definitions/` خصوصی‌اند؛ credential یا مسیر خصوصی منابع وارد Git نشده است. manifestهای کنار export، خروجی بازسازی آفلاین‌اند و registry انتشار هر محیط نیستند؛ وضعیت نصب واقعی از همین رسیدها و گزارش خوانده شود.

## ادامه

برای پایلوت عمومی‌تر، وابستگی‌های master (حفظ اصل درخواست و validator پیش از finalize) و انتقال معتبر finish_reason هنوز بازند. پذیرش معنایی PA-04 و تصمیم واقعی PO نیز انجام نشده‌اند؛ بنابراین ثبت ورودی TL با تحلیل مصوب واقعی همچنان آزمون زنده نشده است. پیش‌نویس فلو قابل بازبینی است، اما این گام مجوز خودکار انتشار آن یا ساخت تصمیم PO نیست.

بررسی و انتشار نسخهٔ دقیق فلو در گزارش گام بعد ثبت شده است؛ ایجاد اجرا و عبور به TL تا تصمیم‌های انسانی و ورودی معتبر باز می‌ماند.
