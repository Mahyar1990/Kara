# خط مبنای پایلوت کلاسور — گام صفر

۲۳ اکتبر ۲۰۲۶ — مبنای بستر `86f3298` روی master؛ ادامهٔ [برنامهٔ کلاسور](clasor-agents-implementation-plan.md) و [بازبینی آمادگی](clasor-readiness-review.md).

## نتیجه

**گام صفر انجام شد:** منابع sandbox تثبیت، پروژهٔ مستقل و حساب‌های ساختگی آماده، و یک Workflow کوچک دارای LLM در موتور بومی Kara واقعاً اجرا شد. ایجنت تخصصی PA-04، قرارداد اجرایی آن و فلو PO → TL هنوز ساخته نشده‌اند. تصمیم مسئول مشخص هر مرحله (U-14) برقرار است.

## منابع تثبیت‌شده

هر چهار مخزن از ref محلی `refs/remotes/origin/sandbox` و commit دقیق همان ref بررسی شدند؛ checkout جاری مبنا قرار نگرفت و fetch یا تغییر سورس انجام نشد. شناسه‌های کامل، مسیرهای محلی و بستهٔ زمینه در `.runtime/clasor-pilot0/` خصوصی‌اند.

- Server: قواعد AGENTS، نقشهٔ پروژه، package.json و سند/مهارت منتخب همان snapshot. شواهد این مبنا NestJS 10 با بستر Express را نشان می‌دهند؛ برداشت تاریخی «Express بدون NestJS» مبنای ادامه نیست.
- Client: قواعد AGENTS، نقشه، فهرست اسناد و منابع منتخب همان snapshot؛ وابستگی Next.js `^16.2.6` و React `^19.2.6` ثبت شد. این‌ها بازهٔ package.json هستند، نه ادعای نسخهٔ نصب‌شدهٔ محیط محصول.
- Newman: در snapshot مبنا AGENTS/PROJECT_MAP ریشه وجود ندارد؛ یک collection با ۲۸۶۴ درخواست شناسایی شد. credential، environment و بدنه‌های درخواست وارد زمینه نشدند. شمار درخواست، نتیجهٔ تست نیست.
- PlayWright: AGENTS/PROJECT_MAP ریشه وجود ندارد؛ ۲۹۳ فایل spec/test و وابستگی `@playwright/test` با بازهٔ `^1.52.0` ثبت شدند. هیچ تست محصول اجرا نشد.

manifest خصوصی، ۱۵ فایل منتخب را با repo/ref/commit/path/SHA-256 ثبت می‌کند. قواعد رفتاری و مهارت‌ها زیر `rules` و شواهد فنی زیر `evidence` جدا هستند. مستند و map، شاهد زمینه‌اند؛ بررسی یک قابلیت واقعی در گام‌های بعد به خواندن سورس مرتبط از همان snapshot نیاز دارد. هیچ کل مخزن یا زمینهٔ خصوصی در آزمون مدل ارسال نشد. از مخازن کلاسور اعتبارنامه، PEM و فایل‌های محیط خوانده/کپی نشدند؛ در این مرحله فقط اطلاعات اتصال خصوصیِ موجود Kara برای پیکربندی مدل پایلوت استفاده شد.

## محیط و اجرای مدل

پروژهٔ «پایلوت ایجنت‌های کلاسور» به‌صورت مستقل در بانک اصلی محلی ساخته شد. سه حساب ساختگی PO، TL و عضو بدون مجوز دارد؛ PO آزمایشی مالک/مدیر این پروژه نیز هست و TL و عضو دیگر نقش بومی normal دارند. ایجاد حساب/عضویت اولیه fixture مستقیم بود؛ ایجاد پروژه، نقش‌های کاری، تنظیم مدل، import و انتشار Workflow با API واقعی انجام شدند. هیچ تصمیم PO/TL در پروندهٔ واقعی ثبت و هیچ دعوت یا پیام بیرونی ارسال نشد.

بستهٔ رسمی `langgenius/openai_api_compatible` نسخهٔ `0.0.68` با همان شناسه/ checksum نصب موجود، از cache در پروژهٔ پایلوت نصب شد. اتصال شرکت از فایل خصوصی موجود خوانده و با API بومی به credential پروژهٔ جدید تبدیل شد؛ نام مدل واقعی، endpoint و توکن در Git یا خروجی ابزار قرار نگرفتند. تنظیمات پروژه‌های قبلی هدف نوشتن نبودند.

این شاهد، اتصال واقعی provider و Workflow دارای LLM بومی در **همین پروژه** است؛ کیفیت PA-04، خروجی ساختاریافته، ابزارها و مجوز/نهایی‌سازی نقش واقعی را نمی‌پذیرد. لاگ عمومی برنامه، اجرای debugger را فهرست نکرد؛ شاهد اجرا از رویداد پایان native API و رکوردهای WorkflowRun/گره گرفته شد؛ تاریخچهٔ اجرای debugger در خود ویرایشگر نیز همان نتیجه را نشان داد. اجرای جدیدی صرفاً برای پرکردن صفحهٔ لاگ ساخته نشد.

## حفظ محیط و روش ادامه

- دادهٔ اصلی پیشین ۳۱ جدول با مبنای خصوصی پذیرش KP-08 تطبیق داده شد: با کنارگذاشتن ردیف‌های پروژه/فضای جدید، شمار/hash تمام ردیف‌های قبلی برابر بود. دادهٔ تازه فقط پروژهٔ پایلوت و fixtureهای متعلق به آن است؛ snapshot جای پشتیبان‌گیری عملیاتی نیست.
- پروژه و برنامهٔ آزمون در محیط محلی باقی‌اند؛ native Workspace، credential، حساب‌ها و اجراهای پایلوت دادهٔ محیط‌اند و با تغییر شاخهٔ Git جدا نمی‌شوند. اطلاعات ورود ساختگی در `pilot.local.json` با دسترسی 0600 و پوشهٔ خصوصی 0700 نگهداری می‌شوند.
- UI با حساب ساختگی، پروژه و برنامهٔ مستقل و مدل متصل به نمودار را باز کرد؛ در تاریخچهٔ همان اجرای debugger خروجی `KARA_NATIVE_OK` بدون alert دیده و تصویر `ui-native-run.png` ثبت شد. هیچ اجرای مدل از مرورگر تکرار نشد. پیام همگام‌سازی در نمودار هم دیده شد؛ این smoke پذیرش کامل تعاملات ویرایشگر نیست. حساب آزمایشی خارج و تب آن بسته شد؛ صفحهٔ قبلی کاربر بدون alert باقی ماند. شواهد مرورگر و لاگ‌های bootstrap/configure/workflow/verify خصوصی‌اند.
- API/وب/worker و upstream در این قدم تغییر نکردند؛ ساخت دوبارهٔ تصویر و رگرسیون سراسری KP-08 لازم نبود. Compose، make doctor و ۵۴ آزمون سبک make check در همین گام موفق شدند.

با تغییر ref/path یا انتخاب قابلیت جدید، بستهٔ زمینه باید تازه شود. برای بازدید برنامه، وارد پروژهٔ پایلوت و «آزمون اتصال مدل پایلوت» شوید. مدل در این پروژه آمادهٔ آزمون بعدی است؛ اشخاص واقعی تیم و اختیارات عملیاتی هنوز جای حساب‌های ساختگی تنظیم نشده‌اند.

## پیش‌نویس قرارداد PA-04 برای گام بعد

این بخش طرح قرارداد است و فایل schema/DSL اجرایی یا ایجنت ساخته‌شده نیست؛ پیاده‌سازی آن پس از شروع ساخت روی `clasor-agents` قرار می‌گیرد.

- ورودی‌ها در حد Start فعلی Kara باشند: متن اصلی `request`، حالت `analyze/clarify/review_change`، زمینهٔ منتخب منابع و یک ورودی متنی جدا برای `feedback_context`. بستهٔ منبع شامل شناسه/مسیر/commit/hash و بخش مورد نیاز است؛ خود منابع، مجوز یا دستور اجرایی جدید نمی‌سازند. هویت، نسخه و تصمیم واقعی از رکوردهای بستر خوانده می‌شوند، نه ادعای prompt یا پاسخ مدل.
- متن اصلی با بازخورد مخلوط نشود. بستر فعلی سابقه و خروجی مبنا را به متغیر متنی منتخب بازخورد **اضافه** می‌کند؛ بنابراین آن متغیر، JSON خالص فرض نشود. در پایلوت متغیر جدا انتخاب شود و رابطهٔ نسخه/بازخورد در بستر حفظ شود؛ قرارداد اجرایی باید این رفتار را با نمونهٔ واقعی بررسی کند.
- خروجی پیشنهادی یک فیلد متنی `analysis` حاوی JSON معتبر است تا به ورودی متنی برنامه‌ریز نگاشت شود. محتوای آن شامل مسئله/محدوده، نیازمندی‌ها، AC، پرسش، فرض و ارجاع/ردیابی باشد؛ وضعیت فقط آمادگی تحلیل را بیان کند و فیلد تأیید انسانی تولید نکند. schema و validator باید پیش از ساخت تحلیلگر تعیین شوند؛ اعتبار نام خروجی در بستر برای صحت این JSON کافی نیست.
- نمونه‌های اولیه محدود باشند: درخواست روشن، درخواست مبهم، و شرط منفی همراه صفر/خالی/خطا؛ نمونهٔ تزریق دستور و خروجی JSON ناقص آفلاین بررسی شوند. شرط صریح نباید حذف یا معکوس، و عدد/سیاست بی‌منبع نباید ساخته شود. خروجی بریده یا بی‌منبع به خطای قابل بررسی برگردد؛ retry یا برش خاموش خودکار نباشد.
- بودجهٔ PA-04 جدا تعیین شود: تنظیم ۴۰۹۶/۵۱۲ فقط برای smoke بود. پیش از ارسال زمینهٔ تخصصی، بودجهٔ prompt/خروجی، سربار مشاهده‌شده و سقف بازخورد تعریف و با تعداد کمی نمونه اندازه‌گیری شود؛ ۱۵ فایل کامل در هر فراخوانی ارسال نشوند. سقف بایت/نویسهٔ Kara با سقف توکن مدل یکی نیست.

خروج گام بعد: قرارداد نسخه‌دار، نمونه/انتظار قابل بازبینی و سازنده/اعتبارسنج سبک؛ سپس Workflow مستقل PA-04 با آزمون معنایی واقعی و یک دور بازخورد. تصمیم نهایی همچنان با PO و آغاز مرحلهٔ بعد با مسئول مشخص آن است.
