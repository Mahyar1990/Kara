# راه‌اندازی کارا با Docker Compose

این مسیر برای محیط محلی مستقل هر همکار است. Git و Docker فعال با Compose نسخهٔ 2.24.4 یا جدیدتر لازم‌اند؛ Python و Node داخل کانتینرها اجرا می‌شوند و نصب آن‌ها یا Make روی میزبان لازم نیست. تصویرهای اختصاصی کارا در گیت قرار ندارند؛ Compose آن‌ها را از سورس می‌سازد.

## آماده‌کردن لپ‌تاپ

- ویندوز: Docker Desktop با Linux containers و یک توزیع WSL 2 با integration فعال. مخزن را داخل فایل‌سیستم لینوکسی WSL، مثلاً `~/projects/`، clone کنید و فرمان‌ها را همان‌جا اجرا کنید. [راهنمای رسمی WSL](https://docs.docker.com/desktop/features/wsl/best-practices/).
- مک: Docker Desktop یا Docker فعال با Colima. نصب ویژهٔ Colima در [راهنمای محیط محلی](local-development.md) است.
- لینوکس: Docker Engine و Compose plugin فعال؛ کاربر فعلی باید دسترسی اجرای Docker داشته باشد.

برای شروع، پیشنهاد عملی تخصیص ۴ پردازنده و ۸ GiB حافظه به Docker و حداقل ۳۰ GiB فضای آزاد است؛ این پیشنهاد برای ساخت اولیهٔ وب است، نه اندازه‌گیری حداقل مصرف برنامه. ساخت اولیه ممکن است طولانی باشد. دسترسی شبکه به GitHub، رجیستری تصاویر، مخازن Debian و npm لازم است.

```sh
docker info
docker compose version
```

اگر روی مک فقط فرمان مستقل `docker-compose` نصب است، در تمام فرمان‌های این راهنما آن را جایگزین `docker compose` کنید.

## اجرای اول

داخل ریشهٔ مخزن `company-agent-platform`، همان پوشه‌ای که `compose.yaml` دارد، اجرا کنید:

```sh
docker compose -f compose.setup.yaml run --build --rm setup
docker compose up -d --build
```

مرحلهٔ اول Python و Git را داخل کانتینر آماده‌سازی اجرا می‌کند، نسخهٔ قفل‌شدهٔ Dify را دریافت و کنترل می‌کند، patchها و قالب‌های کارا را در پوشهٔ ساخت جداگانه آماده می‌کند و تنظیمات خصوصی با رمزهای تصادفی می‌سازد. کانتینر آماده‌سازی به Docker socket دسترسی ندارد. مرحلهٔ دوم API و وب فارسی کارا را می‌سازد و بانک داده، صف، جستجو و سرویس‌های برنامه را اجرا می‌کند. تنظیم Compose رسمی نسخهٔ ثابت با overrideهای کارا [ترکیب می‌شود](https://docs.docker.com/reference/compose-file/include/)؛ فهرست سرویس‌های upstream دوباره کپی نشده است.

سرویس‌ها فقط روی همین لپ‌تاپ در دسترس‌اند. پس از ساخت، آماده‌شدن مهاجرت بانک و API چند دقیقه زمان می‌برد. این بررسی باید `{"result":"pong"}` بدهد:

```sh
docker compose exec -T api python -c "import urllib.request; print(urllib.request.urlopen('http://nginx/console/api/ping', timeout=10).read().decode())"
```

سپس [نصب کارا](http://localhost:8080/install) را باز کنید و حساب مدیر محیط خودتان را بسازید. اتصال مدل نیز در همان محیط تنظیم می‌شود؛ اطلاعات و پروژه‌های لپ‌تاپ همکار دیگر با clone منتقل نمی‌شوند.

## اجرای روزمره و به‌روزرسانی

```sh
docker compose up -d
docker compose ps
docker compose logs --tail 80 api web worker
docker compose down
```

`down` داده‌ها را حفظ می‌کند. پس از دریافت تغییرات جدید از گیت، دو فرمان بخش «اجرای اول» را تکرار کنید تا سورس‌های ساخت و تصاویر به‌روز شوند. آماده‌سازی دوباره، رمزها و فایل تنظیمات خصوصی موجود را عوض نمی‌کند. فرمان `up -d --build` روی محیط روشن ممکن است حافظهٔ زیادی مصرف کند؛ در صورت کمبود حافظه، ابتدا `docker compose stop` را اجرا کنید، سپس ساخت را تکرار کنید.

تنظیمات و داده‌ها در `.runtime/` خصوصی و خارج از Git هستند. این پوشه را حذف نکنید و برای همکاران نفرستید. سورس آماده‌شدهٔ وب فقط فایل‌های tracked نسخهٔ ثابت را می‌گیرد؛ رمزها و داده‌ها وارد context ساخت وب نمی‌شوند.

برای پورت متفاوت، فایل `.env.local.example` را به `.env.local` کپی و پورت‌ها را تنظیم کنید، سپس مرحلهٔ آماده‌سازی را دوباره اجرا کنید. اگر `DIFY_PROJECT_NAME` را تغییر داده‌اید، در همهٔ فرمان‌های اجرای برنامه از `docker compose -p <name> ...` با همان نام استفاده کنید. مسیر Make قبلی و این مسیر به‌صورت پیش‌فرض همان محیط `company-agent-local` را مدیریت می‌کنند؛ هم‌زمان دو نسخه با همان داده‌ها اجرا نکنید.

برای توسعه با ابزارهای میزبان، `make doctor` همچنان قابل استفاده است. بررسی و اصلاح نسخهٔ نصب‌شدهٔ SDK مدل بعد از نصب افزونه، مطابق [راهنمای اصلاح جریان مدل](kara-model-stream-repair.md) انجام می‌شود؛ راه‌اندازی Docker به‌تنهایی پذیرش اتصال مدل نیست.

## خطاهای متداول

| خطا | اقدام |
| --- | --- |
| فایل `.runtime/...` پیدا نمی‌شود | ابتدا فرمان `compose.setup.yaml` را اجرا کنید؛ `docker compose up` به‌تنهایی روی clone تازه کافی نیست. |
| `Pinned template catalog is missing` | clone کامل Git لازم است، نه ZIP. روی میزبان فرمان `git fetch origin <commit>` را که خطا چاپ کرده اجرا و setup را تکرار کنید. برای clone کم‌عمق می‌توانید ابتدا `git fetch --unshallow` را اجرا کنید. اعتبارنامهٔ Git میزبان به کانتینر منتقل نمی‌شود. |
| خطای `!override`، `!reset` یا `include` | Compose را به نسخهٔ 2.24.4 یا جدیدتر ارتقا دهید؛ Compose قدیمی v1 پشتیبانی نمی‌شود. |
| `Cannot connect` یا `permission denied` برای Docker | موتور Docker، context فعال، دسترسی کاربر و در ویندوز WSL integration را بررسی کنید. |
| `port is already allocated` | برنامهٔ استفاده‌کننده از پورت را متوقف کنید یا پورت `.env.local` را تغییر دهید و setup را تکرار کنید. |
| ساخت وب با کد ۱۳۷ یا `Killed` متوقف می‌شود | حافظهٔ Docker را افزایش دهید، سرویس‌ها را با `docker compose stop` متوقف و ساخت را تکرار کنید. |
| خطای دریافت Git، image، apt یا npm | دسترسی شبکه، پراکسی یا CA مورد تأیید سازمان را در ابزار مربوط بررسی کنید؛ Compose نیاز به دریافت این وابستگی‌ها را حذف نمی‌کند. |
| `lookup registry-1.docker.io: i/o timeout` | Docker نمی‌تواند نام رجیستری را resolve کند. ابتدا DNS و مسیر شبکهٔ میزبان/موتور Docker بررسی شود؛ تغییر Compose یا نصب buildx این timeout را حل نمی‌کند. |
| صفحه 502 یا API هنوز پاسخ نمی‌دهد | `docker compose ps` و لاگ‌ها را بررسی کنید؛ شروع کانتینر به معنی آماده‌شدن برنامه نیست. |

برای گزارش مشکل، نام سیستم‌عامل، خروجی `docker compose version` و بخش خطای فرمان شکست‌خورده را بفرستید. فایل‌های env و خروجی کامل `docker compose config` ممکن است رمز داشته باشند و نباید فرستاده شوند.

اگر خطا هنگام `FROM langgenius/dify-api:1.17.1` و همراه timeout نام رجیستری است، این فرمان مستقل همان دریافت را آزمایش می‌کند:

```sh
docker pull langgenius/dify-api:1.17.1
```

تا این فرمان موفق نشود، مسیر `make up` و مسیر Compose هر دو در دریافت تصویر پایه متوقف می‌شوند. اگر شبکهٔ شرکت برای دسترسی به رجیستری پراکسی لازم دارد، تنظیم آن باید برای [خود Docker daemon](https://docs.docker.com/engine/daemon/proxy/) انجام شود؛ تنظیم پراکسی فقط در shell کافی نیست. در Docker Desktop تنظیمات پراکسی از داخل برنامه اعمال می‌شوند. تغییر DNS سرویس‌ها در Compose نیز بر مرحلهٔ دریافت تصویر پایه اثری ندارد. هشدار legacy builder را جدا از خطای دریافت تصویر بررسی کنید.
