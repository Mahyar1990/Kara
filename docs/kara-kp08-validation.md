# گزارش پذیرش سراسری KP-08

۲۳ اکتبر ۲۰۲۶ — معیارهای بخش ۸ [برنامهٔ آمادگی](kara-platform-readiness-plan.md)، [سناریوی قابل اجرا و راهنمای پذیرش](../tests/acceptance/README.md).

## نتیجهٔ چرخهٔ تیمی

پذیرش با دادهٔ ساختگی در بانک جداگانهٔ `kara_kp08_acceptance`، HTTP واقعی nginx/API، JWT و CSRF حساب‌های واقعی آزمایش و موتور بومی انجام شد. ادمین کل موجود و شش حساب تازهٔ ساختگی استفاده شدند؛ ساخت حساب، عضویت اولیه و برنامهٔ قطعی fixture پایگاه داده است، نه آزمون دعوت ایمیلی. ایجاد پروژه، نقش، grant، تعریف ایجنت، انتشار فلو، درخواست و اقدامات مرحله از HTTP انجام شدند. کد محصول یا تصویر اجرایی در این قدم تغییر نکرد.

| معیار | نتیجه و شاهد |
| --- | --- |
| ۱ | ادمین کل دو پروژه با مدیرهای متفاوت ساخت. ساخت پروژه برای مدیر و دسترسی او به اعضای پروژهٔ دیگر رد شدند. |
| ۲ | دو فلو منتشر شد؛ PO برای درخواست اصلی فلو دومرحله‌ای و برای درخواست دوم فلو تک‌مرحله‌ای انتخاب کرد. ساخت اجرا با تصمیم ورود ناموجود رد شد. تصمیم ورود به‌تنهایی موتور را اجرا نکرد. |
| ۳ | اعضای normal با grant خودشان اجرا کردند. مدیر بدون grant به محتوای مرحله دسترسی نداشت؛ debug بومی برنامهٔ مدیریت‌شده بسته بود. grant، نقش بومی normal را تغییر نداد. |
| ۴ | نفر اول سه تلاش با دو بازخورد و سپس نسخهٔ انسانی مستقل ساخت. فقط نسخهٔ منتخب با PO مجاز نهایی شد؛ حذف نقش PO نهایی‌سازی را رد کرد. دو finalize هم‌زمان 200/409 شدند؛ فقط یک تصمیم مؤثر و replay پایدار ثبت شد. |
| ۵ | نفر دوم فقط ورودی نگاشت‌شده از نسخهٔ انسانی نهایی‌شده را گرفت؛ دسترسی محتوایی به مرحلهٔ اول نداشت. مرحلهٔ دوم بدون اجرای خودکار آماده شد؛ بازبین خودش اجرا، بازخورد و اجرای بعدی را انجام داد و PO نهایی کرد. |
| ۶ | PO مرحلهٔ اول را بازگشود؛ مصرف‌کننده stale شد و بازاعتبارسنجی زودهنگام آن رد شد. انتخاب artifact قدیمی رد شد. هر دو مرحله با اجرای صریح و تصمیم تازه تمام شدند؛ دو تصمیم هر مرحله و تمام تلاش‌ها/بازخوردها ماندند. |
| ۷ | کاربر پروژهٔ دیگر، عضو بی‌مجوز، مسئول مرحلهٔ دیگر، مدیر بدون grant، نقش حذف‌شده و درخواست بدون CSRF رد شدند. لغو grant قبل از claim، اجرای pending را از تولید خروجی منع کرد. تحویل مجاز به نفر دوم با حذف دسترسی نفر اول از بین نرفت. |
| ۸ | replay اجرای مرحله و تحویل تکراری موتور، اجرا را مضاعف نکرد. API واقعاً restart و worker واقعی Celery بالا آورده شد؛ تلاش pending ثبت‌شده پس از restart موفق شد. orphan قدیمی با اختیار مدیر و تأیید آثار recover شد؛ نتیجهٔ دیررس نتوانست آن را موفق کند. retry فقط ready ساخت؛ لغو صریح terminal و replay آن پایدار بود. خروج/ورود واقعی مرورگر، سابقه را حفظ کرد. |
| ۹ | انتشار نسخهٔ جدید فلو و تغییر pointer نسخهٔ منتشرشدهٔ برنامهٔ بومی، binding پروندهٔ موجود را تغییر ندادند؛ تلاش‌ها با workflow_id قدیمی انجام شدند. از بانک نهایی آزمون پشتیبان گرفته و در بانک تازهٔ `kara_kp08_rehearsal` بازیابی شد؛ شمار و hash کامل ۳۱ جدول برابر بود. |
| ۱۰ | دقیقاً هشت WorkflowRun موفق متعلق به دو برنامهٔ fixture ثبت شد: هفت اجرای مستقیم موتور با هویت واقعی درخواست‌کننده و یک اجرای واقعی Celery. لاگ‌های مرحله‌ای و checks خصوصی نگهداری شدند. مرورگر واقعی و smoke مستقل مدل نیز بررسی شدند. |

## رابط و مدل

ورود واقعی بازبین فقط پروژهٔ A را نشان داد. صفحهٔ اجرای تیمی، پایان دو مرحله، مسئول‌های واقعی، تحویل نسخهٔ نهایی و تاریخچهٔ سه تلاش بازبین، یک بازخورد و دو نهایی‌سازی PO را نشان داد. نسخهٔ انسانی اولیه و نسخه‌های قبل از بازگشایی باقی بودند. خروج و ورود دوبارهٔ حساب آزمایش، همان پرونده و تاریخچه را برگرداند. تصاویر خصوصی `ui-handoff.png` و `ui-acceptance.png` در `.runtime/kp08/` ثبت شدند؛ اطلاعات ورود چاپ یا وارد Git نشد.

smoke مستقل اتصال شرکت از کانتینر افزونه، با prompt ساختگی و سقف پاسخ ۵۱۲، پاسخ معتبر مدل با HTTP 200 گرفت. اطلاعات اتصال از فایل خصوصی موجود خوانده شد. این شاهد دسترسی واقعی به API مدل است؛ نصب provider و اجرای Workflow دارای LLM بومی یا کیفیت تخصصی ایجنت را اثبات نمی‌کند. چرخهٔ پذیرش بالا کاملاً قطعی و بدون LLM بود.

## حفظ محیط و حدود شواهد

بانک اصلی ابتدا پشتیبان و در بانک تازهٔ آزمون بازیابی شد؛ داده‌های اصلی در طول سناریو مقصد نوشتن نبودند. پس از پذیرش، همهٔ سرویس‌ها به `dify` بازگردانده شدند؛ شمار/hash تمام ستون‌های ۳۱ جدول با مبنا برابر بود. Compose، `make up`، `make doctor`، guard رد بانک اصلی و ۵۴ آزمون سبک `make check` موفق شدند. مرورگر اصلی همان سه پروژهٔ قبلی را بدون alert نشان داد. پشتیبان‌ها، لاگ‌ها، fixture و تصویرها در `.runtime/kp08/` خصوصی باقی‌اند؛ فایل‌های اجرایی upstream تغییر نکردند.

تصویرهای فعلی و منطبق KP-07 بازاستفاده شدند؛ چون سورس API/وب عوض نشد، ساخت کامل کلاینت و رگرسیون‌های موفق KP-07 تکرار نشدند. سناریوی شکست فنی موتور، تغییر مسئول، rollback migration و حفاظت برنامه‌های قدیمی در [پذیرش KP-07](kara-kp07-validation.md) ثبت شده‌اند. KP-08 آزمون ترکیبی افزوده است، نه ادعای پوشش مجدد همهٔ خطاها.

دو اجرای اولیهٔ harness پیش از فراخوانی موتور به دلیل آدرس اشتباه مسیر debug متوقف شدند؛ مسیر آزمون به `workflows/draft/run` اصلاح شد و سناریو کامل عبور کرد. پرونده‌های ناتمام آن‌ها فقط در بانک آزمون باقی‌اند و در هشت اجرای موفق شمرده نشده‌اند. هیچ اصلاح تولیدی برای عبور آزمون لازم نشد. guard پیش از import برنامه، نام بانک اصلی را رد می‌کند و seed موجود را بازنویسی نمی‌کند.

این پذیرش محلی هستهٔ مسیر دستی است. بار زیاد، قطع واقعی Redis/تماس بیرونی، کشتن واقعی worker حین مدل، rollback آثار بیرونی، exactly-once خارجی، Jira و محتوای تخصصی کلاسور آزموده نشده‌اند. orphan با clock قدیمی شبیه‌سازی شد؛ restart API و تحویل Celery واقعی بودند. به‌روزرسانی pointer برنامه fixture بود، نه API جدید بازتعریف ایجنت.

KP-08 برای هستهٔ مسیر دستی محلی پذیرفته است. مرحلهٔ بعد طراحی و ساخت نخستین ایجنت اختصاصی کلاسور با منابع sandbox و آزمون مختص خودش است. اتصال provider/LLM در آن مرحله باید مستقلاً اثبات شود. `clasor-agents` تا شروع همان پیاده‌سازی با `master` هم‌سطح می‌ماند؛ KP-09/10 مربوط به Jira و خودکارسازی بیرونی‌اند و با پذیرش مسیر دستی تکمیل‌شده فرض نمی‌شوند.
