# استقرار کارا روی VDI یا سرور

## مهاجرت بانک در نصب تازه

سرویس یک‌باراجرای `migration` از تصویر اصلی نسخهٔ قفل‌شده و تنظیمات بانک همان محیط استفاده می‌کند. پس از آماده‌شدن PostgreSQL و Redis، فرمان `flask db upgrade` اجرا می‌شود. سرویس‌های API، Worker، Beat و WebSocket فقط پس از خروج موفق آن شروع می‌شوند؛ شکست مهاجرت مانع شروع آن‌ها می‌شود. این ترتیب در مسیر Compose و Make مشترک است و نیازی به حذف بانک یا volume نیست.

سرویس مهاجرت با `extends.file: docker-compose.yaml` صریحاً API فایل upstream را به ارث می‌برد؛ بنابراین هم فایل خصوصی `.runtime/dify/docker/.env` و هم فایل‌های اختیاری محیط API به آن می‌رسند. مسیر نسبی در هر دو راه‌انداز از پوشهٔ Docker upstream حل می‌شود و وابسته به مسیر میزبان نیست. `extends` بدون نام فایل فقط API همان override را می‌بیند و محیط نهایی و ادغام‌شده را منتقل نمی‌کند؛ نتیجه می‌تواند اتصال اشتباه به `localhost:5432` باشد. گزینهٔ `env_file` در سطح `include` برای جای‌گذاری متغیرهای Compose است و جای محیط کانتینر را نمی‌گیرد. تصویر اصلی، فرمان مهاجرت و شرط پایان موفق آن همچنان صریحاً در override تعیین می‌شوند.

بانک پشتیبانی‌شدهٔ این راه‌انداز PostgreSQL است. برای ارتقای محیط دارای داده، ابتدا پشتیبان بگیرید؛ مهاجرت جایگزین پشتیبان‌گیری نیست. `docker compose down` داده‌ها را حفظ می‌کند؛ برای رفع خطای نصب از `down -v` یا پاک‌سازی volume استفاده نکنید.

## تنظیم پایدار شبکه و WebSocket

تنظیمات محیط را در `.env.local` خارج از Git نگه دارید. برای نمونهٔ شبکهٔ داخلی:

```dotenv
DIFY_HTTP_PORT=8080
DIFY_HTTPS_PORT=8443
DIFY_PROJECT_NAME=company-agent-local
DIFY_BIND_ADDRESS=0.0.0.0
DIFY_PUBLIC_URL=http://kara.example.internal:8080
```

دامنهٔ نمونه را با DNS یا IP واقعی میزبان عوض کنید. پیش‌فرض binding فقط `127.0.0.1` است؛ فعال‌کردن شبکه به آدرس عمومی صریح نیاز دارد. آدرس عمومی مسیر، اعتبارنامه یا query ندارد. همهٔ کاربران، از جمله مدیر روی میزبان، از همان آدرس استفاده کنند. برای استقرار دائمی HTTPS و دسترسی شبکهٔ محدود به کاربران موردنظر تنظیم شود.

راه‌انداز، آدرس API و `ws://` یا `wss://` متناظر را از همین origin می‌سازد. اجرای مجدد setup رمزهای خصوصی را حفظ و تنظیمات عمومی را از `.env.local` بازتولید می‌کند؛ `.runtime/compose.env` را دستی ویرایش نکنید. در حالت محلی بدون origin صریح، WebSocket از origin مرورگر پیروی می‌کند؛ `localhost` و `127.0.0.1` نیازمند کوکی ورود همان میزبان‌اند.

محدودیت‌های شبکهٔ شرکت و فایروال میزبان باید اتصال به پورت وب را مجاز کنند. بازکردن صفحه از میزبان، شاهد اتصال VDI همکار نیست. پذیرش تیمی شامل ورود دو حساب مستقل، بازشدن همان فلو، رفع پیام همگام‌سازی و ذخیرهٔ تغییر کنترل‌شده است؛ آزمون کلاینتی این تغییر بنا به درخواست کاربر انجام نشده است.

قالب Nginx نسخهٔ ثابت از DNS داخلی Docker با بازاعتبارسنجی ۳۰ ثانیه‌ای استفاده می‌کند. وابستگی‌های `restart: true` هم در عملیات معمول Compose، Nginx را با تغییر سرویس‌های مرتبط همگام می‌کنند. پس از تعویض دستی کانتینر با `--no-deps` یا باقی‌ماندن اتصال قدیمی، می‌توان دوباره بارگذاری کرد:

```sh
docker compose exec -T nginx nginx -s reload
```

## ساخت در شبکهٔ محدود

این گزینه‌ها عمومی‌اند؛ آدرس داخلی سازمان، گواهی و رمز نباید در Git ثبت شوند:

```dotenv
KARA_NPM_REGISTRY=https://packages.example.internal/repository/npm/
KARA_CA_BUNDLE=/absolute/path/company-ca-bundle.pem
KARA_BOOTSTRAP_IMAGE=python:3.12-bookworm
KARA_TOOLS_IMAGE=python:3.12-bookworm
DIFY_WEAVIATE_IMAGE=semitechnologies/weaviate:1.39.2
```

`KARA_CA_BUNDLE` باید مجموعهٔ PEM مورد اعتماد محیط، شامل زنجیرهٔ CAهای لازم و بدون کلید خصوصی باشد. هنگام setup کانتینری از مسیر مطلق میزبان استفاده کنید. این فایل برای دریافت Git در bootstrap و ساخت وب استفاده می‌شود؛ اعتماد سیستم‌عامل میزبان را عوض نمی‌کند. اعتماد TLS سرویس‌های API و Plugin Daemon برای اتصال واقعی مدل موضوع جداگانه‌ای است و باید مستقل بررسی شود.

اعتبارسنجی bundle با خواندن مستقیم فایل توسط OpenSSL انجام می‌شود؛ وجود توضیحات غیر ASCII در trust store سیستم‌عامل به‌تنهایی دلیل رد فایل نیست. محتوای فایل برای ساخت بدون حذف یا تعویض گواهی‌ها حفظ می‌شود. فایل دارای کلید خصوصی یا PEM نامعتبر همچنان پیش از دسترسی شبکه یا بازنویسی ورودی ساخت رد می‌شود.

Bootstrap از Python کامل با Git همراه استفاده می‌کند؛ ابزار منطقهٔ زمانی وب نیز از تصویر tools کپی می‌شود، بنابراین دریافت apt/apk در این دو مرحله لازم نیست. نسخهٔ pnpm از `packageManager` سورس قفل‌شده با npm نصب می‌شود؛ pnpm و npm از رجیستری تعیین‌شده، lockfile و کنترل صحت بسته‌ها استفاده می‌کنند. بررسی TLS، کنترل مجوز، frozen lockfile و اعتبارسنجی خروجی مدل غیرفعال نمی‌شوند. مخزن داخلی باید همهٔ وابستگی‌های همان lockfile را ارائه کند؛ دسترسی به یک بسته، تضمین ساخت کامل نیست.

برای خواندن تنظیمات image/CA از `.env.local` در Compose اولیه:

```sh
cp .env.local.example .env.local
# Edit .env.local for this environment before setup.
docker compose --env-file .env.local -f compose.setup.yaml run --rm setup
docker compose up -d --build
```

روی لینوکس در صورت نیاز دستورات Docker را با `sudo` اجرا کنید. سرویس‌های زیرساخت و تصاویر باید قبلاً دریافت شده یا از رجیستری مجاز قابل دریافت باشند. جایگزینی رجیستری Weaviate به معنی تغییر نسخهٔ موتور نیست؛ tag و ناشر همان نسخه را بررسی کنید. هیچ‌کدام از این گزینه‌ها محدودیت شبکه را خودکار برطرف نمی‌کنند.

پس از تغییر تنظیمات، setup را دوباره اجرا کنید؛ به بازنویسی دستی فایل‌های تولیدشده نیازی نیست. اگر از دستور `make up` استفاده می‌کنید، همان `.env.local` برای پورت، origin، رجیستری و CA خوانده می‌شود. برای بررسی صرفاً سروری:

```sh
python scripts/local_dify.py doctor --server-only
```

این حالت سلامت API و سرویس‌ها را بررسی می‌کند و تست یا واکشی HTML کلاینت انجام نمی‌دهد. اجرای موفق مدل با آن اثبات نمی‌شود.

## شواهد این اصلاح

اصلاح context کنترل مجوز WebSocket با آزمون سروری پوشش داده شده و hook نصب‌شده در تصویر API جداگانه با context واقعی Flask اجرا شد. مهاجرت روی PostgreSQL موقت از صفر، اجرای مجدد آن و وجود `tenant_account_joins` بررسی شد. نمودار وابستگی هر دو مسیر Compose و Make اعتبارسنجی شد. این بررسی‌ها جای پذیرش کلاینت، تست بار، اجرای واقعی مدل یا بررسی شبکهٔ سازمان را نمی‌گیرند. تست کلاینتی بنا به درخواست کاربر اجرا نشده است. برای اعمال نسخهٔ جدید روی محیط موجود، ابتدا تنظیمات اختصاصی را به `.env.local` منتقل و سپس طبق مسیر آماده‌سازی و راه‌اندازی بالا عمل کنید.

در مسیر cache مرحلهٔ وابستگی، رجیستری و bundle گواهی دوباره از تنظیم جاری اعمال می‌شوند؛ image آمادهٔ قدیمی نباید تنظیم شبکهٔ قبلی را تحمیل کند. فایل CA قبل از دریافت Git یا تولید ورودی ساخت، با parser واقعی PEM بررسی می‌شود؛ فایل خراب یا دارای کلید خصوصی پذیرفته نمی‌شود.

### بازبینی تکمیلی ۳۰ اکتبر ۲۰۲۶

در بازبینی، پذیرش PEM خراب و باقی‌ماندن تنظیم رجیستری یا CA قدیمی در مرحلهٔ وابستگیِ cacheشده اصلاح شد. `make check` با ۷۶ آزمون موفق شد و پیکربندی Compose اصلی و bootstrap معتبر بود. تصویر API تازه در محیط موقت بدون پورت منتشرشده ساخته شد؛ مهاجرت بانک از صفر و پاسخ `pong` API بررسی شد.

سرویس نصب‌شدهٔ همکاری با PostgreSQL و Redis واقعی، دو نشست مصنوعی و emitter ساختگی Socket.IO بررسی شد: درخواست همگام‌سازی هر دو نشست به رهبر رسید، نشست ناشناخته رد شد، منع اجرای فلوهای مدیریت‌شده حفظ شد و context پس از اجرا آزاد شد. این آزمون سرویس سرور است و اتصال واقعی مرورگر یا انتقال WebSocket را اثبات نمی‌کند. در یک Compose موقت دیگر، شکست عمدی سرویس مهاجرت مانع شروع هر چهار نقش وابسته شد؛ نقش‌ها در این آزمون جایگزین ساده داشتند و هدف، بررسی شرط وابستگی Compose بود.

آزمون هم‌زمان چهار نقش واقعی در ماشین Docker محلی با حدود ۴ گیگابایت RAM به کمبود حافظه خورد و موفق تلقی نشد؛ بررسی‌های سروری سپس جداگانه انجام شدند. Worker محیط محلی موجود نیز یک بار راه‌اندازی مجدد شد؛ پس از پاک‌کردن محیط موقت، Worker در حال اجرا و API سالم بود. بنابراین این بازبینی شاهد آزمون بار یا نبود وقفه در محیط مشترک نیست. آزمون و ساخت وب، آزمون کلاینتی و اجرای مدل انجام نشدند؛ VDI نیز با این تغییرات به‌روزرسانی نشد.
