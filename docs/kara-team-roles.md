# نقش‌های کاری اعضای Kara — KP-01

ادمین کل Kara همان حساب اولیهٔ ثبت‌شده در `company_product` است. مدیر پروژه همان عضویت بومی `owner` است. نقش کاری «مالک محصول (PO)» اختیار سراسری یا مالکیت پروژه ایجاد نمی‌کند؛ مدیر پروژه نیز خودکار PO نمی‌شود.

در صفحهٔ **اعضای پروژه**، بخش «نقش‌های کاری اعضا» برای هر عضو فعال چند انتخاب دارد: PO، TL، طراح UI/UX، توسعه‌دهنده و QC. ادمین کل و مدیر همان پروژه می‌توانند آن‌ها را تعیین یا پاک کنند. اعضای دیگر فقط آن‌ها را می‌بینند. سطح دسترسی فنیِ دعوت و ویرایش برنامه‌ها همچنان جداست. نقش کاری به‌تنهایی مجوز اجرای ایجنت نیست؛ آن مجوز در KP-02 اضافه می‌شود.

هر ذخیره نسخهٔ سیاست عضو را افزایش می‌دهد. تغییر هم‌زمان با نسخهٔ قدیمی رد می‌شود و کاربر باید فهرست تازه را دریافت کند. حذف و دعوت مجدد، عضویت تازه و نقش‌های خالی ایجاد می‌کند؛ درخواست متعلق به عضویت پیشین قابل اعمال نیست. حذف از مسیر استاندارد اعضا، نقش‌های آن عضویت را با قید بانک حذف و رویداد ابطال را در همان تراکنش ثبت می‌کند؛ تاریخچهٔ تعیین نقش باقی می‌ماند.

## قرارداد اجرایی

پیشوند: `/console/api/company/projects/<project_id>/team`؛ ورود، نشست، CSRF و فضای فعال بومی لازم‌اند. سمت سرور حساب اقدام‌کننده و اختیار او را تعیین می‌کند. شناسهٔ پروژه یا عضو دیگر مجوز ایجاد نمی‌کند.

| مسیر | رفتار |
| --- | --- |
| `GET /members` | نقش‌ها، شناسهٔ عضویت و revision اعضای همین پروژه |
| `GET /members/<account_id>/roles` | نقش‌های یک عضو همین پروژه |
| `PUT /members/<account_id>/roles` | جایگزینی کامل مجموعهٔ نقش‌ها؛ فقط ادمین کل و مدیر پروژه |

بدنهٔ PUT دقیقاً شامل `roles`، `expected_revision` و `expected_membership_id` است؛ دو مقدار آخر از پاسخ GET گرفته می‌شوند. هدر `Idempotency-Key` یک UUID استاندارد است. مجموعهٔ خالی یعنی برداشتن نقش‌ها. ورودی نامعتبر 400، مجوز ناکافی 403، پروژه/عضو غیرقابل مشاهده 404 و تعارض نسخه، عضویت یا کلید اقدام 409 می‌دهد. تکرار همان اقدام، همان نتیجه را بدون افزایش دوبارهٔ revision یا رویداد تکراری برمی‌گرداند. کلید اقدام برای payload متفاوت قابل استفاده نیست.

## ارتقا و بازگشت

`001_team_roles` در [مهاجرت اجرایی](../infra/api/company_projects/team_migrations.py)، فقط در PostgreSQL و در تراکنش DDL با قفل مشترک runnerها اجرا می‌شود. دفتر قبلی `company_project_schema=1` حفظ می‌شود. دفتر تازه checksum و ترتیب تغییرات را کنترل می‌کند؛ نسخهٔ ناشناخته یا تغییر checksum راه‌اندازی را متوقف می‌کند. داده‌های قبلی به نقش کاری تبدیل نمی‌شوند.

جدول‌های جدید: `company_team_migrations`، `company_team_member_policies`، `company_team_roles` و `company_team_audit_events`. قید مرکب نگاشت پروژه/workspace و قید عضویت بومی، درج نقش در پروژهٔ دیگر را رد می‌کنند. قفل workspace با انتقال مدیر پروژه مشترک است؛ قفل عضویت، تغییر نقش و حذف عضو را هماهنگ می‌کند. تغییر نقش و ثبت رویداد یک تراکنش‌اند.

قبل از ارتقای واقعی، سرویس‌های تغییردهنده متوقف، پشتیبان خصوصی تهیه و در بانک جدا بازیابی شود. برای بازگشت به کد قبلی این گام، جدول‌های افزایشی حذف نشوند؛ نسخهٔ قبلی آن‌ها را نمی‌خواند. این روش برای گام‌های آیندهٔ کنترل اجرای ایجنت قابل تعمیم خودکار نیست. پشتیبان، بانک آزمون و حساب‌های ساختگی وارد Git نمی‌شوند.

## آزمون قابل تکرار

`make check` آزمون‌های آفلاین است. در تصویر API با بانک PostgreSQL جدا، ماژول‌های `company_projects.test_team` و `company_projects.test_team_migrations` را با `python -m unittest` اجرا کنید. نقطهٔ ورود کانتینر باید `/app/api/.venv/bin/python` باشد؛ entrypoint عادی تصویر سرویس را راه‌اندازی می‌کند.

آزمون‌ها چند نقش، مرز پروژه، اختیار ادمین/مدیر، حفظ نقش فنی، حذف و عضویت مجدد، حساب غیرفعال، درخواست تکراری، نسخهٔ قدیمی، اتمی‌بودن audit و مهاجرت تکراری/هم‌زمان/خراب را پوشش می‌دهند. آزمون‌های قبلی `test_access`، `test_inbox`، `test_automations`، `test_catalog`، `test_migration`، `test_readiness` و `company_members.test_access` نیز باید اجرا شوند. آزمون مرورگر و `make doctor` مکمل این‌ها هستند.
