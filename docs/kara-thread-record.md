# سوابق، تصمیم‌ها و شواهد این ترد

تاریخ گردآوری: ۲۰۲۶-۱۰-۲۲. این فهرست مسیر ادامهٔ کار است؛ شرح قرارداد یا شواهد را جایگزین نمی‌کند.
مرز ترد از بررسی مجدد Kara و مدل استفادهٔ تیمی تا پذیرش KP-00/KP-01 و پذیرش روش spec-driven است.
تاریخچه و فایل‌های جاری با هم تطبیق داده شدند؛ گزارش‌های تاریخیِ محیط خاموش، وضعیت زمان خودشان‌اند.

## تصمیم‌های معتبر کاربر

- **نام محصول Kara است**؛ همین پروژه با upstream فنی Dify، نه محصول جدا یا سرویسی کنار آن.
- ادمین کل پروژه و اعضا/مدیر را تعیین می‌کند؛ ادمین کل و مدیر همان پروژه دسترسی‌ها را تنظیم می‌کنند.
- نقش‌های کاری قابل ترکیب‌اند. کاربران مجاز هر ایجنت صریح تعیین می‌شوند؛ نقش کاری حق editor نمی‌سازد.
- تیم چند فلو می‌سازد. درخواست دستی یا از سرویس واسط Jira می‌آید؛ PO واقعی ورود و نسخهٔ فلو را انتخاب می‌کند.
- هر انسان مرحلهٔ خودش را شروع می‌کند، چند دور بازخورد می‌دهد و خروجی معتبر را نهایی می‌کند؛ نفر بعد خودش شروع می‌کند.
- ابتدا هستهٔ عمومی Kara پذیرفته شود، بعد ایجنت‌های اختصاصی کلاسور. Kubernetes فعلاً موضوع این کار نیست.
- برنامه‌ریزی روی master؛ clasor-agents تا ساخت اختصاصی هم‌سطح master و بدون کامیت اختصاصی.
- از این تحویل، توسعهٔ بعدی با Spec Kit و spec/plan/tasks پیش می‌رود؛ پذیرش و مرج TL انسانی می‌ماند.

مرجع مفصل: [مدل کارکرد](kara-operating-model.md)، [قرارداد تیم](kara-team-contract-v1.md)،
[برنامهٔ آمادگی](kara-platform-readiness-plan.md)، [سیاست شاخه‌ها](branches.md).

## شواهد آزمون و محدودیت‌ها

- KP-00: ۵۴ تست مشترک شامل ۳۳ قرارداد؛ Compose config معتبر. در همان زمان محیط خاموش بود و آزمون زنده انجام نشد.
- KP-01 و تکمیل: ۵۴ مشترک + ۴۷ PostgreSQL/API + ۱۴ UI/RTL = **۱۱۵ آزمون تاریخی موفق**؛ HTTP و مرورگر علاوه بر این شمارند.
- backup/restore و migration نقش‌ها روی PostgreSQL، حفظ محتوای ۱۵۱ جدول پیشین و reader قبلی بررسی شد.
- HTTP نشست/CSRF، مجوز manager/root، denial اعضای دیگر، replay/conflict و دو PUT هم‌زمان بررسی شد.
- در مرورگر production، نقش‌ها پس از reload ماندند، نقش بومی تغییر نکرد؛ normal کنترل read-only داشت.
- build نهایی کامل از Dockerfile مشترک با وابستگی‌های cache‌شده و online installers انجام شد؛ Node/lock/TLS عوض نشدند. تلاش runtime جایگزین کنار گذاشته شد.
- تصویر نهایی web `d31f6cb2a7f9` با fingerprint ثبت‌شده در closeout روی بانک اصلی smoke شد؛ عنوان «پروژه‌ها - Kara»، wordmark و favicon درست بودند.
- doctor و Celery ping موفق؛ بانک اصلی سه پروژه، صفر role کاری/حساب synthetic KP-01 و یک trigger متوقف داشت. تغییرات تست فقط روی بانک بازیابی‌شده بودند.
- در این مراحل LLM فراخوانی نشد؛ full fresh install مدیر و restore کامل تازه در closeout تکرار نشدند. پذیرش چندمرحله‌ای هسته در KP-08 آینده است.
- نتایج بالا گزارش تاریخ تحویل قبلی‌اند؛ نسخهٔ جدید runtime باید آزمون مرتبط خودش را دوباره اجرا کند. بررسی کنونی Spec Kit فقط ابزار/مستندات است و build سنگین کلاینت را بی‌دلیل تکرار نمی‌کند.

## مدارک خصوصی و بازتولید

`.runtime/kp01/` شامل backup قبل، hashهای baseline، restore override و harness/نشست‌های تست است.
`.runtime/kp01-closeout/` شامل لاگ ساخت کامل آفلاین، تلاش آنلاین، ساخت نهایی و تصاویر نهایی است.
نام و حدود هر شاهد در closeout ثبت است. این مسیرها Git نیستند و ممکن است روی دستگاه دیگر موجود نباشند؛
credential و دادهٔ خام از آن‌ها به مستندات مشترک منتقل نمی‌شوند.

`.runtime/spec-kit/` محیط ابزار، cache نصب و JSON helperهای هر KP را نگه می‌دارد. روش بازتولید و تفاوت
دستور shell با skill ایجنت در راهنمای spec-driven و execution.md هر بسته ثبت شده است.

## تحویل و ادامه

KP-00/KP-01 پذیرفته‌اند. هیچ KP-02..10 یا ایجنت کلاسور در این تحویل پیاده نشده است.
[spec KP-02](../specs/002-agent-access/spec.md) اولین بستهٔ قابل بررسی برای شروع اجرایی بعدی است.
قبل از اجرای بسته‌های دورتر، طرح آن‌ها با قرارداد نهایی پیشینیان reconcile شود. برای Jira نمونهٔ واقعی
سرویس و اتصال معتبر لازم است؛ نبود آن با پاسخ فرضی پوشانده نمی‌شود.
