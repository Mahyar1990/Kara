# گزارش پذیرش KP-03

۲۲ اکتبر ۲۰۲۶ — فلوهای تیمی نسخه‌دار. [قرارداد و API](kara-team-flows.md) جزئیات اختیار، اتصال مراحل، migration و تاریخچه را ثبت می‌کند.

## بررسی‌های متمرکز

- ۱۷ آزمون PostgreSQL: ۱۰ آزمون فلو، ۵ آزمون migration و دو رگرسیون حساس KP-02؛ همگی موفق. شامل اختیار فنی، دو فلو، snapshot قبلی، پیش‌نویس ناقص، منبع/خروجی نامعتبر، چرخه، مجوز لغوشده، عضویت قدیمی، نقش تصمیم، idempotency، نام یکتا، بایگانی و منع UPDATE/DELETE نسخه در بانک.
- HTTP واقعی روی بانک جدا `kara_kp01_restore`: دو فلو با مراحل متفاوت منتشر شدند؛ ویرایش و انتشار نسخهٔ دوم، محتوای نسخهٔ اول را تغییر نداد. عضو عادی نسخهٔ منتشرشده را خواند و draft را ندید.
- دو انتشار هم‌زمان با revision یکسان ۲۰۰ و ۴۰۹ گرفتند. CSRF ناقص، پروژه/ایجنت خارجی، چرخه و انتشار ناقص رد شدند؛ بایگانی تاریخچه را حفظ کرد.
- شمار WorkflowRun پیش و پس از انتشار/ویرایش یکسان بود؛ فلو هیچ ایجنتی را خودکار اجرا نکرد.
- خطای TypeScript جابه‌جایی مرحله با بررسی حدود آرایه اصلاح شد؛ سپس TypeScript، ۱۴ تست رابط و ساخت کامل ۴۷ مرحله‌ای کلاینت با وابستگی قفل‌شده موفق شدند. مرورگر نهایی نیز موفق بود: مدیر فلو دو مرحله‌ای با اجراکننده، نهایی‌کننده و اتصال خروجی ساخت و دو نسخه منتشر کرد. عضو عادی نسخهٔ اول را با محتوای قبلی دید و دکمهٔ ساخت/ویرایش نداشت. تطبیق متمرکز بانک، دو نسخه، digest متفاوت، افراد انتخاب‌شده و اتصال ثابت مرحلهٔ دوم به کلید مرحلهٔ اول را تأیید کرد. تصویر خصوصی `ui-version-history.png` شاهد رابط است.
- پس از آزمون‌ها، سرویس‌ها به بانک اصلی `dify` برگشتند و migration سوم روی آن اعمال شد. مقایسهٔ تعداد و hash ردیف‌های ۱۷ جدول قبلی، حفظ کامل داده‌های آن‌ها را تأیید کرد. `make up` و `make doctor` موفق بودند؛ صفحهٔ اصلی پروژه‌ها پس از بارگذاری مجدد، سه پیوند پروژه و بدون پیام خطا نمایش داده شد.
- `make check` با ۵۴ آزمون موفق پایان یافت. مجموعه‌های موفق بدون تغییر مرتبط دوباره اجرا نشدند.

گزارش‌های طولانی، fixture دارای رمز، backup و تصویر مرورگر در `.runtime/kp03/` خصوصی می‌مانند. مجموعهٔ کامل API تکرار نشد؛ فقط آزمون‌های مرتبط و بررسی HTTP اجرا شدند.

## حدود پذیرش

این گام تعریف، انتشار، خواندن نسخهٔ دقیق و بایگانی را می‌سازد. هنوز پروندهٔ درحال‌اجرا یا تصمیم ورود ایجاد نمی‌شود؛ ثابت‌ماندن ارجاع اجرای آینده با API نسخهٔ دقیق و snapshot تغییرناپذیر فراهم شده، اما سناریوی پروندهٔ زنده مربوط به KP-04/05 است. اعتبارسنجی نوع خروجی پویا و مجوز تازه هنگام اجرای مراحل نیز در همان اتصال لازم است. پذیرش محلی Community و بدون فراخوانی مدل است.

## ادامه

گام بعد KP-04: درخواست دستی نسخه‌دار و تصمیم PO برای انتخاب و ورود به نسخهٔ دقیق یک فلو؛ بدون شروع خودکار مراحل یا جعل تأیید انسانی.
