# قرارداد نسخهٔ اول همکاری تیمی Kara

نسخهٔ قرارداد `1.0.0` — ۲۱ اکتبر ۲۰۲۶ — خروجی اجرایی KP-00.

این سند و [مرجع قابل اجرا](../kara_contracts/team.py) قرارداد دسترسی، نسخه و گذار مرحله را تثبیت می‌کنند. مرجع، مستقل از وب، مدل و بانک داده است و هنوز به API یا تصویر اجرایی Kara متصل نشده است. حساب‌ها، مجوزهای فعلی، فرم‌های منتظر و دادهٔ زنده تغییر نمی‌کنند. اتصال به حساب واقعی و ذخیره‌سازی در KP-01 تا KP-07 انجام می‌شود.

## ۱. مبنا و مرز اعتماد

مبنای شروع `master` در `58e744b` است؛ ۲۱ آزمون بستر در آن وجود دارد. محیط محلی خاموش است و مبنای عملیاتیِ مدل/پایگاه داده هنوز تأیید نشده است. این محدودیت مانع تثبیت و آزمون آفلاین قرارداد نیست؛ قبل از پذیرش KP-08 بررسی زنده لازم است.

حساب و وضعیت فعال آن از نشست معتبر و سرور، عضویت و نقش‌ها از مخزن پروژه، مجوز ایجنت از مخزن سیاست، مجوز بومی از resolver موجود و تصمیم از محل ثبت قابل اعتماد دریافت شوند. پارامتر user_id، متن مدل، role داخل JSON، نام فرد، لینک عمومی و کلید سرویس شاهد هویت انسان نیستند.

اشیای Actor، ActionContext و IntakeDecision در مرجع، امضای دیجیتال یا احراز هویت نیستند. ساخت یک نمونهٔ Python یا تطبیق هش، صحت منشأ تصمیم را ثابت نمی‌کند. API نباید این اشیا، system، guards یا platform_admin را مستقیماً از دادهٔ کاربر بسازد. ActionContext برای هر اقدام از اطلاعات تازهٔ همان تراکنش تهیه می‌شود؛ مجوز ذخیره‌شدهٔ اقدام قبلی قابل استفادهٔ مجدد نیست.

## ۲. هویت‌ها، نقش‌ها و مجوزها

- ادمین کل، همان اختیار سراسری موجود است؛ نام فنی قدیمی `is_product_owner` در دورهٔ سازگاری حفظ می‌شود.
- مدیر پروژه در نسخهٔ اول به owner بومی همان پروژه نگاشت می‌شود. admin بومی به‌تنهایی اختیار مدیریت اعضا یا اعطای مجوز ندارد.
- نقش‌های کاری `po`، `tl`، `designer`، `developer` و `qc` مستقل از نقش بومی‌اند و می‌توانند برای یک حساب ترکیب شوند.
- نقش کاری به‌تنهایی مجوز اجرای ایجنت نمی‌دهد. grant به ترکیب دقیق پروژه، workspace، ایجنت و حساب تعلق دارد.
- تمام اقدام‌های عملیاتی به حساب و عضویت فعال همان پروژه نیاز دارند. مدیریت دسترسی توسط ادمین کل استثنای مدیریتیِ دارای ثبت رویداد است؛ حق اجرا و تصمیم محصولی از آن استنتاج نمی‌شود.

| اقدام | شرط قرارداد |
| --- | --- |
| `view` | grant خواندن یا یکی از اختیارات ایجنت؛ فقط اطلاعات حداقلی نقش و قرارداد ورودی، بدون لاگ خصوصی/اعتبارنامه |
| `run` | grant صریح run، عضویت فعال و نسخهٔ منتشرشده |
| `feedback` | grant صریح feedback؛ run آن را خودکار ایجاد نمی‌کند. فرم ساده می‌تواند هر دو را یکجا اعطا کند. |
| `finalize` | grant صریح finalize، شخص نهایی‌کنندهٔ تعیین‌شده، نقش تصمیم لازم در صورت تعریف و خروجی معتبر همان مرحله/ورودی |
| `edit_definition` | هم grant ویرایشِ ایجنت تحت کنترل و هم مجوز بومی ویرایش |
| `publish_definition` | هم grant انتشارِ ایجنت تحت کنترل و هم مجوز بومی انتشار |
| `manage_access` | ادمین کل فعال یا مدیر همان پروژه؛ با grant ایجنت قابل واگذاری به دیگران نیست. |
| ثبت درخواست | هر عضو فعال همان پروژه می‌تواند پیش‌نویس بسازد؛ این اقدام درخواست را وارد تولید نمی‌کند. |
| تأیید ورود | فقط حساب فعال با نقش PO همان پروژه؛ عنوان مدیریتی کافی نیست. |
| تنظیم نقش کاری/تعویض مسئول | ادمین کل یا مدیر همان پروژه؛ تغییر همراه علت و رویداد ثبت شود. |
| تعریف فلو | اعضای دارای نقش بومی owner/admin/editor در همان پروژه، تابع مجوزهای واقعی ساخت/انتشار |
| لغو پرونده | ادمین کل، مدیر پروژه یا PO همان پروژه با علت؛ مجوز پذیرش یا مرج ایجاد نمی‌کند. |

سیاست دو شرطی edit/publish مخصوص ایجنت‌هایی است که در همکاری تیمی مدیریت می‌شوند؛ برنامه‌های قدیمی و کنترل‌های بومی در KP-00 تغییر نمی‌کنند. در اتصال KP-02، سازگاری برنامه‌های قدیمی و جلوگیری از دورزدن مسیر اجرا جدا آزموده می‌شوند. تخصیص نقش/مجوز به خود توسط مدیر، یک تغییر قابل حسابرسی است؛ عنوان مدیر به‌خودی‌خود جای آن تغییر را نمی‌گیرد.

## ۳. نسخه و تصمیم

VersionRef شامل `project_id`، `workspace_id`، `entity_id`، revision صحیح مثبت و digest محتوای دقیق است. UUIDها به قالب canonical و زمان‌ها با timezone ذخیره شوند. revision بولی، اعشاری، صفر و رشته پذیرفته نمی‌شود.

digest با SHA-256 روی JSON پایدار با کلیدهای مرتب، UTF-8 و بدون فاصلهٔ اضافهٔ serialization محاسبه می‌شود؛ متن کاربر خودکار trim یا خلاصه نمی‌شود. انواع JSON صریح پذیرفته می‌شوند؛ NaN، کلید غیرمتنی و تبدیل ضمنی tuple مجاز نیستند. در هشِ اتصال ورودی، نسخهٔ درخواست، فلو، نسخهٔ ایجنت/قرارداد، artifactهای مصرفی و شناسه/نسخهٔ دور بازخورد حضور داشته باشند. هش محتوا، امضا یا مجوز دسترسی نیست.

IntakeDecision از محل معتبر خوانده و به درخواست و FlowVersion دقیق متصل می‌شود. تصمیم فقط وقتی معتبر است که outcome=approved، mode=real، لغونشده، در زمان معتبر و با شناسه/نسخه/هش دقیق هر دو مرجع مطابق باشد. تصمیم آزمایشی، رد، تعویق و درخواست اصلاح مجوز آغاز نمی‌دهند. تغییر محتوا با همان شماره نیز تصمیم قبلی را بی‌اعتبار می‌کند.

اختیار PO هنگام ثبت تصمیم در سرور کنترل می‌شود؛ مرجع تطبیق نسخه آن را دوباره احراز هویت نمی‌کند. حذف نقش یک فرد، سابقهٔ تصمیم او را پاک نمی‌کند؛ ابطال تصمیم رکورد/رویداد صریح دارد. اقدام جدیدِ آن فرد همیشه با مجوز فعلی بررسی می‌شود. تأیید ورود با تأیید نهایی نیازمندی، پذیرش، انتشار و مرج یکی نیست و هر نوع تصمیم موضوع و مرجع خودش را دارد.

## ۴. حالات و گذار مرحله

حالات: blocked، ready، running، awaiting_feedback، awaiting_decision، completed، failed، stale و cancelled. هر مرحله یک `revision` برای کنترل هم‌زمانی دارد؛ این شماره با revision محتوای خروجی یا شمارهٔ اجرای مدل متفاوت است.

| مبدأ / رویداد | مقصد | عامل مجاز و شروط |
| --- | --- | --- |
| blocked / unblock | ready | سیستم، پس از نهایی‌شدن پیش‌نیاز، اعتبار تصمیم ورود و تازگی ورودی |
| ready / start | running | عضو دارای run؛ شروط بالا و شناسهٔ تلاش تازه |
| running / attempt_succeeded | awaiting_feedback | callback داخلیِ تلاش فعال، خروجی دارای قرارداد معتبر |
| running / attempt_failed | failed | callback داخلیِ همان تلاش فعال |
| awaiting_feedback یا awaiting_decision / feedback | ready | عضو دارای feedback؛ ثبت دور تازه و اتصال ورودی با هش تازه |
| awaiting_feedback / request_decision | awaiting_decision | عضو دارای feedback؛ خروجی معتبر و ورودی/تصمیم معتبر |
| awaiting_decision / finalize | completed | مجوز finalize، نهایی‌کننده و نقش لازم، خروجی منتخب همان مرحله و همان اتصال ورودی |
| failed / retry | ready | عضو دارای run؛ پیش‌نیاز و تصمیم و ورودی معتبر؛ retry فنی خودکار در این قرارداد پیاده نشده است. |
| هر حالت به‌جز stale/cancelled / invalidate | stale | سیستم با شاهد تغییر ورودی مصرف‌شده؛ حتی خروجی completed حفظ و stale می‌شود. |
| stale / revalidate | ready | عضو دارای run؛ اتصال ورودی تازه و شروط ورود؛ تأیید قبلی خروجی بازنمی‌گردد. |
| هر حالت به‌جز completed/cancelled / cancel | cancelled | اختیار لغو پرونده؛ تاریخچه حفظ شود. |

شناسهٔ Workflow منتشرشده در خود مرحله ثابت است؛ ActionContext باید علاوه بر همان پروژه و ایجنت، همین workflow_id را داشته باشد. اشاره به نسخهٔ جدید همان ایجنت رد می‌شود.

قاعدهٔ مشترک: expected_revision باید با revision فعلی یکی باشد؛ گذار مجاز، revision را یک واحد زیاد می‌کند. گذار تعریف‌نشده رد می‌شود. در running دقیقاً یک active_attempt_id وجود دارد؛ خروج از آن حالت این اشاره‌گر را خالی می‌کند، اما رکورد تلاش حذف نمی‌شود. نتیجهٔ تلاش قدیمی، callback پس از لغو و سیستمِ مدعی نهایی‌سازی انسانی رد می‌شوند.

Artifact منتخب با scope، شناسهٔ مرحله و input_digest تطبیق داده می‌شود. پس از بازخورد یا تجدید ورودی، خروجی دور قبلی برای نهایی‌سازی کافی نیست. موفقیت اجرای مدل فقط پیش‌نویس می‌سازد؛ مرحلهٔ بعد پس از تصمیم معتبر ready می‌شود و اجرای آن با فرد مجاز همان مرحله است.

مرجع Python تنها پیشنهاد گذار را روی مقدار immutable محاسبه می‌کند. قفل پایگاه داده، CAS واقعی، idempotency، بررسی رابطهٔ artifact با رکورد تلاش و اعتبارسنجی معنایی محتوا بر عهدهٔ آداپتر/تراکنش مراحل بعد است. دو فراخوانی روی یک snapshot قدیمی را این مرجع به‌تنهایی سریالی نمی‌کند. نتیجهٔ آزمون آفلاین به‌عنوان حل هم‌زمانی پایگاه داده گزارش نشود.

## ۵. شکل هدف API برای مراحل بعد

این مسیرها قرارداد هدف نسخهٔ اول‌اند. مسیر نقش‌های عضو و فهرست `/members` در KP-01 فعال شدند؛ در KP-02 مسیرهای تعریف ایجنت، مجوزها و تلاش اجرای مستقل نیز طبق [قرارداد اجرایی ایجنت‌های تیم](kara-team-agents.md) اضافه شده‌اند. مسیرهای پیش‌نویس، انتشار و نسخهٔ دقیق فلو نیز در KP-03 طبق [قرارداد فلوهای تیمی](kara-team-flows.md) اضافه شده‌اند؛ ثبت/اصلاح درخواست و تصمیم ورود PO نیز در KP-04 طبق [قرارداد درخواست](kara-team-requests.md) اضافه شده‌اند؛ اجرای مرحله، بازخورد، ویرایش انسانی و نهایی‌سازی در KP-05 طبق [قرارداد اجرایی مرحله](kara-team-stages.md) متصل شده‌اند؛ کارتابل اقدام و تحویل منتخب در KP-06 طبق [قرارداد کارتابل](kara-team-inbox.md) متصل شده‌اند؛ لغو و بازاعتبارسنجی گسترده همچنان مربوط به KP-07 است. همگی زیر `/console/api/company/projects/<project_id>/team`، با نشست/CSRF موجود و بررسی workspace فعال تعریف می‌شوند؛ جدول‌های اصلی حساب و نشست جایگزین نمی‌شوند.

| مسیر نسبی | اقدام |
| --- | --- |
| `/members/<account_id>/roles` | GET/PUT نقش‌های کاری؛ فقط مدیر مجاز بنویسد. |
| `/agents` و `/agents/<agent_id>/grants` | تعریف نقش قابل اجرا و تنظیم حساب‌های مجاز |
| `/flows` و `/flows/<flow_id>/versions` | تعریف و انتشار نسخهٔ فلو تیمی |
| `/requests` و `/requests/<request_id>/revisions` | ثبت/خواندن درخواست و اصلاح نسخه‌دار |
| `/requests/<request_id>/intake-decisions` | ثبت تصمیم PO و FlowVersion منتخب |
| `/actions?page=1` | GET اقدام‌های آمادهٔ همان عضو، با مجوز جاری و بدون تغییر وضعیت؛ KP-06 |
| `/instances/<instance_id>/stages/<stage_id>` | وضعیت و ورودی‌های مجاز مرحله |
| مسیر مرحله + `/attempts`، `/feedback`، `/finalizations` | شروع، بازخورد و نهایی‌سازی با اقدام صریح |
| `/instances/<instance_id>/cancellations` | لغو با اختیار و علت ثبت‌شده |

اکشن‌های تغییردهنده در بدنه `expected_revision` با نوع integer صحیح مثبت و در header، `Idempotency-Key` با UUID canonical دریافت کنند. نبود هر کدام خطای 400 و تعارض نسخه خطای 409 است؛ شناسهٔ هدف از مسیر گرفته و در هش payload اقدام وارد شود. برای نقش‌های کاری، `expected_membership_id` نیز از پاسخ خواندن گرفته شود تا حذف و عضویت مجدد درخواست قدیمی را بی‌اثر کند. تکرار همان کلید با payload یکسان همان نتیجه را بدهد و با payload متفاوت 409 بدهد. شروع کار باید به همان نسخهٔ منتشرشده متصل باشد، نه آخرین draft یا مقدار جدید `app.workflow_id`.

ورودی کاربر شامل متن و ارجاع انتخابی است؛ actor، guards، state، تصمیم‌گیرنده، hashهای معتبر و flags مجوز از سرور می‌آیند. بدنهٔ پاسخ محدود به دادهٔ مجاز همان اقدام باشد. شناسهٔ خارج پروژه 404، نبود اختیار 403، قالب ورودی نادرست 400، تعارض نسخه/اقدام 409 و نقص پیش‌نیاز معنایی 422 شود. ContractError داخلی به کد/پیام مناسب تبدیل و جزییات خصوصی یا توکن به پاسخ افزوده نشود.

## ۶. آزمون و معیار تحویل

[نمونه‌های دسترسی](../fixtures/kara-contracts/access-cases.json) صریحاً ساختگی‌اند. [آزمون‌های قرارداد](../scripts/test_team_contract.py) جداسازی حساب/پروژه/workspace/ایجنت، ترکیب نقش، لغو مجوز، تصمیم آزمایشی/قدیمی، شرط خطا و انقضا، چند دور اصلاح، نهایی‌کننده، نتیجهٔ دیررس و تحویل بین دو نقش را بررسی می‌کنند. این‌ها تست آداپتر حساب، API یا مدل نیستند.

اجرای مستقل:

```sh
.venv/bin/python -m unittest discover -s scripts -p 'test_team_contract.py' -v
make check
```

این قرارداد dependency تازه‌ای اضافه نمی‌کند و در ساخت API کپی یا import نشده است. برای به‌کارگیری در runtime، اتصال قابل بررسی و تست یکپارچگی لازم است. مدل داده و طرح ارتقای متناظر در [مدل داده و migration](kara-team-data-migration.md) ثبت شده‌اند. این دو سند با هم خروجی آفلاین KP-00 هستند؛ مبنای محیط روشن و اتصال نقش‌های کاری به حساب واقعی در KP-01 بررسی شدند. وضعیت و موارد باز در [بازبینی دو گام](kara-kp00-kp01-review.md) آمده‌اند؛ اتصال مرجع گذار مرحله به runtime همچنان مربوط به گام‌های بعد است.
