# گزارش پذیرش KP-05

۲۲ اکتبر ۲۰۲۶ — اجرای صریح مرحله، بازخورد و نهایی‌سازی انسانی. [قرارداد و API](kara-team-stages.md).

## بررسی متمرکز

- ۲۱ آزمون PostgreSQL در یک نوبت موفق شدند: ۱۳ آزمون مرحله، پنج آزمون migration و سه رگرسیون حساس اجرای قبلی و نسخهٔ درخواست. شامل اختیار مسئول واقعی، چند دور، خروجی قدیمی، نقش لازم، منبع تغییرکرده، retry، لغو مجوز و callback قدیمی، idempotency/CAS، تاریخچهٔ immutable و جداسازی پروژه/محتوا.
- HTTP واقعی روی بانک جدا `kara_kp01_restore`: چهار WorkflowRun قطعی و واقعی با حساب normal اجرا شد؛ سه تلاش مرحلهٔ اول و یک تلاش مرحلهٔ دوم. دو پیام بازخورد به ورودی واقعی موتور رسیدند؛ متن پایه و مؤثر، دورها و خروجی‌ها حفظ شدند. ویرایش انسانی با حساب مدیر و kind=human ثبت شد؛ فقط Artifact منتخب پس از تصمیم واقعی حساب نهایی‌کننده به مرحلهٔ بعد رسید. ایجاد/بازخورد/نهایی‌سازی، اجرای بعدی را خودکار آغاز نکردند.
- تعارض دو run هم‌زمان ۲۰۲/۴۰۹ و دو finalize هم‌زمان ۲۰۰/۴۰۹ بود. replay تلاش را دوباره اجرا نکرد. نقش/مسئول، پروژه و CSRF بررسی شدند. هیچ LLM فراخوانی نشد؛ فرایندها فقط ورودی را بازمی‌گردانند و نمونه‌ها ساختگی‌اند.
- ۵۴ آزمون `make check` موفق بودند. SQL migrationهای ۰۰۱ تا ۰۰۴ تغییر نکرده است.

- دو آزمون مرزی جدید نیز موفق شدند: تلاش مستقلِ ازپیش‌ساخته‌شده به مرحله وصل نمی‌شود؛ بایگانی فلو ایجاد اجرای تازه را می‌بندد و اجرای موجود را حفظ می‌کند. پس از تکمیل فیلتر فهرست، فقط آزمون بایگانی دوباره اجرا و موفق شد.

- TypeScript، ۱۴ تست رابط/منو و ساخت کامل ۴۷ مرحله‌ای کلاینت با کش محلی و lockfile ثابت موفق شدند؛ dependency جدید اضافه نشد.
- مرورگر با دو حساب آزمایشی: عضو normal اجرای تیمی ایجاد کرد، دو بار مرحله را صریح اجرا کرد، یک بازخورد با ورودی متنی مشخص فرستاد، نسخهٔ انسانی سوم را ساخت و همان نسخه را برای تصمیم انتخاب کرد. او حق نهایی‌سازی نداشت؛ حساب نهایی‌کننده وارد شد و با علت، خروجی منتخب را نهایی کرد. مرحلهٔ بعد فقط ready شد.
- تطبیق بانک با مرورگر: دو WorkflowRun واقعی با حساب و Workflow ثابت، یک بازخورد رسیده به ورودی مؤثر، سه Artifact شامل یک ویرایش انسانی با parent درست، تصمیم حساب نفر دوم و ورودی مرحلهٔ بعد برابر Artifact منتخب تأیید شدند. هیچ تلاش خودکاری برای مرحلهٔ بعد وجود نداشت. تصویر خصوصی `.runtime/kp05/ui-stage-finalization.png` شاهد رابط است؛ حساب آزمایشی خارج و تب موقت بسته شد.

- backup بانک اصلی در بانک موقت مستقل restore و migration پنجم روی آن اجرا شد؛ تعداد/hash ردیف‌های ۲۳ جدول قبلی با snapshot پیش از تغییر برابر بود. بانک موقت همین آزمون حذف شد.
- سرویس‌ها به بانک اصلی `dify` برگشتند؛ migration پنجم اعمال شد و مقایسهٔ همان ۲۳ جدول همچنان برابر بود. شش جدول جدید مرحله خالی‌اند و دادهٔ ساختگی وارد بانک اصلی نشده است. Compose، `make up` و `make doctor` موفق بودند. تب اصلی کاربر تازه شد و هر سه پروژه بدون پیام خطا دیده شدند.

## حدود پذیرش

کارتابل شخصی، بازیابی worker از دست‌رفته، لغو و تعویض مسئول و cascade بازاعتبارسنجی مربوط به KP-06/07 هستند. این گام ادامهٔ ورودی/تصمیم نامعتبر را می‌بندد و تاریخچه را حفظ می‌کند؛ ادعای exactly-once برای اثر بیرونی یا آزمون Enterprise/مدل ندارد. فرمت ورودی فایل بومی هنوز در قرارداد ایجنت‌های فعلی پشتیبانی نمی‌شود؛ فایل درخواست به انسان مجاز ارائه می‌شود.

گزارش‌های بلند، fixture، backup و تصویر مرورگر در `.runtime/kp05/` خصوصی و خارج Git هستند؛ مجموعهٔ کامل API بدون ضرورت تکرار نشد.

KP-06: کارتابل «اقدام‌های من»، مسئول و وضعیت جاری درخواست، تحویل خروجی منتخب و پیگیری کل فرایند برای هر نقش با حداقل دسترسی لازم.
