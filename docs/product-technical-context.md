# آماده‌سازی زمینهٔ فنی محلی

برنامه‌ریز برای پیشنهاد تسک‌های قابل بررسی به اطلاعات واقعی مخزن نیاز دارد. هر نفر مسیرهای سیستم خودش را معرفی می‌کند؛ مسیر شخصی، نسخه‌های بررسی‌شده و گزارش زمینه در `.runtime/products/<product-id>/` نگهداری می‌شوند و وارد Git نمی‌شوند.

## ساخت گزارش اولیه

```sh
python3 scripts/prepare_product_context.py --product klassor \
  --backend '/path/to/backend' --client '/path/to/client' --ref origin/sandbox
```

مسیرها باید پوشهٔ ریشهٔ مخزن باشند. گزینه‌های `--newman` و `--playwright` مسیر مخزنهای تست جدا را می‌گیرند. ارائه‌نشدن مسیر، با وضعیت نامشخص باقی می‌ماند و به معنای بی‌نیازی از تست نیست.

طبق دستور مالک محصول، مبنای هر چهار مخزن کلاسور شاخهٔ `sandbox` است. ابزار برای کلاسور به‌صورت پیش‌فرض `origin/sandbox` را انتخاب می‌کند؛ مرجع دقیق و commit آن ثبت می‌شوند. این مرجع، نسخهٔ ثبت‌شدهٔ محلی شاخهٔ شرکت است و بدون fetch، تازگی آن نسبت به GitLab تأیید نمی‌شود. منابع از همان commit خوانده می‌شوند؛ شاخهٔ کاری توسعه‌دهنده جابه‌جا نمی‌شود و فایل‌های پوشه مبنای این بررسی نیستند. اگر مرجع موجود نباشد، عملیات متوقف می‌شود و به شاخهٔ دیگری برنمی‌گردد.

اگر فناوری مورد انتظار بک‌اند مشخص است، `--expected-backend nestjs` یا `--expected-backend express` را اضافه کنید. ابزار اختلاف فناوری مورد انتظار با وابستگی مستقیم را گزارش می‌کند؛ رفع اختلاف و تعیین مبنای صحیح با مالک محصول است.

برای به‌روزرسانی همان مسیرهای خصوصی:

```sh
python3 scripts/prepare_product_context.py --product klassor --refresh
```

می‌توان مسیر جدید مخزن تست یا فناوری مورد انتظار را همراه `--refresh` اضافه کرد. همهٔ چهار نقش در گزارش وجود دارند؛ مخزن معرفی‌نشده صریح مشخص است.

برای تغییر محل کلاینت، `--refresh --client '/new/path/to/client'` را اجرا کنید؛ سپس بستهٔ دانش را دوباره بسازید. مسیر فقط در تنظیم خصوصی ذخیره می‌شود و به مستندات مشترک یا تاریخچهٔ Git اضافه نمی‌شود.

## قواعد مخزن و مستندات محصول

```sh
python3 scripts/prepare_product_knowledge.py --product klassor
```

این مرحله متن `AGENTS.md` و `PROJECT_MAP.md` بک‌اند و کلاینت، مستندات متنی در هر دو مسیر `doc/` و `docs/`، و مهارت‌ها و مراجع متنی در `.agents/skills/` را از commit ثبت‌شده در گزارش فنی دریافت می‌کند. constitution مخزن، اگر موجود باشد، هم در فهرست قرار می‌گیرد. شاخه یا فایل‌های پوشه جای نسخهٔ ثبت‌شده را نمی‌گیرند. پس از تغییر مسیر یا به‌روزرسانی نسخهٔ مبنا، ابتدا گزارش فنی و سپس دانش دوباره ساخته شوند.

خروجی‌های خصوصی `knowledge-catalog.local.json` و `knowledge-summary.local.md` شامل متن پالایش‌شده، فهرست منابع، نوع، مسیر داخل مخزن، commit و هش محتوا هستند. `AGENTS.md` قواعد توسعهٔ همان مخزن است؛ `PROJECT_MAP.md` برای مسیر‌یابی و اطلاعات پروژه و مستندات برای قراردادها و شواهد فنی استفاده می‌شوند. مهارت‌ها فقط فهرست می‌شوند؛ اجرای هیچ مهارت یا فرمانی در این مرحله انجام نمی‌شود.

فایل‌های Markdown/MDX و متن UTF-8 دریافت می‌شوند. سایر قالب‌ها، از جمله فایل‌های Excel، فقط با شناسهٔ Git در فهرست می‌آیند و متنشان استخراج نمی‌شود. سقف هر متن ۲ میلیون بایت و سقف کل متن‌ها ۲۵ میلیون بایت است. منبع حذف‌شده به دلیل اندازه، قالب، نبود دسترسی یا کلید خصوصی، صریح ثبت می‌شود؛ گزارش نباید پوشش کامل آن منبع را ادعا کند.

نمونه‌های Bearer و مقادیر مشخص رمز/توکن پالایش می‌شوند؛ میزبان و query آدرس‌های کامل حذف می‌شوند و مسیر API باقی می‌ماند. فایل دارای کلید یا گواهی صادر نمی‌شود. این پالایش جامع نیست؛ بررسی انسانی داده‌ها پیش از ارسال به مدل همچنان لازم است. ابزار چیزی به مدل یا Dify ارسال نمی‌کند و این دانش خارج از Git، با همان مجوزهای خصوصی گزارش فنی، ذخیره می‌شود.

## ورودی مشترک نقش‌های توسعه

```sh
python3 scripts/build_product_agent_context.py --product klassor
```

`agent-context.local.json` و نمای فارسی `agent-context.local.md` قواعد هر دو مخزن، مقدمه و فهرست بخش‌های نقشهٔ پروژه، نمایهٔ مستندات و فهرست منابع قابل انتخاب را دارند. متن همهٔ مستندات یا مهارت‌ها به بستهٔ هر اجرا وارد نمی‌شود. گزینهٔ `--role backend` یا `--role client` دامنه را محدود می‌کند؛ بدون آن هر دو مخزن انتخاب می‌شوند.

برای یافتن منبع مرتبط، جست‌وجوی محلی روی نام و متن انجام می‌شود؛ نتیجه، پیشنهاد انتخاب است و بررسی ارتباط منبع همچنان لازم است:

```sh
python3 scripts/build_product_agent_context.py --product klassor --role backend --search 'موضوع یا نام API'
```

برای ساخت بستهٔ مربوط به همان کار، از شناسهٔ دقیق نتیجه یا فهرست استفاده کنید؛ عبارت‌های نمونهٔ زیر باید با مقادیر واقعی همان نسخه جایگزین شوند:

```sh
python3 scripts/build_product_agent_context.py --product klassor --role backend \
  --section 'backend:عنوان بخش نقشه' --source 'backend:doc/مسیر-واقعی.md'
```

هر گزینه قابل تکرار است. `--source` مهارت یا مرجع متنی مورد نیاز را هم می‌پذیرد؛ `--section` بخش سطح دوم نقشه را همراه زیربخش‌هایش انتخاب می‌کند. قواعد پایهٔ AGENTS خودکار وارد می‌شوند. نقش‌های بعدی پیاده‌سازی، تست و بازبینی همین ساختار را می‌گیرند و دستور نقش مستقل خود را خواهند داشت. برنامه‌ریز مطابق قرارداد ۰٫۳ از همین ورودی استفاده خواهد کرد؛ اتصال اجرایی Dify آن هنوز ساخته نشده است.

ابزار، شناسهٔ دانش را با گزارش فنی و هش محتوا تطبیق می‌دهد. بستهٔ قدیمی، قواعد پایهٔ ناموجود، منبع خارج از دامنه یا درخواست بیش از ۲۰۰ هزار کاراکتر رد می‌شود؛ متن بی‌صدا بریده نمی‌شود. شناسهٔ بسته و مرجع دقیق هر منبع در خروجی قرار دارند. بستهٔ زمینه جای نیازمندی تأییدشده، نتیجهٔ گفت‌وگوی فنی، مطالعهٔ سورس یا دستور نقش را نمی‌گیرد و چیزی به مدل ارسال نمی‌کند.

## محتوای گزارش و حدود آن

- `sources.local.json`: مسیرهای محلی، مرجع Git و فناوری مورد انتظار، در صورت تعیین.
- `technical-context.local.json`: فناوری مشاهده‌شده، نسخه‌های وابستگی از package و lock، نام اسکریپت‌ها، نسخهٔ Git و وجود تغییر محلی، پوشه‌های اصلی، منابع منتخب و هش آن‌ها، و موارد باقی‌مانده.
- `technical-context.local.md`: نمای فارسیِ همان اطلاعات برای بررسی انسان.

ابزار، اطلاعات بستهٔ اصلی و چند فایل مشخص را می‌خواند. مقدار توکن، فایل محیط، تنظیمات سرویس، دیتابیس، متن سورس و تعریف کامل اسکریپت‌ها به گزارش کپی نمی‌شوند. از Dockerfile فقط برچسب نسخهٔ Node در سطر `FROM` استخراج می‌شود؛ آدرس رجیستری درج نمی‌شود. نام اسکریپت به معنی ایمن یا موفق بودن اجرای آن نیست.

در مخزن Newman، از مجموعه‌های Postman فقط مسیر، هش و تعداد درخواست‌ها و رویدادهای تست ثبت می‌شود؛ URL، header، مقدار variable و متن script کپی نمی‌شوند. در بررسی شاخه، تعداد فایل‌های دارای نام‌گذاری رایج test/spec نیز ثبت می‌شود؛ وجود فایل، شاهد اجرای موفق یا پوشش کامل نیست.

سقف خواندن هر منبع منتخب ۱۰ میلیون بایت و هر مجموعهٔ Postman، به دلیل اندازهٔ بیشتر این فایل‌ها، ۵۰ میلیون بایت است. مجموعهٔ بزرگ‌تر یا با قالب نامعتبر، با وضعیت صریح و بدون آمار ثبت می‌شود و در موارد نیازمند بررسی می‌آید.

خواندن مخزن، هیچ اسکریپت نصب، ساخت، تست، migration، hook یا فرمان پروژه را اجرا نمی‌کند. Git با قفل اختیاری غیرفعال و بدون fsmonitor خوانده می‌شود. هیچ push، fetch، تغییر شاخه یا تغییری در سورس انجام نمی‌شود.

نسخهٔ Git فقط برای پوشهٔ ریشهٔ همان مخزن ثبت می‌شود؛ نبود Git یا وجود تغییر محلی صریح باقی می‌ماند. شناسهٔ زمینه از همین اطلاعات و هش منابع منتخب ساخته می‌شود؛ این شناسه، هش همهٔ فایل‌های سورس یا تأیید کامل معماری نیست. فایل خارج از ریشه که با پیوند نمادین در دسترس است، به‌عنوان منبع منتخب خوانده نمی‌شود.

گزارش اولیه همیشه `technical_review_complete=false` و `development_ready=false` دارد. برای هر درخواست مشخص، مطالعهٔ سورس و مستند مرتبط، قرارداد API، روش واقعی اجرای بررسی‌ها و نتیجهٔ گفت‌وگوی فنی همچنان لازم است. وجود مسیر مخزن، به Dify دسترسی به آن پوشه نمی‌دهد؛ این ابزار گزارش محلی می‌سازد و چیزی به مدل، Dify یا سرویس دیگری ارسال نمی‌کند.

فایل‌های خروجی فقط پس از احراز نادیده‌گرفته‌شدن در Git ساخته می‌شوند؛ پوشهٔ محصول با دسترسی ۷۰۰ و فایل‌ها با دسترسی ۶۰۰ ذخیره می‌شوند. گزارش، پیش از استفاده به‌عنوان ورودی مدل، توسط مسئول محصول بررسی می‌شود. دادهٔ واقعی مشتری یا اطلاعات اتصال نباید به بستهٔ مشترک اضافه شود.

## وضعیت کلاسور

سورس بک‌اند، کلاینت، Newman و Playwright در محیط محلی معرفی شده‌اند و بررسی با مبنای `sandbox` انجام می‌شود. اطلاعات مختص هر مخزن در پروندهٔ خصوصی نگهداری می‌شوند. برنامه‌ریز Dify و اجرای توسعه هنوز ساخته نشده‌اند؛ این ابزار مرحلهٔ تهیهٔ زمینه را فراهم می‌کند. [قرارداد برنامه‌ریز](klassor-technical-planning-contract.md) نقش مالک محصول، TL و توسعه‌دهنده را تعریف می‌کند.
