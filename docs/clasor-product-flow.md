# نگاشت و پیش‌پرواز مسیر PA-04 → TL

**به‌روزرسانی:** [اتصال اعتبارسنج و انتشار نسخهٔ ۲](clasor-finalization-hook.md) انجام شد. سه اصلاح عمومی در master و محیط محلی فعال‌اند؛ تاریخچهٔ آن‌ها در این شاخه ادغام نشده است. گزارش‌های قبلیِ این سند وضعیت پیش از اتصال hook را توصیف می‌کنند؛ پذیرش مدل و تصمیم واقعی انسان همچنان باقی است.

نسخهٔ بستهٔ نگاشت 0.1.0؛ [نسخهٔ بومی ۱ فلو](clasor-flow-publication.md) پس از تکمیل تعریف‌ها منتشر شده است. بررسی‌های این سند مربوط به ساخت بستهٔ آفلاین است. در گام ساخت آفلاین، فلو در Kara منتشر نشده بود؛ اکنون تعریف بومی منتشر است، اما تصمیم انسانی ثبت نشده و هیچ مدل یا اجرای خودکاری آغاز نشده است. پذیرش کامل PO → TL همچنان باز است.

[قالب فلو](../clasor_agents/product_flow/flow-template.json)، [سازنده و پیش‌پرواز](../clasor_agents/product_flow/flow.py) و [manifest](../clasor_agents/product_flow/manifest.json) از بسته‌های فعلی [PA-04](clasor-pa04-workflow.md) و [TL](clasor-tl-planner-workflow.md) استفاده می‌کنند. این یک تعریف فلوی تیمی Kara است، نه Workflow بزرگ با دو LLM و نه موتور اجرای جدید. هر نقش Workflow و خروجی خودش را دارد.

```sh
.venv/bin/python scripts/build_clasor_product_flow.py --check

```

## تعریف و پین‌کردن نقش‌ها

قالب ساختار بدنهٔ POST پیش‌نویس `/console/api/company/projects/<project_id>/team/flows` را دارد. شناسه‌های ایجنت و اشخاص در قالب null هستند؛ فایل بدون تکمیل، قابل انتشار نیست. `bind(options, selections)` از پاسخ تازهٔ `/flows/options` و انتخاب مستقل caller بدنهٔ کامل پیش‌نویس را می‌سازد؛ خود تابع HTTP ندارد. selections برای هر کلید analysis/planning شامل agent_id، workflow_id، account_id و membership_id است؛ workflow_id از رسید مستقل import/انتشار همان بسته پین شود، نه حدس یا پاسخ مدل.

عضویت جاری، نقش po/tl، grantهای run/finalize موجود در options، شناسهٔ Workflow و قرارداد Start/End با بسته‌های فعلی تطبیق می‌یابند. این تطبیق قرارداد، برابری گراف/prompt نصب‌شده را اثبات نمی‌کند؛ caller باید برابری نسخهٔ منتشرشده با export را جدا بررسی کند. options دامنهٔ پروژه را از نشست سرور می‌گیرد؛ دادهٔ آن باید از همان پروژه خوانده شود. سازنده اختیار ساخت/انتشار را اعطا نمی‌کند؛ سرور هنگام انتشار آن را جدا بررسی می‌کند.

| مرحله | مسئول اجرا و نهایی‌سازی | ورودی اصلی | خروجی |
| --- | --- | --- | --- |
| analysis | یک حساب منتخب PO با عضویت و مجوزهای لازم | request از نسخهٔ درخواست؛ mode=analyze؛ source_context با منابع منتخب | analysis متن JSON |
| planning | یک حساب منتخب TL با عضویت و مجوزهای لازم | request از همان نسخه؛ analysis از `stage.analysis.analysis`؛ زمینه/هش تکمیل‌شده | plan متن JSON |

سازنده برای هر مرحله یک شخص را executor و finalizer می‌گذارد و decision_role همان po یا tl است. یک نفر می‌تواند هر دو نقش را با اختیار واقعی داشته باشد؛ این بسته حساب جدا را الزام نمی‌کند. تعویض مسئول در اجرای موجود از مسیر بومی تغییر مسئول باشد؛ preflight با snapshot قبلی، تغییر binding یا incarnation عضویت را رد می‌کند. grant feedback در options فلو فهرست نمی‌شود؛ قابلیت feedback و run در پاسخ تازهٔ جزئیات مرحله و برای همان نشست دوباره بررسی می‌شود.

قالب اولیهٔ analysis هیچ منبع خصوصی ندارد: sources=[] و previous_analysis=null. برای منابع منتخب هر درخواست، بستهٔ assemble موجود PA-04 و مسیر مجاز اصلاح ورودی/بازخورد استفاده و بعد از خواندن پاسخ جدید دوباره بسته ساخته شود. متن منابع خصوصی را در مقادیر ثابت فلوی عمومیِ قابل خواندن برای اعضا قرار ندهید. `analysis_run(package, request, instance, stage, actor, published_binding)` اصل درخواست، نسخه، مسئول، action=run و تطابق preview با بستهٔ تخصصی را بررسی و فقط بدنهٔ expected_revision را برمی‌گرداند.

## چرخهٔ تکمیل ورودی TL

شناسهٔ StageInstance برنامه‌ریزی، تحلیل منتخب و رسید تصمیم PO پس از ایجاد اجرا/نهایی‌سازی معلوم می‌شوند؛ بنابراین planning_context و hash معتبر آن را نمی‌توان از قبل به‌عنوان ثابت عمومی فلو ساخت. قالب اولیه planning_context={} و hash صفر دارد. کنترل ورودی TL آن را **پیش از فراخوانی مدل رد می‌کند**؛ readyشدن مرحله به‌معنای آماده‌بودن این بسته نیست. بدون تکمیل ورودی run نکنید.

راه موجود در Kara، اصلاح ورودی از action=feedback است. برای اولین تحویل TL:

1. caller مورد اعتماد بستهٔ PA-04، رسید مستقل تصمیم واقعی PO، درخواست/اجرای تازه و projection مرحلهٔ TL شامل handoffs را دریافت کند. حساب TL فقط محتوای منتخبِ تحویلی را لازم دارد؛ دریافت تاریخچهٔ خصوصی تحلیلگر لازم نیست. بستهٔ PA-04/منابع مجاز از مرز caller معتبر می‌آیند، نه از مجوز عمومی خواندن خروجی‌های PO.
2. published_binding مستقل از نسخهٔ منتشرشدهٔ فلو و actor با account_id/membership_id نشست جاری خوانده شوند. `planning_setup(...)` شناسه/نسخه/پروژه/مسئول و action=feedback را کنترل می‌کند. این helper فقط **اولین آماده‌سازی** پیش از هر attempt/feedback/artifact برنامه‌ریزی را پوشش می‌دهد.
3. خروجی شامل body آمادهٔ POST مرحلهٔ planning با پسوند `/feedback`، کلید idempotency و expectation خصوصی است. body دارای expected_revision فعلی، artifact_id=null، inputs معتبر، پیام ثبت آماده‌سازی و feedback_variable=null است. این ثبت صرفاً آماده‌سازی ورودی است، تصمیم یا بازخورد معنایی TL نیست؛ با متغیر null، پیام به prompt الحاق نمی‌شود. مقدار اولیه feedback_context همان placeholder غیرخالی قالب است.
4. سرور در همان CAS، revision و round را یک واحد افزایش می‌دهد. بستهٔ TL با base_revision **همان revision مورد انتظارِ بعد از ثبت** ساخته می‌شود؛ prospective snapshot صرفاً انتظار محلی است، شاهد رخداد سرور نیست. این کار مانع دور باطلِ تغییر hash در اثر افزایش revision می‌شود. HTTP را فقط caller مجاز انجام دهد؛ این بسته چیزی ارسال نمی‌کند.
5. بعد از پاسخ/خواندن تازه، `planning_run(setup, package, request, instance, stage, actor)` نسخه/دور، FlowVersion، مسئول، binding، رسید handoff، هر پنج preview_inputs، inputs واقعی و رکورد بازخورد مؤثر/input_digest را تطبیق می‌دهد. پاسخ قدیمی، ورودی تغییرکرده، تحلیل غیرمنتخب و نسخهٔ تازهٔ درخواست رد می‌شوند. فقط پس از این بررسی، بدنهٔ run با expected_revision تازه برگردانده می‌شود؛ هیچ ایجنتی در این helper اجرا نمی‌شود.

کلیدهای idempotency برای آماده‌سازی و اجرای بعدی جدا هستند. packet و کلیدها را خصوصی ذخیره و در retry انتقال همان‌ها را تکرار کنید؛ فراخوانی دوباره planning_setup کلید جدید می‌سازد و جای retry همان عملیات نیست. preflight موفق قفل سرور یا ACL نیست؛ سرور هنگام mutation دوباره مجوز و revision را کنترل می‌کند. receipt/hash/packet باید از caller معتبر بیایند؛ ساختن آن‌ها از دادهٔ نامعتبر یا متن مدل اثبات تأیید PO نیست.

بازخورد محتوایی بعدی TL در feedback_context، با انتخاب plan مبنا و حفظ نسخه‌هاست. helper اولین آماده‌سازی، حلقهٔ چنددور بازخورد، retry مدل یا نهایی‌سازی را انجام نمی‌دهد؛ استفادهٔ دوباره از آن پس از شروع برنامه‌ریزی رد می‌شود. تصمیم PO و نهایی‌سازی TL و مرج دستی همچنان عملیات واقعی انسان هستند. تغییر AC باید receipt تازه و staleشدن برنامه/تصمیم‌های وابسته را در مسیر بومی ایجاد کند؛ preflight فقط ناسازگاری را رد می‌کند و خودش تاریخچه یا وضعیت را تغییر نمی‌دهد.

## بررسی و مرز پذیرش

make check نهایی با ۱۱۰ آزمون موفق شد. ۹ آزمون متمرکز آفلاین شامل نگاشت دو نقش، کنترل قرارداد با validate_bindings/validate_inputs واقعی بستر (بدون DB)، رد sentinel توسط Code دقیق TL، مجوز/عضویت/Workflow ناسازگار، درخواست تغییرکرده، CAS و readback، مسئول جایگزین و handoff غیرمنتخب هستند. پاسخ بعد از آماده‌سازی در آزمون شبیه‌سازی شده است؛ این آزمون‌ها اجرای واقعی API یا همکاری چندحسابی را ثابت نمی‌کنند.

فایل‌های این بسته فقط دارایی اختصاصی کلاسورند؛ کد عمومی Kara، شاخه‌های دیگر، sources و upstream تغییر نکردند. runtime/رابط تغییر نکرد و smoke کلاینت موضوعیت نداشت. مانع metadata پایان مدل، حفظ اصل درخواست در بازخورد و hook عمومی اعتبارسنج پیش از finalize همچنان وابستگی‌های master هستند؛ validator تخصصی ضعیف نشده است.

[caller HTTP تخصصی](clasor-product-caller.md) اضافه شده و ذخیره/بازخوانی پیش‌نویس روی پایلوت واقعی بررسی شده است؛ ثبت ورودی TL تا وجود binding برنامه‌ریزی و تحلیل نهایی معتبر باز مانده است. import/انتشار Workflow و فلو، اعتبار معنایی مدل، دو بازخورد PO و بازخورد TL، تغییر نسخه و پذیرش واقعی مسیر هنوز باقی‌اند؛ هیچ‌یک از وضعیت آفلاین این بسته نتیجه گرفته نمی‌شود.
