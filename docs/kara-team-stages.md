# اجرای مرحله، بازخورد و نهایی‌سازی انسانی

KP-05 — ایجاد Instance به [تصمیم ورود PO](kara-team-requests.md)، RequestRevision و FlowVersion دقیق متصل است. ایجاد پرونده یا موفقیت اجرای فنی به‌تنهایی هیچ مرحله‌ای را نهایی نمی‌کند.

## آغاز و اختیار

ایجاد اجرای تیمی با PO یا اجراکنندهٔ تعیین‌شدهٔ مرحلهٔ اول، با مجوز فعلی run و incarnation همان عضویت ممکن است. برای هر تصمیم ورود فقط یک Instance ایجاد می‌شود. هر بار باید تصمیم جاری، واقعی، تأییدشده، لغونشده و منقضی‌نشده و شناسه/digest درخواست و فلو با بانک تطبیق داشته باشند؛ پاسخ تاریخی replay مجوز شروع نیست. اصلاح درخواست یا تغییر تصمیم جاری، ادامهٔ اجرای قبلی را متوقف می‌کند و تاریخچه را پاک نمی‌کند.

بایگانی فلو، ایجاد اجرای تازه را می‌بندد؛ اجرای موجود با مراجع ثابت و تصمیم ورود معتبر می‌تواند ادامه پیدا کند.

شروع و retry فقط با اجراکنندهٔ تعیین‌شده، عضویت فعلی و grant صریح run است. بازخورد، اصلاح ورودی، ویرایش انسانی خروجی و درخواست تصمیم به grant feedback همان ایجنت نیاز دارند. نهایی‌سازی به grant finalize، شخص نهایی‌کننده، incarnation عضویت و نقش کاری تعیین‌شده در فلو نیاز دارد. عنوان مدیر یا PO به‌تنهایی این مجوزها را ایجاد نمی‌کند. نسخه، digest منبع اجرایی و فعال‌بودن ایجنت/برنامه در اقدام تازه بررسی می‌شوند.

فهرست اجراها تنها وضعیت و مسئولان را نشان می‌دهد. محتوای مرحله فقط با grant فعلی view/run/feedback/finalize همان ایجنت قابل خواندن است؛ لاگ میانی، prompt و اعتبارنامه در این API عرضه نمی‌شوند. نفر مرحلهٔ بعد می‌تواند ورودی تحویل‌شدهٔ خودش را بدون مجوز مشاهدهٔ تمام سابقهٔ ایجنت قبلی مصرف کند.

## تلاش، دور و خروجی

مرحلهٔ اول ready و مرحله‌های بعد blocked ساخته می‌شوند. run فقط یک تلاش pending در outbox موجود می‌سازد؛ worker همان Workflow منتشرشده را با شناسهٔ ثابت تلاش و حساب واقعی عضو اجرا می‌کند. `company_team_stage_attempts` فقط اتصال یک‌به‌یک به تلاش موجود ایجنت است؛ موتور یا صف اجرای دیگری ساخته نشده است. شناسهٔ داخلی ایجاد تلاش توسط سرور ساخته می‌شود؛ تلاش مستقلی که کلاینت قبلاً اجرا کرده قابل اتصال به مرحله نیست.

تطبیق درخواست/تصمیم/نسخه و اختیار هنگام claim، ورود به موتور و دریافت نتیجه دوباره انجام می‌شود. نتیجهٔ قدیمی، لغو مجوز یا ورود نامعتبر خروجی قابل نهایی‌سازی نمی‌سازد. callback و ذخیرهٔ نتیجه در یک تراکنش انجام می‌شوند؛ callback تکراری روی همان تلاش یا تلاش قدیمی، خروجی/دور جدید را جایگزین نمی‌کند.

اجرای موفق با خروجی مطابق نام‌های قرارداد و JSON/اندازهٔ معتبر، Artifact با kind=workflow و وضعیت awaiting_feedback می‌سازد. معنای محتوای خروجی را انسان بررسی می‌کند؛ این اعتبارسنجی جای کنترل کیفیت معنایی نیست. شمار تلاش‌های فنی از شمار بازخوردهای انسانی جداست. خروجی نامعتبر یا شکست فنی به failed می‌رود؛ retry فقط مرحله را ready می‌کند و اجرای دوباره اقدام جدا می‌خواهد.

بازخورد با expected_revision، خروجی مبنا، متن، مقادیر ورودی و feedback_variable ثبت می‌شود؛ یک دور تازه با digest تازه می‌سازد. در مرحلهٔ دارای خروجی و ورودی متنی، انتخاب ورودی متنی دریافت‌کنندهٔ بازخورد لازم است. متن پایه، خروجی مبنا و تاریخچهٔ پیام‌های بازخورد در همان ورودی ترکیب می‌شوند و قبل از run بعدی نمایش داده می‌شوند. دادهٔ ثبت‌شده شامل submitted و effective است تا ورودی انسانی و ورودی واقعاً رسیده به موتور قابل تشخیص باشند. برای مرحلهٔ فاقد ورودی متنی، بازخورد علت اصلاح مقادیر است؛ اصلاح باید در ورودی‌های عددی/انتخابی اعمال شود.

بازخورد انتخاب قبلی را پاک می‌کند؛ Artifact دور قبلی قابل نهایی‌سازی نیست. ویرایش انسانی خروجی، Artifact مستقل kind=human با parent_id، حساب/عضویت و علت می‌سازد و خروجی اجرایی را بازنویسی نمی‌کند. درخواست تصمیم فقط یک Artifact دور فعلی را انتخاب و مرحله را awaiting_decision می‌کند. نهایی‌کننده فقط همان Artifact را با علت و CAS نهایی می‌کند؛ تصمیم در رکورد immutable ثبت می‌شود. فقط پس از این تصمیم، مرحلهٔ بعد ready می‌شود؛ اجرای آن خودکار نیست و ورودی از Artifact منتخب می‌آید، نه آخرین خروجی موجود.

## API و نگهداری

پیشوند `/console/api/company/projects/<project_id>/team` با نشست و CSRF موجود:

| مسیر | اقدام |
| --- | --- |
| `/instances` | GET وضعیت اجراها و درخواست‌های قابل ایجاد برای همین حساب؛ POST ایجاد با request_id، intake_decision_id، expected_revision درخواست |
| `/instances/<instance_id>/stages/<stage_id>` | GET محتوا، ورودی مؤثر، مجوز اقدام، تلاش‌ها، دورها، Artifactها و تصمیم‌های مجاز |
| مسیر مرحله + `/run` و `/retry` | POST فقط expected_revision مرحله |
| مسیر مرحله + `/feedback` | POST expected_revision، artifact_id یا null، message، inputs، feedback_variable یا null |
| مسیر مرحله + `/edit_output` | POST expected_revision، artifact_id، content و reason |
| مسیر مرحله + `/request_decision` | POST expected_revision و artifact_id |
| مسیر مرحله + `/finalize` | POST expected_revision، artifact_id و reason |

همهٔ تغییرها Idempotency-Key با UUID canonical می‌خواهند؛ کلید/دادهٔ متفاوت یا revision قدیمی ۴۰۹ می‌گیرد. قفل Tenant مشترک با مجوز/عضویت و قفل مرحله، تغییر و ثبت journal را اتمی می‌کنند. worker از claim و outbox قبلی استفاده می‌کند؛ تضمین exactly-once برای اثر بیرونی ادعا نمی‌شود.

مهاجرت افزایشی `005_team_stages` شش جدول اضافه می‌کند؛ SQL مهاجرت‌های ۰۰۱ تا ۰۰۴ تغییر نمی‌کند. ارجاع پرونده/تصمیم/فلو و Artifact/تلاش/مرحله با FKهای دامنه‌دار کنترل می‌شود. Instance و رکوردهای اتصال تلاش، بازخورد، Artifact و تصمیم نهایی UPDATE/DELETE نمی‌پذیرند. مرحله، revision، round و active/selected pointerهای مستقل دارد.

سقف ورودی و اجرای فنی از قرارداد Workflow و guardrailهای بومی می‌آید؛ تعداد دور انسانی سقف عددی ثابت ندارد. سقف JSON خروجی با `KARA_TEAM_ARTIFACT_MAX_BYTES` در API/worker قابل تنظیم است؛ پیش‌فرض ۲۵۶ KiB، بازهٔ ۱ KiB تا ۱۶ MiB. ورودی ترکیب‌شدهٔ بازخورد نیز باید در حد قرارداد ورودی باقی بماند. پیوست‌های درخواست همچنان برای اعضای همان پروژه قابل دریافت‌اند؛ قرارداد اجرایی فعلی، ورودی file بومی را نمی‌پذیرد و فایل را پنهانی به مدل نمی‌فرستد.
