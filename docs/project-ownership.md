# ادمین کل Kara و پروژه‌ها

مالک اولیهٔ نصب، ادمین کل Kara است. شناسهٔ حساب یک بار در جدول `company_product` ثبت می‌شود؛ عضویت یا مالکیت یک پروژه این اختیار را ایجاد نمی‌کند. مرکز مدیریت در همین جدول مشخص است و هنگام انتقال نسخهٔ قدیمی به فضای تازه متصل می‌شود. برای این اختیار حساب یا نقش موازی Dify ساخته نمی‌شود.

- مدیر محصول می‌تواند پروژه بسازد و مالک پروژهٔ جدید را انتخاب کند. ویرایش مشخصات و جایگزینی مالک پروژه‌های موجود همچنان با حساب اولیهٔ نصب است. نقش محصول مستقل از نقش‌های فنی پروژه است؛ [مدیریت کاربران](users.md) مرجع دو نقش مدیر و کاربر عادی است.
- هر پروژه یک فضای کاری مستقل Dify دارد. برنامه‌ها، ایجنت‌ها، دانش، اسکیل‌ها، اعضا و تنظیمات مدل آن از فضای کاری سایر پروژه‌ها جدا هستند.
- مالک پروژه با نقش اصلی `owner` می‌تواند کاربران فعال کارا را اضافه، نقش آن‌ها را تعیین و عضویتشان را حذف کند. ادمین کل Kara نیز دسترسی مدیریتی به پروژه‌ها دارد و از مسیر اعضا قابل حذف نیست.
- نقش `editor` برای همکار سازندهٔ برنامه، ایجنت، دانش و اسکیل کافی است. `normal` برای استفاده و `dataset_operator` برای مدیریت دانش مطابق قابلیت نسخه به کار می‌روند. مدیر فنی (`admin`) به‌تنهایی اختیار تغییر اعضا یا مالک پروژه ندارد.
- عضویت یک حساب می‌تواند در چند پروژه با نقش‌های متفاوت باشد. فهرست پروژه‌ها فقط عضویت‌های همان حساب را نشان می‌دهد؛ ادمین کل Kara همه را می‌بیند.
- نقش مالک پروژه به‌تنهایی مجوز ساخت پروژه یا مدیریت محصول نمی‌دهد. مالک پروژه نمی‌تواند مالکیت خود را از ابزار انتقال مالکیت اصلی Dify واگذار کند یا اعضای پروژهٔ دیگری را تغییر دهد. تعیین مالک از مسیر اختصاصی پروژه فقط با ادمین کل Kara انجام می‌شود.

مرکز مدیریت محصول در دسترس مدیران محصول است. دعوت مرکزی، به‌تنهایی دسترسی به هیچ پروژه‌ای نمی‌دهد. مالک پروژه همکار را از فهرست کاربران فعال کارا به پروژه اضافه می‌کند؛ این کار مستقیم و بدون لینک دعوت است. ثبت‌نام عمومی و ساخت خودکار فضای کاری بسته‌اند؛ راه‌اندازی اولیه و دعوت استاندارد همچنان از حساب‌های Dify استفاده می‌کنند.

APIهای پروژه از ورود و CSRF اصلی استفاده می‌کنند. خواندن پروژه با عضویت کنترل می‌شود، ورود به پروژه فضای کاری فعال را با بررسی عضویت تغییر می‌دهد و ساخت برنامه به فضای کاری همان پروژه محدود است. کنترل تغییر اعضا در مسیرهای سرویس اصلی و RBAC سازگاری Community هم اجرا می‌شود؛ پنهان‌کردن دکمه به‌تنهایی مبنای حفاظت نیست.

ساخت فضای کاری، عضویت مالک و ثبت پروژه داخل تراکنش بیرونی اجرا می‌شوند تا commitهای داخلی سرویس اصلی موجب ثبت ناقص پروژه نشوند. تعیین مالک با قفل فضای کاری انجام می‌شود و دقیقاً یک مالک بومی باقی می‌ماند. برای سازگاری، نام فنی `is_product_owner` و توابع قدیمی API همچنان به ادمین کل اشاره می‌کنند؛ این فیلد نقش کاری PO نیست. [نقش‌های کاری تیم](kara-team-roles.md) جدا نگهداری می‌شوند. این پیاده‌سازی برای Community ثابت‌شدهٔ ۱.۱۷.۱ است؛ RBAC خارجی Enterprise نیازمند اتصال و آزمون جداگانه است.

آزمون‌های تصویر API با حساب و دادهٔ ساختگی و rollback کامل، ادمین کل Kara، مالک پروژه، مدیر، توسعه‌دهنده و عضو پروژهٔ دیگر را بررسی می‌کنند. شناسهٔ مستقیم برنامه، دانش و اسکیل پروژهٔ دیگر نیز از مسیرهای بومی بررسی می‌شود. داده‌ها و نسخهٔ بازیابی محلی وارد Git نمی‌شوند.
