# Workflow برنامه‌ریز فنی TL

نسخهٔ بسته و دستور 0.1.0؛ قرارداد 0.1.0. **وضعیت جاری: تعریف مستقل در پایلوت import/منتشر و ثبت شده و Codeها در sandbox واقعی با پاسخ مرجع بررسی شدند؛ آزمون مدل و پذیرش PO → TL باقی‌اند.** [گزارش آماده‌سازی بومی](clasor-native-definitions.md) مرجع نصب جاری است.

[دستور](../clasor_agents/tl_planner/prompt.md)، [سازنده](../clasor_agents/tl_planner/workflow.py)، [DSL](../clasor_agents/tl_planner/workflow.json)، [manifest متناظر](../clasor_agents/tl_planner/workflow-manifest.json)، [schema ورودی](../clasor_agents/tl_planner/schemas/input.schema.json) و [مبدل Start](../clasor_agents/tl_planner/transport.py) با هم نسخه‌گذاری می‌شوند. [قرارداد خروجی](clasor-tl-planner-contract.md) و اعتبارسنج قبلی حفظ شده‌اند؛ ساخت prompt و Code از همان schema/توابع انجام می‌شود، نه نسخهٔ دستی جداگانه.

```sh
.venv/bin/python scripts/build_clasor_tl_planner.py --check
.venv/bin/python -m unittest scripts.test_clasor_tl_workflow
```

برای بازسازی، فرمان اول را بدون --check اجرا کنید. فایل workflow.json همان DSL اپلیکیشن به‌صورت JSON قابل خواندن به‌عنوان YAML است؛ این بسته در برنامهٔ مستقل پایلوت import شده و graph آن تطبیق داده شده است. الگوی گراف و dependency رسمی ثابت از سازندهٔ PA-04 گرفته می‌شود، بدون تغییر فایل‌ها یا نسخهٔ PA-04. مبنای فنی همان Dify 1.17.1 و افزونهٔ OpenAI API Compatible ثابت 0.0.68 است؛ نسخهٔ تازه‌ای از upstream دریافت یا ویرایش نشده است.

## ورودی و مرز اعتماد

ابتدا caller مجاز با prepare، رسید مستقل تصمیم PO و handoff منتخب، بستهٔ TL را بسازد و hash canonical کل بسته را مستقل ذخیره کند. سپس `build_inputs(prepared_input, expected_input_sha256, feedback_context)` پنج ورودی متنی زیر را می‌سازد:

| Start | نگاشت |
| --- | --- |
| request | متن دست‌نخوردهٔ نسخهٔ درخواست |
| analysis | متن JSON تحلیل نهایی منتخب؛ در فلو `stage.analysis.analysis` |
| planning_context | JSON سایر فیلدهای بسته: نسخه/نقش، binding، رسید و snapshotهای مخزن |
| expected_input_sha256 | hash مستقل ذخیره‌شده توسط caller مورد اعتماد |
| feedback_context | رشتهٔ جداگانهٔ بازخورد؛ ابتدا خالی |

کنترل اول پنج ورودی را به همان بستهٔ اولیه برمی‌گرداند و ساختار بسته، hash کل، hash درخواست و تحلیل، وضعیت تحلیل و ref/commit/hash متن منابع را کنترل می‌کند. یکپارچگی hash، احراز هویت نیست؛ گرفتن hash از همان ورودی نامعتبر یا پاسخ مدل امن نیست. caller باید پیش از اجرا preview_inputs هر پنج مقدار را با بسته تطبیق دهد و هویت، مجوز و revision جاری را دوباره از سرور بررسی کند. هیچ اتصال HTTP یا تغییر وضعیت توسط این مبدل انجام نمی‌شود.

در گراف، رسید تصمیم و شناسهٔ حساب‌ها به prompt داده نمی‌شوند؛ فقط request، analysis، repositories، دو hash و بازخورد به مدل می‌رسند. metadata اصلی برای caller و validator حفظ می‌شود. قواعد مخزن و evidence آرایه‌های جدا دارند و prompt منبع حاوی دستور جعلی را داده تلقی می‌کند. مقاومت معنایی مدل در برابر این دستورها هنوز با اجرای واقعی اثبات نشده است.

## گراف و بازخورد

`Start → کنترل ورودی Code → LLM → اعتبارسنج Code → End(plan)`

Codeها فقط کتابخانهٔ استاندارد و توابع محلیِ بسته‌شده در export دارند؛ فایل/شبکه، نصب dependency و ابزار اجرایی ندارند. گرهٔ خروجی فقط یک فیلد متنی plan می‌دهد. validator همان validate_plan قرارداد را اجرا می‌کند؛ علت پایان از `llm.finish_reason` می‌آید و null، length یا JSON ناقص به خطا می‌رسند. retry مدل خاموش است؛ خطای اعتبارسنج خروجی موفق تولید نمی‌کند.

بازخورد بومی فقط به feedback_context نگاشت شود؛ مقدار آن می‌تواند پیشوند فارسی و JSON الحاقی previous_output/feedback_history داشته باشد. متن عیناً دادهٔ prompt می‌ماند و JSON خالص فرض نمی‌شود. build_inputs تحلیل یا request را با بازخورد بازنویسی نمی‌کند. برای مقدار ثابت اختیاری اولیه در تعریف فلوی فعلی، اگر Kara رشتهٔ خالی را نپذیرفت، placeholder غیرخالی «هنوز بازخوردی ثبت نشده است.» استفاده شود؛ همان مقدار باید در preview مقایسه شود.

hash بسته، request/analysis و snapshot/رسید/مرحله را مقید می‌کند؛ feedback_context جزو این hash نیست و ورودی مؤثر/سابقهٔ بازخورد باید به input_digest و تلاش بومی سرور متصل بمانند. با بازسازی بسته برای revision تازه، expected hash و planning_context متناظر نیز باید با هم عوض شوند. این فایل هنوز caller خودکارِ تنظیم این مقادیر یا پذیرش چند دور بازخورد واقعی نیست.

caller پس از اجرا باید id/actor/workflow را با snapshot مستقل تلاش تطبیق دهد و سپس validate_attempt را با status/finish_reason/outputs واقعی اجرا کند. گیت داخل Code جای بررسی هویت بومی یا ACL را نمی‌گیرد؛ اعتبارسنجی موفق، finalize مرحله نیست. پس از ویرایش انسانی نیز validate_plan لازم است؛ اتصال عمومی آن پیش از finalize همچنان کار master است.

## حدود و تنظیم مدل

کل بستهٔ آماده‌شده، wire متنی و دادهٔ محتوایی prompt هرکدام حداکثر ۳۲KiB هستند؛ request حداکثر ۴۰۰۰ نویسه، analysis حداکثر ۱۶۰۰۰ و feedback حداکثر ۸۰۰۰ است. هر مخزن حداکثر ۱۲ repository_rule و ۱۲ evidence، با سقف ۴۰۰۰ نویسه برای هر متن دارد؛ سقف مجموع بایت زودتر می‌تواند محدود کند. ref فقط refs/remotes/origin/sandbox و commit کامل ۴۰رقمی است. هیچ برش خاموش یا خواندن خودکار مخزن انجام نمی‌شود. متن بزرگ باید با انتخاب صریح منابع کوچک‌تر در بستهٔ تازه ارائه شود.

alias مستقل `Clasor TL Planner Pilot v0.1.0` در DSL قرار دارد؛ credential یا endpoint در بسته نیست و پیکربندی/صحت این alias در گام آماده‌سازی تعریف تغییر یا آزمون نشد. manifest زمینهٔ پیشنهادی ۱۶۳۸۴ و سقف پاسخ ۴۰۹۶ توکن و گزینه‌های پروفایل سازگار قبلی را ثبت می‌کند؛ این تنظیمات روی مدل TL اجرا/اندازه‌گیری نشده‌اند و نام alias تضمین ظرفیت نیست. سقف نویسه/بایت تخمین توکن نیست؛ بودجهٔ واقعی prompt/schema/پاسخ پیش از آزمون معنایی باید بررسی شود.

## بررسی و ادامه

هشت آزمون Workflow، **کد دقیق داخل export** را با دو پاسخ مرجع ساختگی اجرا کردند: بازسازی بسته، تحلیل و scope، بازخورد بومی، دستکاری ورودی/منبع، ref نادرست، duplicate JSON، سقف حجم و خروجی ناقص بررسی شدند. این پاسخ‌ها از مدل نیامده‌اند. manifest تغییر prompt، schema، مبدل، validator، سازندهٔ گراف و export را تشخیص می‌دهد؛ ساخت hash شاهد پذیرش مدل نیست.

make check نهایی با ۱۰۱ آزمون موفق شد؛ آزمون‌های قبلی قرارداد و PA-04 نیز حفظ شدند. runtime و رابط محصول تغییر نکردند؛ تست کلاینت و Compose/doctor موضوع این گام نبودند. ورود/انتشار Workflow و ثبت ایجنت در گام بومی بعدی انجام شدند؛ انتشار فلو، پیکربندی/پذیرش مدل، ثبت واقعی ورودی TL، دورهای بازخورد PO/TL و پذیرش معنایی باقی‌اند. حفظ اصل درخواست در بازخورد و گیت تخصصی پیش از finalize هنوز وابستگی‌های عمومی master هستند؛ انتقال معتبر finish_reason نیز پیش‌نیاز آزمون مدل است. هیچ‌کدام در این شاخه دور زده نشده‌اند.

نگاشت و پیش‌پرواز در [بستهٔ فلوی دومرحله‌ای](clasor-product-flow.md) آماده‌اند و caller به API متصل شده است؛ پیش‌نویس کامل بومی آمادهٔ بازبینی نسخه و مسئول‌ها پیش از انتشار فلو است. انتشار و پذیرش واقعی پس از رفع وابستگی‌ها و آزمون انسانی انجام شوند.
