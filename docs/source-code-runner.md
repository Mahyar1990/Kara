# سورس کد و Runner محلی کارا

منوی «سورس کد» در پروژه، بین «دانش» و «مهارت‌ها» قرار دارد. این قابلیت مستقل است: برنامه‌ها، ایجنت‌ها، فلوها، مدل‌های آن‌ها و اتصال‌های قبلی را ویرایش یا بازنشر نمی‌کند. سورس آماده‌شده را می‌توان از تنظیمات Runner به اجرای محلی همان پروژه و دستگاه متصل کرد؛ [راهنمای اجرای محلی](local-execution.md) مراحل را توضیح می‌دهد.

## چیدمان صفحه

صفحهٔ «سورس کد» دو تب «مخزن‌ها» و «worktreeهای من» دارد. مخزن‌ها با آدرس کامل، برنچ و نسخه در کارت‌های فشرده نمایش داده می‌شوند و دکمه‌های ویرایش و حذف کنار اطلاعات قرار دارند. انتخاب Runner و سابقهٔ آماده‌سازی در تب worktreeها است.

فرم تعریف و ویرایش worktree سه تب «اطلاعات»، «بخش‌ها» و «مستندات» دارد. در «بخش‌ها»، دکمهٔ «بخش جدید» دیالوگ مستقلی برای اطلاعات بخش و مستند اختیاری آن باز می‌کند؛ تأیید، شما را به فهرست فشردهٔ بخش‌ها برمی‌گرداند. مستند همراه بخش به فهرست مستندات worktree اضافه می‌شود و از همان تب قابل ویرایش است؛ حذف بخش، مستند را حذف نمی‌کند. افزودن و ویرایش مستند هم در دیالوگ انجام می‌شود. تغییر تب، پیش‌نویس را حفظ می‌کند؛ تأیید دیالوگ داخلی فقط پیش‌نویس را تغییر می‌دهد و ثبت نهایی با «ذخیرهٔ worktree» انجام می‌شود. انصراف از دیالوگ داخلی، تغییرات همان دیالوگ را کنار می‌گذارد.

پس از ثبت آماده‌سازی، دیالوگ وضعیت با نشانگر انتظار، حالت «در صف Runner» و سپس «در حال آماده‌سازی» باز می‌ماند. بستن آن اجرای Runner را متوقف نمی‌کند؛ کارهای فعال بالای تب worktreeها هم نمایش داده می‌شوند و وضعیت هر دو ثانیه تازه می‌شود. این نمایش، وضعیت کلی است و درصد یا خروجی زندهٔ Git را گزارش نمی‌کند.

## راه‌اندازی

1. در «تنظیمات و اتصال‌ها ← اتصال به گیت‌لب»، آدرس پایهٔ HTTPS سرویس و توکن **شخصی خودتان** را ذخیره کنید. برای Git مجوز `read_repository` کافی است؛ آزمون هویت اختیاریِ سرور کارا به `read_user` نیز نیاز دارد. توکن روی سرور رمزگذاری می‌شود و در فرم بازگردانده نمی‌شود. تغییر مقصد به توکن تازه نیاز دارد.
2. در «سورس کد»، نام، URL مربوط به HTTPS Clone و نام دقیق برنچ هر مخزن را ثبت کنید. مخزن‌ها در پروژه مشترک‌اند؛ ویرایش و حذف تعریف فقط با سازنده یا مدیر پروژه است. حذف، منطقی است و تاریخچه را نگه می‌دارد.
3. یک worktree شخصی بسازید. برای هر بخش، شناسه، مسیر نسبی، مخزن و اتصال شخصی را انتخاب کنید. نمونه: `backend` در `services/backend` و `frontend` در `clients/frontend`. هر تعریف حداکثر ۸ بخش دارد. توکن هر بخش باید متعلق به همان آدرس GitLab باشد.
4. مستندات ارتباط بخش‌ها را با مسیر و متن Markdown تعریف کنید؛ مانند `docs/architecture.md`، `docs/api-contracts.md` و `docs/dependencies.md`. در متن، مسئولیت بخش‌ها، مسیر ارتباط‌ها، API و نسخهٔ قراردادها، وابستگی و ترتیب راه‌اندازی را بنویسید. این فایل‌ها خارج از مسیر مخزن‌ها قرار می‌گیرند. حداکثر ۱۶ فایل، هر فایل ۶۴KiB و مجموع ۲۵۶KiB است. Markdown به‌صورت متن نگهداری و نوشته می‌شود.
5. در «Runnerهای شخصی»، بستهٔ هم‌نسخهٔ سرور را دریافت و در پوشه‌ای خصوصی باز کنید. Python 3.10+ و Git لازم است. macOS و Linux پشتیبانی می‌شوند؛ در Windows از WSL استفاده کنید.
6. برای دستگاه خود کد یک‌بارمصرف بسازید؛ ظرف ۱۰ دقیقه در ترمینال وارد کنید. کد را در آرگومان یا چت ننویسید. در پوشه‌ای که بسته باز شده است:

```sh
python3 -m kara_source_runner pair --server https://your-kara.example.com
python3 -m kara_source_runner run
```

برای محیط توسعهٔ فعلی آدرس `http://localhost:8080` است. HTTP فقط برای آدرس‌های دقیق loopback مجاز است. بیرون loopback اتصال HTTPS با اعتبارسنجی گواهی الزامی است. Runner اتصال خروجی دارد و پورت ورودی باز نمی‌کند؛ اتصال مستقیم به پایگاه داده یا Redis ندارد.

برای انتخاب محل فایل‌ها:

```sh
python3 -m kara_source_runner run --root /your/private/workspaces
```

فایل خصوصی دستگاه پیش‌فرض `~/.config/kara-source-runner/device.json` است؛ فقط مالک می‌تواند آن را بخواند (`0600`). برای دستگاه دیگر از `--config` پیش از نام دستور استفاده کنید. فایل تنظیمات و پوشه‌های کد را در Git قرار ندهید.

7. در «سورس کد»، Runner خودتان را انتخاب و «آماده‌سازی روی Runner» را ثبت کنید. Runner باید در ترمینال در حال اجرا باشد. هر بخش با `git fetch` فقط از برنچ تعیین‌شده و سپس **Git worktree واقعی با HEAD جداشده روی SHA دقیق** آماده می‌شود. دریافت shallow است؛ submodule و Git LFS به‌صورت خودکار دریافت نمی‌شوند.

## محل داده و تکرارپذیری

مسیر پیش‌فرض `~/KaraSourceWorkspaces/<job-id>/` است. درون آن، مسیر هر بخش و فایل‌های Markdown نوشته می‌شوند. پوشهٔ `.kara/` شامل مخزن bare محلی هر بخش و فایل `manifest.json` است؛ manifest آدرس، برنچ، SHA، مسیر و نسخهٔ تعریف را ثبت می‌کند. برای حفظ worktree، مخزن‌های bare مربوط را جداگانه جابه‌جا یا حذف نکنید.

آماده‌سازی اولیه پوشهٔ تازه می‌سازد. پس از موفقیت، روی همان Runner دکمه به «به‌روزرسانی در همین پوشه» تبدیل می‌شود؛ این عملیات درخواست و سابقهٔ تازه ثبت می‌کند ولی همان پوشه و مخزن‌های Git را استفاده می‌کند. انتخاب Runner دیگری به آماده‌سازی اولیهٔ جداگانه روی آن دستگاه نیاز دارد. تغییر برنچ یا اتصال، تعریف worktree قبلی را بی‌صدا به‌روزرسانی نمی‌کند: آن را بازبینی و دوباره ذخیره کنید. SHA پس از دریافت ثبت می‌شود؛ دو آماده‌سازی از برنچ متحرک ممکن است SHA متفاوت داشته باشند.

سرور تنها تعریف مخزن‌ها، Markdown واردشده در فرم، تعریف شخصی worktree، وضعیت دستگاه و نتیجهٔ commitها را نگه می‌دارد. **محتوای مخزن، خروجی خام Git و مسیر ریشهٔ خصوصی کاربر به سرور ارسال نمی‌شود.** گزارش خطا محدود و بدون توکن است. توکن برای Git در URL، آرگومان یا تنظیمات مخزن نوشته نمی‌شود؛ helper موقت با دسترسی خصوصی پس از هر بخش حذف می‌شود. اتصال Git redirect را دنبال نمی‌کند و تنظیمات Git سراسری، credential helper، hook و اجرای submodule غیرفعال‌اند. آماده‌سازی سورس، فایل‌های مخزن یا Markdown را اجرا نمی‌کند و هرگز push انجام نمی‌دهد. به‌روزرسانی درجا با درخواست کاربر merge محلی انجام می‌دهد؛ چیزی به GitLab ارسال نمی‌شود. اجرای گره‌های برنامه از مسیر جداگانهٔ Runner نسخهٔ ۲ انجام می‌شود.

## به‌روزرسانی در همان پوشه

بستهٔ جدید Runner را از صفحهٔ Runner دریافت و نسخهٔ در حال اجرا را با آن جایگزین کنید؛ pairing مجدد لازم نیست و فایل خصوصی تنظیمات را حفظ کنید. قابلیت `source-update-v1` پس از اجرای مجدد ثبت می‌شود. سرور به Runner قدیمی کار به‌روزرسانی نمی‌دهد.

روی همان دستگاه، «به‌روزرسانی در همین پوشه» را بزنید. آخرین آماده‌سازی هر worktree و دستگاه حتی بیرون از پنجرهٔ ۱۰۰تایی سابقه نمایش داده می‌شود؛ سرور نیز ثبت دوبارهٔ آماده‌سازی اولیه برای سورس موجود را رد می‌کند تا صفحهٔ قدیمی یا retry باعث پوشهٔ تکراری نشود. Runner برنچ انتخاب‌شده را fetch می‌کند؛ در اولین به‌روزرسانی ممکن است برای یافتن نیای مشترک، تاریخچهٔ shallow را کامل کند. commitهای محلی با Git merge و هویت `Kara Runner` حفظ و ادغام می‌شوند. فایل‌های ذخیره‌نشده، تغییرات stageشده و فایل‌های untracked ابتدا با `git stash --include-untracked` پشتیبان می‌گیرند و پس از ادغام با حفظ index دوباره اعمال می‌شوند. پشتیبان stash و refهای `refs/kara/backups/<update-job-id>/head` و `/stash` باقی می‌مانند؛ پوشهٔ کامل دیگری ساخته نمی‌شود. فایل‌های ignored stash نمی‌شوند و merge اجازهٔ بازنویسی آن‌ها را ندارد.

اگر اتصال یا فرایند Runner پس از stash قطع شود، تلاش بعدی stash ثبت‌شده در دفتر بازیابی محلی را پیش از ادامه بازمی‌گرداند؛ حتی قطع بین ساخت stash و ثبت شناسهٔ آن پوشش داده می‌شود. قفل سیستم‌عامل نیز از به‌روزرسانی هم‌زمان همان پوشه توسط دو فرایند Runner جلوگیری می‌کند و پس از خروج یا crash آزاد می‌شود.

اگر Git تعارض تشخیص دهد، عملیات با پیام تعارض متوقف می‌شود؛ هیچ `reset --hard`، `clean`، حذف stash یا abort خودکاری انجام نمی‌شود. در پوشهٔ بخش مربوط، `git status` و `git stash list` را بررسی کنید. تعارض merge را حل و commit کنید یا با تصمیم خودتان abort کنید. اگر تغییرات stash هنوز اعمال نشده‌اند، stash مربوط به شناسهٔ به‌روزرسانی را پس از حل merge اعمال کنید. اگر تعارض مربوط به اعمال stash باشد، فایل‌های متعارض را حل کنید. سپس دوباره به‌روزرسانی را بزنید. در فضای چندمخزنی ممکن است بخش‌های قبلی به‌روز شده باشند و یک بخش تعارض داشته باشد؛ تا موفقیت کامل، سورس قابل انتخاب برای اجرای جدید نیست.

درخواست جدید فقط بر روی همان پروژه، مالک، Runner و ساختار بخش‌ها اجرا می‌شود. تغییر مسیر بخش، مخزن یا مستندات تعریف‌شده نیاز به worktree تازه دارد؛ فایل‌های مستند محلی در به‌روزرسانی بازنویسی نمی‌شوند. اگر اجرا یا مأموریت فعالی به نسخهٔ قبلی وابسته باشد، ابتدا باید پایان یابد یا لغو شود. هنگام شروع به‌روزرسانی، نسخهٔ قبلی در سابقه به‌عنوان جایگزین‌شده حفظ و از انتخاب‌های اجرا کنار گذاشته می‌شود. پس از موفقیت، اتصال فعلی پروژه به همین سورس به شناسهٔ جدید منتقل می‌شود؛ در صورت خطا یا قطع ارتباط، استفاده از نسخهٔ قبلی تا به‌روزرسانی موفق بعدی مسدود می‌ماند.

## دسترسی و قطع ارتباط

- اتصال GitLab، worktree، Runner و سابقهٔ آماده‌سازی فقط برای حساب مالک قابل مشاهده و اجرا هستند؛ حتی مدیر پروژه توکن شخص دیگر را دریافت نمی‌کند.
- اعتبار دستگاه روی سرور فقط به‌صورت هش ذخیره می‌شود. هر فراخوانی دستگاه، فعال‌بودن حساب، دستگاه، عضویت پروژه و نسخهٔ مخزن و اتصال مربوط به کار را دوباره بررسی می‌کند.
- فقط دستگاه مقصد می‌تواند کار را claim کند، credential همان کار را بگیرد یا نتیجه را ثبت کند. API دستگاه، مجوز اجرای برنامه یا دسترسی به API کنسول نمی‌دهد.
- هر worktree هم‌زمان یک آماده‌سازی فعال دارد. کلید اقدام از ایجاد تکراری ناشی از retry جلوگیری می‌کند.
- Runner هر ۱۰ ثانیه در زمان اجرای Git، اعتبار کار را بررسی می‌کند. لغو کار یا دستگاه در بررسی بعدی اجرای محلی را متوقف می‌کند. قطع کامل ارتباط باعث توقف فرمان جاری پس از timeout ارتباط می‌شود؛ lease سرور ۹۰ ثانیه است و در خواندن بعدی وضعیت، کار «ارتباط Runner قطع شد» می‌گیرد. کارهای در صف تا رسیدن دستگاه منتظر می‌مانند و قابل لغو هستند.
- لغو دسترسی دستگاه، کارهای فعال آن را لغو می‌کند؛ حذف یا لغو، فایل‌های محلی را پاک نمی‌کند. اتصال دوباره نیازمند کد تازه و فایل تنظیمات تازه است.
- تعویض یا حذف توکن در حین دریافت نمی‌تواند credentialی را که قبلاً به حافظهٔ Runner رسیده پس بگیرد؛ برای ابطال فوری توکن، آن را در GitLab نیز revoke کنید.

## بررسی پیاده‌سازی

`make check` شامل قرارداد مسیر/URL/برنچ، دو مخزن ساختگی با worktree واقعی، SHA دقیق، مستندات و حفظ ویرایش‌های قبلی است. آزمون‌های PostgreSQL ماژول‌های `company_projects.test_gitlab_connections` و `company_projects.test_source_code`، جداسازی حساب و پروژه، مالکیت، رمزگذاری، مقصد، کد یک‌بارمصرف، دستگاه، lease، نسخه، لغو و مسیر HTTP دستگاه را پوشش می‌دهند. ساخت وب شامل TypeScript و تست ترتیب منو است. مهاجرت‌ها فقط جدول تازه ایجاد می‌کنند؛ `test_team_migrations` حفظ داده‌های قبلی را کنترل می‌کند.

دریافت واقعی از GitLab خصوصی مستلزم توکن، شبکه و اجرای Runner توسط کاربر است؛ آزمون محلی Git با مخزن ساختگی جای آن را اثبات نمی‌کند.

منابع قرارداد Git: [Git worktree](https://git-scm.com/docs/git-worktree)، [مجوزهای توکن GitLab](https://docs.gitlab.com/security/tokens/access_token_scopes/).
