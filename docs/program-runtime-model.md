# انتخاب مدل شخصی هنگام اجرای برنامه

در برنامه‌های مبتنی بر Workflow و Chatflow با شروع دستی، «مدل اجرای برنامه» یک ورودی مخصوص کارا است. سازنده نیازهای مدل را تعیین می‌کند و اجراکننده اتصال شخصی خودش را انتخاب می‌کند. یک تعریف برنامه می‌تواند بین کاربران مشترک باشد؛ انتخاب مدل و توکن هر اجراکننده مستقل می‌ماند.

## ساخت و استفاده

1. در برنامهٔ جدید، مرحلهٔ «شروع» ورودی مدل اجراکننده را دارد. در برنامهٔ فعلی، مرحلهٔ شروع را باز و «انتخاب مدل توسط اجراکننده» را فعال کنید. این تغییر ابتدا پیش‌نویس است؛ انتشار و مجوزهای اجرای تیمی روال عادی خود را دارند.
2. نیاز به خروجی JSON، فراخوانی ابزار یا پردازش تصویر را مشخص کنید. نیاز به تصویر و خروجی ساختاریافتهٔ مراحل LLM نیز خودکار بررسی می‌شود.
3. تمام مراحل از نوع LLM در این برنامه از یک انتخاب مشترک استفاده می‌کنند. مدل مشخص هنگام ساخت و انتشار لازم نیست. پارامترهای هر مرحله حفظ می‌شوند؛ می‌توانید temperature و حداکثر توکن را تعیین یا با اقدام صریح از پیش‌فرض‌های مدل استفاده کنید.
4. در فرم اجرای آزمایشی، برنامهٔ منتشرشده، اجرای مرحلهٔ LLM/iteration/loop و اجرای تیمی، اتصال شخصی را انتخاب کنید. انتخاب خالی به معنی مدل پیش‌فرض شخصی اجراکننده است. نبود مدل پیش‌فرض سازگار، مجوز استفاده از مدل فرد دیگر یا جایگزینی خودکار با یک مدل دیگر ایجاد نمی‌کند.
5. فقط اتصال‌های LLM از نوع chat و سازگار با نیازمندی‌های اعلام‌شده نمایش داده می‌شوند. وجود افزونه، مالکیت اتصال، عضویت، قابلیت‌ها و سازگاری پارامترهای مراحل در سرور دوباره بررسی می‌شود؛ پارامتر ناشناخته یا خارج از محدوده بی‌صدا حذف نمی‌شود.
6. اتصال، توکن و دسترسی شبکه را از «تنظیمات و اتصال‌ها → اتصال به مدل هوش مصنوعی» مدیریت کنید. ذخیرهٔ برنامه یا نمایش فهرست مدل‌ها اجرای inference ایجاد نمی‌کند؛ دریافت metadata مدل ممکن است با سرویس افزونه ارتباط بگیرد.

قالب‌های آمادهٔ جدید نیز مدل را در زمان اجرا می‌گیرند و برای ساخت، اتصال شخصی سازنده لازم ندارند. قالب‌های نیازمند دانش همچنان به دانش مجاز و آماده نیاز دارند. برنامه‌های قدیمی خودکار تبدیل نمی‌شوند و تا فعال‌کردن گزینه، همان مدل تعیین‌شده در نسخهٔ خود را با توکن شخصی اجراکننده استفاده می‌کنند.

## اجرا، صف و سابقه

- ورودی رزروشدهٔ `__kara_model_connection` فقط شناسهٔ اتصال را می‌پذیرد. نوع آن در گراف با `kara_model_input: {version: 1, capabilities: [...]}` مشخص است. این ورودی از ورودی‌های کاری و pool متغیرهای اجرای مدل کنار گذاشته می‌شود؛ توکن، URL و تنظیمات خام مدل از فرم اجرا پذیرفته نمی‌شوند.
- در صف ایجنت تیمی، شناسهٔ انتخاب‌شده یا پیش‌فرض هنگام ایجاد تلاش ثبت می‌شود. ورودی‌های درخواست، تحویل مراحل، digest و تصمیم‌های انسانی با این انتخاب جایگزین نمی‌شوند. سرور هنگام اجرای واقعی دوباره مالکیت و سازگاری را بررسی می‌کند.
- برای هر اجرا، یک شیء transient از Workflow ساخته می‌شود. گراف نسخهٔ منتشرشده، fingerprint، مجوزها و انتخاب سایر کاربران تغییر نمی‌کند.
- گراف ذخیره‌شدهٔ اجرای بومی شامل ارائه‌دهنده، نام مدل و پارامترهای تعیین‌شده در مراحل است. metadata غیرمحرمانهٔ انتخاب در `kara_runtime_model_used` و extras مربوط به pause ذخیره می‌شود. بخش جزئیات سابقه، مدل همان اجرا را نشان می‌دهد.
- ادامهٔ اجرای متوقف‌شده از همان انتخاب ثبت‌شده استفاده می‌کند. حذف اتصال، تغییر revision یا لغو عضویت آن را متوقف می‌کند؛ پیش‌فرض تازه جای انتخاب قبلی را نمی‌گیرد. در مرز نهایی افزونه همچنان اعتبارنامهٔ شخصی حساب واقعی دوباره خوانده می‌شود.
- اتوماسیون بدون انتخاب صریح از پیش‌فرض شخصی حساب ثبت‌شدهٔ اجراکننده استفاده می‌کند. اجرای ناشناس از توکن مشترک استفاده نمی‌کند.

## محدودهٔ نسخهٔ اول و بررسی

این قابلیت یک انتخاب مشترک برای nodeهای نوع LLM در Workflow/Chatflow با شروع دستی است. انتخاب مدل مجزا برای هر مرحله، مدل‌های embedding/rerank، ایجنت داخلی، برنامه‌های قدیمی Chat/Completion و شروع‌های بدون Start به این ورودی متصل نمی‌شوند و تنظیم شخصی قبلی خود را دارند. مدل runtime باید chat باشد؛ prompt قدیمی completion در نسخهٔ همان اجرا به یک پیام user تبدیل می‌شود. منبع منتشرشده دست‌نخورده می‌ماند.

تست‌های متمرکز PostgreSQL و adapter بومی با مدل و انتقال شبکهٔ ساختگی، مالکیت، نبود fallback، سازگاری، نسخهٔ منبع، انتشار بدون مدل سازنده، انتقال انتخاب به اجرا/iteration/loop/صف و حفظ ورودی‌های تیمی را بررسی می‌کنند. این تست‌ها تأیید اجرای مدل واقعی یا تست کلاینت نیستند.
