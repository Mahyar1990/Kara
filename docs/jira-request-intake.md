# ورود پاسخ ذخیره‌شدهٔ جیرا به درخواست‌های تیم

در پروژه، «درخواست‌های تیم → ورود از جیرا» را باز کنید. مدیر پروژه، ادمین کلِ عضو پروژه یا PO می‌تواند ورود را انجام دهد. حساب و فضای فعال از نشست گرفته می‌شوند. نقش مدیر کارا به‌تنهایی مجوز پروژه ایجاد نمی‌کند.

1. نشانی پایهٔ HTTPS جیرا را بدون توکن و هدر وارد کنید؛ مسیر نصب، اگر وجود دارد، جزئی از نشانی است. این نشانی شناسهٔ منبع است و در این مرحله فراخوانی نمی‌شود.
2. یکی از اجراهای موفق اخیرِ خودتان در همین پروژه را انتخاب کنید. اجرای آزمایشی نیز قابل انتخاب است و به‌عنوان اجرای منتشرشده معرفی نمی‌شود. فقط ۵۰ اجرای موفق اخیر بررسی می‌شوند؛ خروجی سازگار باید `issues`، `total` و `start_at` یا `startAt` داشته باشد. برنامه‌های ثبت‌شده در ایجنت‌های تیم، حتی بایگانی‌شده، از این مسیر قابل خواندن نیستند.
3. یا «پاسخ JSON ذخیره‌شده» را انتخاب و بدنهٔ واقعی پاسخ جست‌وجو را وارد کنید. متن نمایشی تب نتیجه، دستور cURL و اعتبارنامه ورودی این فرم نیستند.
4. «ثبت و به‌روزرسانی درخواست‌ها» را بزنید. نتیجهٔ هر مورد و تعداد صفحهٔ دریافت‌شده نمایش داده می‌شود. موفقیت یک صفحه، دریافت کل نتایج نیست.

این گام هیچ اتصال زنده، زمان‌بندی، اعتبارنامهٔ سرویس، ارسال به جیرا یا شروع اجرای تیمی ندارد. Workflow را خود کاربر اجرا و نتیجهٔ مشخص را صریحاً وارد می‌کند. فراخوانی در VDI و انتقال پاسخ ذخیره‌شده نیز از همین قرارداد استفاده می‌کند؛ دسترسی شبکه از روی یک نمونهٔ JSON اثبات نمی‌شود. دریافت خودکار و ثبت پیوسته، مرحلهٔ مستقل بعدی است.

## رفتار ثبت و به‌روزرسانی

- کلید جلوگیری از تکرار: پروژه، فضای پروژه، نشانی پایهٔ استانداردشده و `issue.id`. کلید نمایشی جیرا شناسهٔ اصلی ارتباط نیست.
- عنوان از `fields.summary` و متن از `fields.description`، بدون خلاصه‌سازی مدل، می‌آیند. نبودن فیلد description رد می‌شود تا پاسخ ناقص متن موجود را پاک نکند؛ توضیحات null به متن خالی تبدیل و null اصلی در آخرین snapshot منبع حفظ می‌شود. نوع فیچر/باگ/ساپورت حدس زده نمی‌شود؛ قرارداد تعیین نوع، کار جداگانه‌ای است.
- حداکثر هر ورود ۱۰۰ issue و دو مگابایت JSON است. شناسهٔ تکراری در همان صفحه، زمان بدون منطقهٔ زمانی، شمارنده‌های ناسازگار و خطای جیرا پیش از نوشتن رد می‌شوند. همهٔ موارد یک ورود در یک تراکنش‌اند.
- دریافت مجدد همان محتوا درخواست تازه یا نسخهٔ تازه نمی‌سازد. نسخهٔ قدیمی‌تر بر اساس `fields.updated` نادیده گرفته می‌شود. replay همان کلید و payload نتیجهٔ قبلی را برمی‌گرداند؛ اختیار در هر replay دوباره بررسی می‌شود.
- تغییر عنوان یا متن، نسخهٔ بومی با منشأ `jira` می‌سازد؛ پیوست‌های فعلی حفظ می‌شوند، تصمیم ورود جاری اعتبار خود را از دست می‌دهد و بازیابی موجود، مراحل وابسته را stale می‌کند. نسخه‌ها، تصمیم‌های تاریخی و تحلیل‌ها حذف یا بازنویسی نمی‌شوند.
- تغییر صرفاً مشخصات منبع مانند وضعیت، اولویت یا مسئول، متن درخواست و تأیید PO را تغییر نمی‌دهد. وضعیت جیرا در کنار وضعیت رسیدگی کارا نمایش داده می‌شود.
- اگر متن جاری کارا از آخرین متن واردشده جدا شده باشد، تغییر منبع جای آن را نمی‌گیرد. آخرین عنوان و متن جیرا در جزئیات برای بررسی نمایش داده می‌شوند. PO می‌تواند نسخهٔ مناسب را با «اصلاح درخواست» ثبت کند؛ اگر دو متن مطابق شوند، دریافت مجدد پرچم تعارض را برمی‌دارد. هیچ ادغام یا پذیرش انسانی جعل نمی‌شود.
- نبودن یک issue در یک صفحه هیچ داده‌ای را حذف نمی‌کند. تشخیص حذف، خروج از فیلتر و تغییر دسترسی به تطبیق مستقل نیاز دارد.

## API

زیر `/console/api/company/projects/<project_id>/team/requests`، با نشست و CSRF بومی:

- `GET /jira/runs`: فهرست حداقلی اجراهای خودِ کاربر؛ متن خروجی و prompt در فهرست عرضه نمی‌شوند.
- `POST /jira/import`: با `Idempotency-Key` استاندارد UUID و یکی از دو بدنهٔ زیر؛ actor، منشأ نسخه و پروژهٔ مقصد از دادهٔ معتبر سرور تعیین می‌شوند.

```json
{"base_url":"https://jira.example.com","run_id":"<workflow-run-uuid>"}
```

```json
{"base_url":"https://jira.example.com","response":{"startAt":0,"total":0,"issues":[]}}
```

خروجی شامل `data` با شناسهٔ درخواست و نتیجهٔ هر مورد، `received_count`، `total`، `start_at` و `has_more` است. نتیجه یکی از `created`، `updated`، `metadata_updated`، `unchanged`، `older_ignored` و `needs_review` است. گرفتن موفقیت به معنی دریافت زنده از جیرا یا تأیید محتوای مشتری نیست؛ منشأ import را کاربر ارائه می‌کند.

مهاجرت افزایشی `007_jira_intake` جدول ارتباط و آخرین snapshot منبع را اضافه می‌کند و قید منشأ نسخه را گسترش می‌دهد؛ checksum مهاجرت‌های قبلی ثابت است. متن‌های درخواست در تاریخچهٔ بومی حفظ می‌شوند؛ snapshot جدول اتصال فقط آخرین پاسخ دریافت‌شده است و آرشیو کامل تغییر مشخصات جیرا نیست.

## بررسی این گام

سه تست PostgreSQL با دادهٔ ساختگی، ثبت تکراری و replay، تغییر متادیتا بدون ابطال تصمیم، نسخه‌سازی متن، حفظ ویرایش انسانی، ورودی نامعتبر، جداسازی پروژه و مالکیت/وضعیت اجرای Workflow را بررسی می‌کنند. تست کلاینت و مرورگر برای این تغییر اجرا نمی‌شود. اعتبار اتصال واقعی جیرا و دریافت همهٔ صفحه‌ها موضوع این گام نیست.
