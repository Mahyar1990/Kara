# Workflow تحلیلگر PA-04

**به‌روزرسانی اتصال نهایی:** بستهٔ 0.1.3 اعلان hook نسخهٔ ۱ Kara را روی همان Code validator دارد؛ revision دستور 0.1.2 و schema ثابت‌اند. [گزارش اتصال اعتبارسنج](clasor-finalization-hook.md) مرجع جاری است؛ نسخه‌ها و نتایج زیر سابقهٔ گام‌های قبلی‌اند.

۲۳ اکتبر ۲۰۲۶ — گام ۲ برنامهٔ کلاسور؛ شاخهٔ `clasor-agents`.

**وضعیت:** بستهٔ قابل import نسخهٔ 0.1.2 آماده و بررسی محلی موفق است؛ پذیرش مدل و دور بازخورد هنوز انجام نشده‌اند. دو تلاش واقعی نسخه‌های 0.1.0 و 0.1.1 در Kara اجرا شدند و به‌درستی در اعتبارسنج متوقف شدند. این وضعیت مربوط به تحویل اولیه بود؛ اکنون 0.1.2 در برنامهٔ مستقل پایلوت وارد/منتشر و ثبت شده است؛ [گزارش آماده‌سازی بومی](clasor-native-definitions.md) مرجع آن است. کیفیت مدل و تصمیم PO هنوز پذیرفته نشده‌اند. این مرحله مجوز شروع مسیر PO → TL نیست.

## بسته و بازسازی

- [اعتبارسنج هویت اجرای بومی](../clasor_agents/pa04/native.py)، متصل به [قرارداد 1.0.0](clasor-pa04-contract.md).
- [آزمون‌های متمرکز](../scripts/test_clasor_pa04_workflow.py)؛ فقط کتابخانهٔ استاندارد Python، بدون فراخوانی مدل.

```sh
.venv/bin/python scripts/build_clasor_pa04.py --check
.venv/bin/python -m unittest scripts.test_clasor_pa04_workflow
```

`workflow.json` همان DSL اپلیکیشن و JSON معتبرِ قابل خواندن به‌صورت YAML است؛ برخلاف bundle قرارداد، برای import استودیو ساخته شده است. برای فایل YAML معمول می‌توان بدون تغییر مقادیر آن را با یک YAML serializer تبدیل کرد؛ آزمون import نسخه‌های قبلی از همین روش استفاده کرد. نسخهٔ فنی مبنا Dify 1.17.1 و افزونهٔ رسمی OpenAI API Compatible نسخهٔ 0.0.68 با شناسهٔ کامل ثابت در DSL است. هیچ endpoint، توکن یا حساب محیط در export وجود ندارد.

manifest، hash دستور، graph، سازنده، قرارداد و adapter را نگه می‌دارد. تغییر دستور و export با هم ثبت شوند؛ بازسازی hash به‌تنهایی شاهد پذیرش نیست.

## مسیر اجرا و مرز اعتماد

`Start → کنترل ورودی Code → LLM → اعتبارسنج Code → End`

چهار ورودی Start همان `request`، `mode`، `source_context` و `feedback_context` هستند. درخواست دست‌نخورده می‌ماند؛ JSON منابع/تحلیل قبلی در source_context و سابقهٔ انسانی در feedback_context قرار می‌گیرد. بازخورد خالی اولیهٔ Start مجاز است و None بومی به رشتهٔ خالی تبدیل می‌شود. برای binding ثابت فلوی تیمی، Kara حتی مقدار ثابت اختیاری را غیرخالی اعتبارسنجی می‌کند؛ پایلوت از «هنوز بازخوردی ثبت نشده است.» استفاده می‌کند. در clarify/review_change بازخورد و در review_change تحلیل پیشین نیز لازم است.

Code اول نوع، اندازه، شناسه/هش منابع و حالت را پیش از مدل بررسی می‌کند. Code دوم علت پایان واقعی LLM را می‌خواند؛ فقط `stop` و JSON منطبق با schema، hash درخواست و نگاشت شرط → نیازمندی → AC را به End می‌رساند. خروجی فقط `analysis` به‌صورت متن JSON است. فایل/شبکه در Code استفاده نمی‌شود، retry مدل خاموش است و خطای validator به خروجی موفق تبدیل نمی‌شود.

این گیت محتوایی UUID پروژه/مرحله یا ACL را از مدل نمی‌گیرد. در caller قابل اعتماد، binding از درخواست و StageInstance خوانده می‌شود؛ revision پیش از run، شناسهٔ تلاش از پاسخ run و workflow/actor از snapshot سرور ذخیره می‌شوند. پس از اجرا، `validate_native_result` باید با این هویت مستقل و metadata واقعی WorkflowRun/گرهٔ LLM فراخوانی شود. گرفتن expected_identity یا expected_binding از پاسخ مدل مجاز نیست. این helper کلاینت HTTP، احراز هویت، تغییر وضعیت یا جایگزین مجوزهای Kara نیست؛ native execution همچنان نسخه، مسئول مشخص و grant را کنترل می‌کند.

در بررسی زندهٔ این مرحله شناسه‌های واقعی درخواست/نسخه/مرحله/تلاش استفاده شدند؛ request/hash و چهار مقدار preview_inputs با envelope قرارداد تطبیق یافتند. WorkflowRun به همان تلاش، actor و Workflow منتشرشده متصل بود. adapter هر دو تلاش ناموفق را رد کرد. هنوز نمونهٔ موفقی برای بررسی Artifact و پیوند بازخورد واقعی وجود ندارد.

## مدل و بودجه

پروفایل مستقل پایلوت با alias `Clasor PA04 Pilot v0.1.1`، زمینهٔ تنظیم‌شدهٔ ۱۶۳۸۴ و سقف پاسخ ۴۰۹۶ توکن است؛ نام فنی alias بیانگر ظرفیت مدل واقعی نیست. `compatibility_mode=extended` و `agent_thought_support=not_supported` درخواست خاموش‌کردن thinking را به سرویس سازگار ارسال می‌کنند؛ پشتیبانی سرویس باید جدا تأیید شود. `stream_include_usage=disabled` نیز در اتصال آزمایشی ثبت شد، اما مشکل metadata را رفع نکرد. این گزینه‌ها در manifest هستند و DSL به‌تنهایی credential مدل را تنظیم نمی‌کند.

اتصال smoke قبلی با سقف ۴۰۹۶/۵۱۲ و پیش‌فرض مدل پروژه تغییر نکرد. حد پیشنهادی ۲۰۴۸ در manifest تاریخیِ بستهٔ قرارداد، تنظیم فعال Workflow نیست. حدود ۳۲KiB/تعداد منابع همچنان برقرارند؛ سقف نویسه تضمین بودجهٔ توکن نیست. داده‌های کوتاه ساختگی این نوبت آزمون ظرفیت حداکثری یا منبع خصوصی مخزن محسوب نمی‌شوند.

مصرف گزارش‌شدهٔ دو اجرای بومی به‌ترتیب ۶۴۳۵ و ۴۹۲۲ توکن بود؛ جمع ۱۱۳۵۷، شامل prompt و پاسخ. مبلغ صفرِ گزارش‌شده تعرفهٔ مدل شرکت نیست و ادعای رایگان‌بودن ندارد. یک probe مستقیمِ تشخیصی با سقف پاسخ ۳۲ توکن نیز انجام شد؛ این probe اجرای موفق PA-04 محسوب نمی‌شود و در جمع WorkflowRunها نیست. پس از مشخص‌شدن مانع، نمونه‌های دیگر و retry مدل اجرا نشدند.

در probe، HTTP 200 و پایان SSE دریافت شد: یک chunk علت `length` داشت و سپس chunk آمار مصرف با `choices[0].finish_reason=null` آمد. SDK نصب‌شده علت پایان را در هر choice بازنویسی می‌کند؛ این ترتیب، علت معتبر را پاک می‌کند. خاموش‌کردن درخواست آمار هم در اجرای 0.1.1 علت پایان را حفظ نکرد. محل ناسازگاری در مسیر metadata سرویس/افزونه مشخص است؛ برای نسخهٔ اصلاحی هنوز شاهد موفق نداریم. طبق توضیح کاربر VPN ممکن است اتصال به LLM شرکت را مختل کند؛ این اجراها پاسخ دریافت کردند، اما از آن نمی‌توان سلامت دائمی شبکه را نتیجه گرفت.

متن خام 0.1.1 با وجود دریافت‌شدن، پذیرش معنایی هم ندارد: رفتار بازخوانی حفظ شده بود، اما شرط/نیازمندی تکراری، فرض وجود رفتار فعلی و موارد خارج‌ازمحدودهٔ اعلام‌نشده دیده شد. دستور 0.1.2 برای اتمی‌بودن، عدم تکرار، حفظ شناسه در بازخورد و خودداری از این استنتاج‌ها روشن‌تر شد. اثر این اصلاح هنوز با مدل آزموده نشده است. ارزیابی معنایی انسان با قبولی schema یکی نیست.

هر دو Stage در `failed` مانده‌اند؛ صفر Artifact معتبر، صفر feedback و صفر تصمیم نهایی ثبت شد. رابط وب نیز تلاش ناموفق، نبود خروجی و صفر مرحلهٔ نهایی‌شده را نمایش داد. تأیید ورود صرفاً با حساب PO ساختگی برای آزمون بود؛ تصمیم واقعی PO/TL تولید نشده است. سوابق شکست و تنظیمات خصوصی در `.runtime/clasor-pa04/` حفظ شده‌اند.

## بررسی کوتاه و ادامه

- ۸ آزمون جدیدِ Workflow/adapter و ۱۱ آزمون قرارداد؛ اجرای نهایی `make check`: **۷۳ آزمون موفق**. کد دقیق Code با چهار پاسخ مرجع بررسی شد؛ این چهار پاسخ، خروجی مدل نیستند.
- Code آماده‌سازی/اعتبارسنج در sandbox واقعی اجرا شدند؛ import/publish و ثبت ایجنت/فلوی تک‌مرحله‌ای در پایلوت واقعی انجام شدند. graph اجرایی منتشرشدهٔ 0.1.1 با export همان نسخه یکسان بود؛ import فقط viewport چیدمان بوم را حذف کرد.
- Compose و `make doctor` موفق؛ کلاینت HTTP 200، API pong، فارسی/RTL برقرار. API/web بستر تغییر نکردند و rebuild/تست کامل کلاینت تکرار نشد.
- hash/count داده‌های اصلی ۳۱ جدول بیرون از پایلوت و اجرای smoke قبلی حفظ شد؛ هر چهار ref محلی sandbox با خط مبنا یکسان ماندند.

قدم بعد **رفع و اثبات انتقال finish_reason واقعی** است؛ در نبود آن `stop` حدس زده نشود. اصلاح عمومی اتصال/افزونه، اگر لازم شود، کار مستقل بستر روی `master` است و upstream داخل `.runtime/dify` ویرایش نمی‌شود. پس از آن 0.1.2 در برنامه/نسخهٔ تازه import شود، نمونهٔ روشن، مبهم، منفی/صفر/انتظار/خطا و یک دور feedback بومی اجرا شوند. تعارض منبع، سؤال صرفاً فنی، منبع حاوی دستور جعلی و review_change نیز پذیرش معنایی زندهٔ تأییدشده ندارند. ابتدا یک نمونه برای بازشدن گیت؛ سپس فقط موارد باقی‌مانده اجرا شوند. بعد از قبولی تحلیلگر، اتصال PO → TL مطرح می‌شود.
