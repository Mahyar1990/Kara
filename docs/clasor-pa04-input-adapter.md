# بستهٔ ورودی تخصصی PA-04

وضعیت: سازنده و پیش‌پرواز آفلاین؛ بدون اجرای مدل، HTTP یا تغییر بستر.

[inputs.py](../clasor_agents/pa04/inputs.py) روی پاسخ‌های خواندنی API فعلی Kara کار می‌کند:
`assemble(request, instance, stage, source_catalog, selected_source_ids, ...)`.
request همان جزئیات درخواست با current، instance خلاصهٔ اجرای فلو و stage جزئیات مرحله با preview_inputs/artifacts است. این رکوردها باید از نشست مجاز و خواندن تازهٔ سرور بیایند؛ JSON مدل یا فایل آپلودشده جای آن‌ها نیست. catalog بستهٔ خصوصیِ منابع بررسی‌شده است و انتخاب فقط با id انجام می‌شود؛ fixtureها ساختگی‌اند.

سازنده تعلق پروژه/فضای کاری، درخواست/نسخه و digest بومی، مرحله/اجرا، اعتبار ورود و حفظ متن اصلی در preview را بررسی می‌کند. متن بدون normalization به Start می‌رود. منابع منتخب با id مرتب و hash محتوا اعتبارسنجی می‌شوند؛ kind قواعد مخزن از evidence جداست. متن منبع، مجوز ایجاد نمی‌کند. برای منابع مخزن، caller باید reference/revision را با manifest خصوصی sandbox تطبیق دهد؛ این سازنده ref مخزن را حدس نمی‌زند یا fetch نمی‌کند.

خروجی شامل envelope معتبر، expected_binding مستقل از مدل، چهار ورودی Start و provenance برای ثبت خصوصی است. digest بومی درخواست (شامل عنوان/پیوست)، digest بومی Artifact و SHA-256 متن‌ها جدا نگهداری می‌شوند. انتخاب خروجی قبلی فقط با شناسه از artifacts همان مرحله/دور/input_digest یا parent صریح رکورد بازخورد دور جاری انجام و محتوای آن مجدداً با قواعد PA-04 بررسی می‌شود؛ آخرین خروجی به‌طور ضمنی انتخاب نمی‌شود. بازبینی یک نسخهٔ تازه با Artifact نسخهٔ قدیمی در این مسیر پشتیبانی نشده و نیازمند مسیر صریح نسخه‌دار است.

ترتیب استفاده:

1. پاسخ‌های تازه و منابع مجاز را بخوانید؛ بسته را بسازید و binding/provenance را خصوصی ذخیره کنید.
2. چهار ورودی را در تنظیم مرحله/بازخورد نگاشت کنید؛ متغیر بازخورد فقط feedback_context باشد. این helper چیزی روی سرور ثبت نمی‌کند.
3. جزئیات مرحله را دوباره بخوانید و بسته را با revision تازه بسازید. برای اجرای پس از بازخورد، feedback_context باید رشتهٔ مؤثر سرور شامل سابقه باشد؛ آن را JSON خالص فرض نکنید. `check_preview(package, stage)` تطابق دقیق هر چهار ورودی و revision را کنترل می‌کند؛ اختلاف به خطا می‌رسد و خودکار اصلاح نمی‌شود.
4. اجرای واقعی فقط از مسیر مجاز Kara با expected_revision تازه باشد؛ preflight محلی قفل یا ACL نیست. نتیجه با validate_native_result و هویت مستقل تلاش بررسی شود. موفقیت مدل مرحله را نهایی نمی‌کند.

کنترل محلی تغییر request را تشخیص می‌دهد، اما جلوگیری عمومی سمت سرور از تغییر اصل درخواست در بازخورد هنوز وابستگی master است. اجرای validator تخصصی پس از ویرایش انسان و پیش از finalize نیز وابستگی master است؛ این adapter آن را نصب یا دور نمی‌زند. تا آن زمان تحویل واقعی PO → TL پذیرفته نیست.

بررسی: پنج آزمون متمرکز ساخت بسته، نسخه/پروژهٔ ناسازگار، تغییر request، انتخاب خروجی قبلی، منبع دستکاری‌شده و سقف ورودی. آزمون‌ها API-shaped و آفلاین‌اند؛ اتصال HTTP، بازخورد واقعی و پذیرش معنایی باقی‌اند. Workflow/prompt نسخهٔ 0.1.2 تغییر نکرده‌اند.
