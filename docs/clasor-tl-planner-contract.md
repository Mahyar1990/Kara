# قرارداد برنامه‌ریز TL و مسیر تحویل PA-04

نسخهٔ 0.1.0؛ پیش‌نویس اجرایی ورودی، آماده برای ساخت Workflow بعدی. برنامه‌ریز منتشرشده، تصمیم PO واقعی یا پذیرش کامل PO → TL در این قدم وجود ندارد.

این قرارداد ادامهٔ گام ۴ [برنامهٔ کلاسور](clasor-agents-implementation-plan.md) و تطبیق قرارداد/دستور برنامه‌ریز موجود در `clasor-analysis-agents` است؛ تاریخچه یا Workflow قدیمی منتقل نمی‌شود. قرارداد قدیمی هشت بخش بستهٔ توسعه و تفکیک پیشنهاد از تصمیم واقعی را تعریف کرده بود. در مسیر جاری مسئول اجرا و بازخورد برنامه‌ریزی TL است؛ گفت‌وگوی PO/TL/Developer و مرج دستی حفظ می‌شوند. Jira برای مسیر دستی اجباری نیست.

ورودی نسخه‌دار:

| فیلد | مرجع معتبر |
| --- | --- |
| request / request_revision_id / request_sha256 | نسخهٔ دست‌نخوردهٔ درخواست در بستهٔ PA-04 |
| analysis / analysis_sha256 | فقط محتوای analysis منتخب در handoffs مرحلهٔ TL |
| finalization | stage_id، artifact_id، digest بومی، decision_id، finalized_by، finalized_at از رسید مستقل تصمیم انسانی PO |
| stage_id / base_revision | StageInstance برنامه‌ریزی تازه؛ برای اقدام سرور دوباره بررسی شود |
| repositories | چهار کلید server/client/newman/playwright؛ هرکدام ref دقیق و commit کامل sandbox |
| repository_rules / evidence | آرایه‌های جدا با path، commit، content و sha256 متن همان snapshot |

[prepare](../clasor_agents/tl_planner/handoff.py) روی projection خواندنی `stage.handoffs` بستر کار می‌کند؛ دریافت تاریخچهٔ کامل تحلیلگر برای حساب TL لازم نیست. رسید مستقل باید پس از تصمیم واقعی PO ذخیره و با همان نسخهٔ درخواست نگه داشته شود. گرفتن آن از متن تحلیل یا ساختن آن از همان handoff نامعتبر مرز اعتماد را حذف می‌کند. helper اعتبار نشست، نقش PO، انقضای تصمیم ورود، لغو مجوز یا CAS سرور را جایگزین نمی‌کند.

ورودی فقط برای مرحلهٔ ready و intake معتبر ساخته می‌شود؛ handoff، preview و رسید باید دقیقاً یک Artifact/تصمیم را معرفی کنند. PA-04 دوباره اعتبارسنجی می‌شود؛ blocked/needs_clarification مصرف نمی‌شوند. تغییر AC یا ویرایش انسانی پس از تصمیم، رسید/تحلیل تازه و بررسی دوباره می‌خواهد؛ انتخاب خودکار آخرین خروجی مجاز نیست. نمونهٔ تصمیم در تست‌ها ساختگی است و تصمیم انسانی محسوب نمی‌شود.

تمام چهار ref باید `refs/remotes/origin/sandbox` و commit کامل ۴۰رقمی داشته باشند. متن قواعد/شواهد اگر ارسال شود باید همان commit و hash را داشته باشد. نبود AGENTS در مخزن تست به‌معنی خطا نیست؛ آرایهٔ قواعد می‌تواند خالی باشد. آرایهٔ evidence خالی فقط کمبود زمینه است؛ اجازهٔ ادعای مسیر فایل یا روش تست نمی‌دهد. این helper از نام مخزن فناوری یا فرمان تست حدس نمی‌زند؛ refها باید توسط caller از manifest خصوصی جاری خوانده شوند. مسیر محلی، اطلاعات اتصال، دادهٔ مشتری و متن خصوصی وارد Git نشوند. سقف کل بسته ۳۲KiB است؛ برش/خواندن خودکار همهٔ مخزن یا retry مدل نداریم.

قرارداد خروجی برای Workflow بعدی یک کلید متنی `plan` با JSON نسخه‌دار است. فیلدهای الزامی داخل آن:

| فیلد | قاعده |
| --- | --- |
| contract_version، role_id، analysis_sha256 | 0.1.0، TL-PLANNER و hash دقیق تحلیل ورودی |
| status | needs_product_decision / needs_technical_review / ready_for_technical_discussion |
| summary، scope | هدف و مرز تحلیل مصوب؛ تغییر رفتار فقط به صورت سؤال PO |
| repository_impact | هر چهار مخزن با اثر change/run_or_read/unrelated/unknown و دلیل مبتنی بر منبع |
| tasks | شناسه محلی، هدف، نوع، مخازن، ACها، منابع، خروجی قابل تحویل، وابستگی و شرط شروع، روش بررسی و شاهد مورد انتظار |
| coverage | هر AC تحلیل به جزء کار، سناریو، ابزار/مخزن تست، ترکیب نسخه‌ها و شاهد لازم نگاشت شود |
| questions | موضوع، اثر، مسئول پاسخ PO یا TL و مرحلهٔ متوقف‌شده |
| proposals | پیشنهادهای گفت‌وگوی فنی، با منبع؛ ادعای توافق انسان نباشد |
| limitations | زمینهٔ ناموجود/متعارض، تست اجرا‌نشده و محدودیت محیط |

شناسهٔ AC ناشناخته، AC بی‌پوشش، وابستگی گم‌شده/چرخه‌ای، منبع خوانده‌نشده و مخزن تست بی‌دلیل باید در validator خروجی بعدی رد شوند. Newman برای رفتار API و Playwright برای مسیر مرورگر با شواهد پروژه انتخاب شوند؛ اجرای هردو برای هر کار اجباری نیست. قالب هشت‌بخشی قبلی (مشخصات، هدف، مخازن، اجزا، پوشش، ترتیب/محیط، تحویل/MR، پرسش/تصمیم) در نمایش همین داده‌ها حفظ شود. این جدول هنوز JSON Schema/validator خروجی یا DSL ساخته‌شده نیست.

آمادهٔ توسعه یک وضعیت قابل تولید توسط مدل نیست: پس از بازبینی TL، ثبت نتیجهٔ واقعی گفت‌وگوی PO/TL/Developer برای hash همان نسخهٔ plan، تعیین مسئول و رفع مانع مؤثر می‌توان تحویل توسعه را بررسی کرد. مدل نمی‌تواند approved، grants، تصمیم انسانی، اجرای موفق تست یا MR واقعی بسازد. مرج با TL و دستی است.

مسیر اتصال پیشنهادی فلو:

1. مرحلهٔ analysis: مسئول PO، PA-04، بازخورد در feedback_context و خروجی analysis؛ انتخاب و finalize صریح PO.
2. مرحلهٔ planning: مسئول TL با grant مستقل؛ `analysis ← stage.analysis.analysis`؛ باقی زمینه از بستهٔ خصوصی منتخب، request از نسخهٔ اصلی و feedback_context جدا.
3. فقط readyشدن مرحلهٔ TL پس از finalize؛ هیچ اجرای خودکار با حساب PO. بازخوردهای TL نسخه‌های plan بسازند؛ نهایی‌سازی با TL باشد.
4. تغییر تحلیل، ورودی برنامه و گفت‌وگوی وابسته را stale کند. تغییر مسئول فقط از مسیر بومی تغییر مسئول، با حفظ تاریخچه.

وابستگی عمومی باز روی master: حفظ اصل درخواست در بازخورد و hook اعتبارسنج تخصصی پس از ویرایش انسانی/پیش از finalize. انتقال صحیح finish_reason نیز قبل از آزمون مدل لازم است؛ null به stop تبدیل نمی‌شود. این چت این قابلیت‌های عمومی را پیاده‌سازی نمی‌کند.

بررسی این قدم فقط آفلاینِ ورودی/تحویل است. قدم بعد ساخت schema/validator خروجی، prompt و DSL متناظر با همین قرارداد، سپس پس از رفع وابستگی‌ها آزمون واقعی PA-04، بازخورد PO و تحویل TL است. تصمیم نامعتبر، نسخهٔ ناسازگار، منبع ناقص، گفت‌وگوی ثبت‌نشده و تست در مخزن اشتباه باید در پذیرش باقی بمانند.

وضعیت تحویل این نوبت:

| وضعیت | دارایی/کار |
| --- | --- |
| ساخته‌شده | قرارداد PA-04 و Workflow 0.1.2 قبلی؛ سازندهٔ ورودی از رکوردهای Kara و preflight؛ پیش‌پرواز تحویل و قرارداد پیش‌نویس TL |
| ناقص | اتصال HTTP سازنده به اجرای واقعی؛ schema/validator خروجی و prompt/DSL برنامه‌ریز؛ دو وابستگی عمومی Kara |
| صرفاً آزمون‌نشده | انتشار 0.1.2، پذیرش معنایی مدل، بازخورد واقعی PO و چرخهٔ PO → TL؛ موفقیت اتصال OK جای این‌ها نیست |

پنج آزمون سازندهٔ PA-04 و چهار آزمون تحویل TL آفلاین موفق شدند؛ آزمون‌های قبلی قرارداد/Workflow حفظ شدند. هیچ مدل، رابط یا runtime تغییر/اجرا نشد؛ smoke کلاینت موضوعیت نداشت. لاگ‌های طولانی خارج از Git نگهداری شدند.
